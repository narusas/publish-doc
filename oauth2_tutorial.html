00 · 출발 문제 정의

"내 비밀번호를 남의 앱에 알려줘도 될까?"

사진 인화 앱이 여러분의 구글 포토에 있는 사진을 가져오려 합니다. 가장 단순한 방법은 구글 아이디와 비밀번호를 그 앱에 직접 입력하는 것입니다. 그런데 이게 왜 끔찍한 생각일까요?

🚨 비밀번호를 직접 넘기는 방식

  • 그 앱은 이제 여러분 계정 전체를 할 수 있습니다. 사진뿐 아니라 메일, 결제, 비밀번호 변경까지.
  • 앱이 비밀번호를 그대로 저장합니다. 그 회사가 해킹당하면 내 비밀번호도 유출됩니다.
  • 권한을 "사진만"으로 좁힐 방법이 없습니다. 전부 아니면 전무.
  • 앱 하나만 차단하려 해도 비밀번호를 바꾸는 수밖에 없고, 그러면 다른 앱도 전부 끊깁니다.

✅ OAuth2 방식

  • 비밀번호는 구글에만 입력합니다. 앱은 비밀번호를 영원히 보지 못합니다.
  • 앱은 "사진 읽기" 권한만 담긴 토큰(token)을 받습니다.
  • 그 토큰은 몇 시간 뒤 만료되고, 언제든 내가 회수할 수 있습니다.
  • 앱 하나를 끊어도 다른 앱과 내 비밀번호는 멀쩡합니다.
🅰️ 비유로 이해하기

🚗 OAuth2 = 발렛 파킹 키

고급차에는 발렛 키가 따로 있습니다. 이 키로는 시동을 걸고 잠깐 운전만 할 수 있습니다. 트렁크는 안 열리고, 글로브박스도 잠긴 채입니다. 발렛에게 마스터 키(=비밀번호)를 통째로 주는 대신, 딱 필요한 권한만 담긴 제한된 키(=토큰)를 건네는 것 — 이게 OAuth2의 핵심 아이디어입니다.

🧭 한 문장으로 못 박기

OAuth2는 "인증(로그인)"이 아니라 "권한 위임(authorization)" 프레임워크입니다. 즉 "이 앱이 내 데이터에 이런 행동을 해도 좋다"고 허락하는 표준이에요. OIDC(OpenID Connect)는 그 위에 "그래서 지금 로그인한 사람이 누구냐"를 얹은 로그인 표준입니다. 이 둘의 차이가 이 튜토리얼 전체를 관통하는 핵심이니, 천천히 익혀 봅시다.

⚡ Quick Check
OAuth2가 풀려는 가장 근본적인 문제는?
정답은 B. OAuth2는 암호화 알고리즘이 아니라 권한을 안전하게 빌려주는 약속(프로토콜)입니다. "전부 아니면 전무"였던 비밀번호 공유를 "딱 필요한 만큼, 한시적으로"로 바꿔줍니다.
01 · 기초 헷갈리면 끝까지 헷갈리는 한 쌍

인증(Authentication)과 인가(Authorization)는 다른 질문이다

주니어가 가장 많이 섞어 쓰는 두 단어입니다. 이름도 둘 다 'Auth…'로 시작해서 더 헷갈리죠. 하지만 둘은 완전히 다른 질문에 답합니다.

🪪 인증 = AuthN

"너 누구야?"

신원을 확인하는 일. 공항 보안검색대에서 여권을 보여주는 단계입니다.

  • 예: 아이디/비밀번호 로그인, 지문, OTP
  • OIDC에서 담당 — 결과물은 id_token
  • 확인하는 쪽: 클라이언트(앱)

🎫 인가 = AuthZ

"너 이거 해도 돼?"

권한을 확인하는 일. 항공권에 적힌 좌석 등급으로 라운지 입장 여부를 판단하는 단계입니다.

  • 예: "이 사용자는 송장을 읽을 수 있나?"
  • OAuth2에서 담당 — 결과물은 access_token
  • 확인하는 쪽: API 서버(리소스 서버)
🅰️ 비유로 이해하기

✈️ 공항: 여권(인증) → 탑승권(인가)

여권 심사(인증)는 "당신이 진짜 김아무개인가"를 확인합니다. 그 다음 탑승권(인가)은 "당신이 이 비행기, 이 좌석에 탈 수 있는가"를 결정하죠. 여권이 있다고 아무 비행기나 타는 게 아니고, 탑승권이 있다고 그게 당신 신원을 증명하는 것도 아닙니다. 둘은 별개의 검사예요. OAuth2/OIDC도 똑같습니다.

⚠️ 가장 흔한 주니어 실수

access_token(인가용)을 가지고 "이 사람이 로그인했다"고 판단하는 것입니다. access_token은 "이 토큰을 든 자에게 이런 권한이 있다"는 뜻일 뿐, "그게 누구인지"는 보장하지 않습니다. 로그인 여부는 반드시 OIDC의 id_token으로 판단해야 합니다. (이 부분은 OIDC 섹션에서 깊게 다룹니다.)

02 · 기초 다섯 배우

등장인물 다섯을 모르면 모든 용어가 뒤엉킨다

OAuth2 문서의 용어는 딱딱합니다. 하지만 사실은 실제 서비스의 역할 분담일 뿐이에요. 아래 카드를 눌러 각 역할이 정확히 뭘 책임지는지 확인하세요.

🔎 구글 로그인으로 매핑해 보기

사용자=나 · 브라우저=크롬 · 클라이언트=내가 쓰는 사진 앱 · 인증 서버=accounts.google.com · API 서버=photoslibrary.googleapis.com. 한 회사 안에서도 인증 서버와 API 서버는 보통 분리됩니다. 인증 서버는 토큰을 '발급'하고, 각 API 서버는 그 토큰을 '검증'만 하죠.

⚡ Quick Check
access_token이 유효한지, scope가 충분한지를 최종 판단하는 주체는?
정답은 C. 토큰을 발급하는 건 인증 서버지만, 매 API 요청마다 토큰의 유효성·scope·만료·대상(audience)을 검증해서 데이터를 줄지 말지 정하는 건 API 서버입니다.
03 · 기초 토큰이 도대체 뭔데

토큰은 "이미 확인받았다"는 증표다

토큰(token)은 매번 신원을 다시 증명하지 않아도 되게 해주는 증표입니다. 한 번 제대로 확인받고 나면, 그 다음부터는 토큰만 내밀면 됩니다.

🅰️ 비유로 이해하기

🎟️ access_token = 콘서트 입장 팔찌

입구에서 신분증과 티켓을 확인(=로그인)받고 나면 손목에 팔찌(=access_token)를 채워줍니다. 공연장 안에서는 신분증을 다시 안 보여줘도 돼요. 팔찌만 보여주면 음료 바, VIP존(=scope) 출입이 됩니다. 팔찌를 찬 사람이 곧 권한자라서 — 이게 Bearer 토큰의 의미입니다. 팔찌를 주우면 누구든 쓸 수 있으니 절대 흘리면 안 됩니다.

토큰에도 종류가 있다 — 두 가지 형태

토큰한 줄 요약누가 읽나비유
access_tokenAPI를 호출할 권한API 서버입장 팔찌
id_token"이 사람은 누구"라는 신원 증명(OIDC)클라이언트명찰 / 신분증
refresh_token만료된 access_token을 새로 받는 교환권클라이언트팔찌 재발급권

⚠️ 자주 틀리는 포인트: id_token은 API 호출용이 아닙니다. "이 사람이 누구다"를 클라이언트가 확인하는 용도일 뿐, API 서버에 보내면 안 됩니다.

⚡ Quick Check
"Bearer 토큰"이라는 말의 핵심 의미는?
정답은 B. Bearer = "지참인". 팔찌처럼 가진 사람이 곧 권한자이므로, URL이나 로그에 남기지 말고 Authorization: Bearer <token> 헤더로만, HTTPS 위에서 주고받아야 합니다.
04 · 핵심 가장 중요한 그림

로그인 버튼 한 번에 일어나는 16단계, 전부 따라가 보자

이게 이 튜토리얼의 심장입니다. Authorization Code + PKCE 흐름 — 오늘날 웹·앱 로그인의 표준입니다. 다음 ▶ 버튼을 눌러 메시지가 누구에게서 누구에게로 가는지 한 줄씩 지켜보세요. 각 단계의 실제 HTTP 메시지가 아래에 펼쳐집니다.

🔑 보기 전에 딱 하나만: 프론트채널 vs 백채널

┄ 프론트채널 = 브라우저(주소창)를 거쳐 오가는 메시지. 사용자도 보이고, 가로채일 수도 있는 '노출된' 통로입니다. → 그래서 여기로는 민감한 토큰을 직접 보내지 않습니다.
━ 백채널 = 서버끼리 직접 주고받는 통신(HTTPS). 브라우저를 안 거칩니다. → client_secret과 실제 토큰 교환은 전부 여기서 일어납니다.

⚡ Quick Check
authorization code가 브라우저 주소창(프론트채널)으로 돌아오는데, 왜 그걸 훔쳐도 공격자가 토큰을 못 받을까요? (대표적 이유 하나)
정답은 A. code 자체는 '교환권'에 불과합니다. 그걸 토큰으로 바꾸려면 백채널에서 code_verifier(PKCE)와 클라이언트 인증이 추가로 필요하죠. 그래서 코드만 새어나가도 공격이 성립하지 않습니다. PKCE는 다음에 자세히 봅니다.
05 · 단계별 1단계

로그인 버튼은 사실 'authorization request URL'을 만든다

사용자가 버튼을 누르면, 앱은 브라우저를 인증 서버로 보냅니다. 그 주소(URL)에 들어가는 파라미터 하나하나가 보안의 핵심입니다. 아래에서 scope를 켜고 끄며 URL이 어떻게 바뀌는지 직접 만들어 보세요.

🛠 Authorization URL 빌더

요청할 권한(scope) 고르기




각 파라미터의 뜻

  • response_type=code: "코드 방식으로 줘" (요즘 표준)

05 · 단계별 3단계

    
돌아오는 건 토큰이 아니라 'authorization code'다

    
동의가 끝나면 인증 서버는 브라우저를 다시 앱으로 돌려보냅니다(redirect). 이때 주소창에 ?code=...&state=...가 붙어 옵니다. 이 code는 토큰이 아니라, 토큰으로 바꿀 수 있는 짧은 수명의 교환권입니다.


    

      
🅰️ 비유로 이해하기

      
🧥 authorization code = 물품보관소 교환권

      
코트를 맡기면 번호표(교환권)를 줍니다. 번호표 자체는 코트가 아니에요. 나중에 카운터(백채널)에서 번호표를 내밀어야 코트(토큰)로 바꿔줍니다. 그래서 누가 번호표 사진을 몰래 찍어도(프론트채널 노출), 카운터에서 추가 확인(PKCE·클라이언트 인증)을 통과 못 하면 코트를 못 가져갑니다.

    


    
그런데 왜 코드를 한 번 더 교환할까?

    
코드는 브라우저 주소창을 거쳐 옵니다. 주소창은 기록에도 남고, 확장 프로그램이 볼 수도 있는 '노출된' 통로(프론트채널)예요. 그래서 진짜 권한이 담긴 토큰은 여기로 직접 보내지 않고, 다음 단계인 백채널 토큰 교환에서 안전하게 받습니다.


    
🛡️ state: 위조 방지 도장

    
요청을 보낼 때 만든 임의의 state 값을, 돌아온 응답의 state와 대조합니다. 다르면? 다른 흐름의 응답이거나 공격(CSRF)일 수 있으니 즉시 폐기합니다.

05 · 단계별 핵심 보안 장치

    
PKCE: 코드를 훔쳐가도 못 쓰게 만드는 안전핀

    
PKCE(픽시, Proof Key for Code Exchange)는 코드 탈취 공격을 무력화합니다. 원리는 간단해요 — 먼저 비밀(code_verifier)을 만들고, 그 자물쇠(code_challenge)만 미리 보낸 뒤, 나중에 토큰을 받을 때 비밀 원본을 증명하게 합니다.


    

      
🅰️ 비유로 이해하기

      
🔐 code_verifier = 열쇠 원본 · code_challenge = 그 열쇠로만 열리는 자물쇠

      
1) 앱이 무작위 비밀 code_verifier(열쇠)를 만듭니다. 2) 그것의 해시 code_challenge(자물쇠)만 인가 요청에 실어 보냅니다. 자물쇠로는 열쇠를 역산할 수 없어요. 3) 나중에 토큰을 받을 때 열쇠 원본을 제시합니다. 인증 서버는 "이 열쇠가 그때 그 자물쇠를 여나?"를 확인하죠. 코드를 훔친 공격자에겐 열쇠 원본이 없으니 토큰 교환에 실패합니다.

    


    

      
🧪 직접 해보기 — 실제 SHA-256 해싱

      
      

        
        
      

      

      
위 challenge 값은 여러분 브라우저가 실제로 SHA-256으로 계산한 결과입니다(데모). 같은 verifier를 넣으면 항상 같은 challenge가 나오죠 — 이게 인증 서버가 검증하는 방식이에요.

    


    

      
⚡ Quick Check

      
공격자가 authorization code는 훔쳤지만 code_verifier는 모릅니다. 토큰 교환의 결과는?

      
      
      
      
정답은 A. PKCE는 특히 client_secret을 숨길 수 없는 SPA·모바일 앱(public client)에서 필수입니다. 요즘은 비밀을 보관할 수 있는 서버 앱에서도 함께 쓰는 게 권장돼요.

07 · 심화 로그인의 완성

    
OIDC: "그래서 로그인한 사람이 누구냐"

    
OAuth2만으로는 "누가 로그인했는지"를 안전하게 알 수 없습니다. OIDC는 OAuth2 위에 신원 계층을 얹어, 검증 가능한 id_token으로 그 답을 줍니다.


    

      
OAuth2 (인가)
  • 질문: "이 API 호출 권한 있나?"
  • 핵심 토큰: access_token
  • 검증 주체: API 서버
  • 토큰 내용: 클라이언트가 들여다볼 필요 없음(opaque일 수 있음)

      
OIDC (인증)
  • 질문: "이 사용자 누구야?"
  • 핵심 토큰: id_token (항상 JWT)
  • 검증 주체: 클라이언트
  • 토큰 내용: 사용자 정보(claims)를 담음

    


    
🔬 id_token(JWT) 해부 — 직접 디코딩하고 서명 검증까지

    
JWT는 점(.)으로 나뉜 세 조각입니다: 헤더.페이로드.서명. 앞 두 조각은 그냥 base64로 인코딩됐을 뿐 암호화가 아니라서 누구나 읽습니다. 신뢰는 오직 세 번째 '서명'을 검증해야 생깁니다. 아래에서 실제로 해봅시다.

08 · 심화 어디서 도느냐가 다 바꾼다

    
웹 서버 · SPA · 모바일 · CLI — secret을 숨길 수 있느냐

    
같은 Authorization Code 흐름이라도, 앱이 어디서 실행되느냐에 따라 보안 설계가 갈립니다. 기준은 단 하나 — "client_secret을 안전하게 숨길 수 있는가?"


    

      

        
🔒 Confidential Client (비밀 보관 가능)

        
서버에서 도는 앱. 코드가 서버에만 있어 client_secret을 안전하게 숨길 수 있습니다. → 백채널에서 secret으로 자신을 인증.

        
예: 전통적 웹 서버 앱(Spring, Django, Rails), 백엔드 서비스

      

      

        
🌐 Public Client (비밀 못 숨김)

        
사용자 기기에서 도는 앱. 자바스크립트·앱 바이너리를 뜯어보면 secret이 보입니다. → secret을 안 쓰고 PKCE로 보호.

        
예: SPA(React/Vue), 모바일 앱, 데스크톱·CLI

      

    


    

      
🧭 플랫폼별 설계 탐색기

      

        
        
        
        
      

      

    


    

      
⛔ 이제는 쓰지 않는 옛 방식

      
Implicit flow(브라우저로 access_token을 바로 던지던 방식)는 토큰이 주소창에 노출돼 위험합니다. 요즘은 SPA도 Authorization Code + PKCE를 씁니다. ROPC(사용자 비밀번호를 앱이 직접 받는 방식)도 OAuth2가 없애려던 문제를 되살리므로 피하세요.

    

  


  
  

    
09 · 심화 사람이 없을 때

    
사람이 없는 호출: client credentials · service token · PAT

    
배치 작업, 마이크로서비스 간 통신, CI/CD 파이프라인… 로그인할 '사람'이 없는 호출은 지금까지의 브라우저 흐름이 통째로 필요 없습니다. 동의 화면도, id_token도, redirect도 없죠. 대신 서비스가 '자기 자신'으로 토큰을 받습니다.


    
🤖 Client Credentials Grant — 서비스의 정식 로그인

    
OAuth2 표준 grant입니다. 클라이언트가 자신의 자격증명(client_id + client_secret)만으로 access_token을 받습니다. 토큰의 주체(subject)는 사용자가 아니라 그 서비스 자신이에요. 흐름이 얼마나 단순한지 보세요 — 단 두 번의 백채널 왕복입니다.

    


    
📚 세 가지를 똑바로 구분하기

    

      

        
Client Credentials OAuth2 표준

        
백엔드·배치·내부 워커가 자기 자신으로 호출. 사용자 동의·id_token·redirect 없음.

        
grant_type=client_credentials
&scope=invoice:read

        
주체: service:billing-worker

      

      

        
Service Token 우산 용어

        
워크로드·자동화에 주는 자격증명을 폭넓게 부르는 말. 형태는 다양합니다:

        
    
          
  • OAuth2 CC 토큰
    • 
          
  • 정적 API 키
    • 
          
  • 클라우드 workload identity (AWS IAM Role, GCP SA, K8s SA, SPIFFE)
    • 
        

      

      

        
PAT 개인 계정 위험

        
Personal Access Token: 사람 계정의 권한을 API 토큰처럼 쓰는 것. 표준 OAuth2 grant가 아님(제품별 기능).

        
    
          
  • 로컬 스크립트·임시 작업엔 OK
    • 
          
  • 운영 서비스 기본값으론 위험
    • 
        

      

    


    
🆚 PAT가 왜 위험한가

    

      
    
        
  • 주체가 '사람'이다. 그 사람이 퇴사하면 운영 서비스가 갑자기 멈춥니다. 감사 로그도 "김개발이 했다"로 찍혀 진짜 행위 주체(서비스)가 가려집니다.
    • 
        
  • 권한이 과하다. 보통 그 사람 계정의 넓은 권한을 그대로 물려받습니다. (그래서 GitHub은 권한을 좁히는 fine-grained PAT를 권장)
    • 
        
  • 오래 산다 & 잘 샌다. 만료를 안 걸면 영원히 유효하고, 실수로 코드에 커밋돼 유출되는 사고가 가장 흔합니다.
    • 
      

    

    
그래서 PAT를 쓸 거면: fine-grained 우선만료일 필수secret manager 보관절대 커밋 금지정기 회전


    
🧭 어떤 토큰을 써야 할까 — 결정 도우미

    

      

        
        
      

      

    


    

      
상황권장 방식주의할 점

      
사용자 로그인Authorization Code + PKCE + OIDCPAT/서비스 토큰으로 '로그인 흉내' 내지 말 것

      
백엔드가 자기 권한으로 호출Client Credentials / workload identity주체는 service:billing이지 user:kim이 아님

      
CI/CD 자동화짧은 수명 service token / app installation token저장소·환경 단위 scope + 감사 로그

      
로컬 개발 스크립트fine-grained PAT (제한적 허용)만료·최소 scope·이름·보관 위치 강제

      
서비스가 사용자 대행명시적 delegation / on-behalf-of 설계몰래 사용자처럼 쓰면 감사 모델 붕괴

    


    

      
⚡ Quick Check

      
운영 백엔드가 매시간 billing API를 자기 권한으로 호출해야 합니다. 가장 적절한 선택은?

      
      
      
      
정답은 C. 사람이 없는 호출은 서비스 자신을 주체로 하고, 짧은 만료·최소 scope·감사 로그를 갖춘 토큰을 써야 합니다. A는 사람 의존·과권한, B는 id_token을 API에 쓰는 흔한 오용입니다.

💾 토큰을 브라우저 어디에 저장하나?

      
SPA에서 토큰을 localStorage에 두면 편하지만 XSS 한 방에 통째로 털립니다. 반대로 HttpOnly 쿠키는 JS가 못 읽어 XSS엔 강하지만 CSRF 대비(SameSite 등)가 필요하죠. 정답은 상황마다 다르고, 점점 BFF(Backend-for-Frontend) 패턴 — 토큰은 백엔드가 쥐고 브라우저엔 세션 쿠키만 주는 방식 — 이 권장됩니다.
