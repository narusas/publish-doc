# 웹 애플리케이션 인증 기초 튜토리얼 — 설계 문서

- 날짜: 2026-08-14
- 산출물: `auth_basics.html` (신규), `index.html` (카드 추가)
- 시리즈: 인터랙티브 개발 튜토리얼 모음 (7번째 문서)

## 1. 왜 만드는가

`index.html`의 순서상 `https_tutorial.html` 다음이 `oauth2_tutorial.html`이다. 두 문서 사이의
낙차가 너무 크다.

- `https_tutorial.html` — **"두 기계 사이의 통신을 어떻게 지키나"**에서 끝난다.
  사람을 알아보는 이야기는 한 줄도 없다.
- `oauth2_tutorial.html` — **"인증을 남에게 맡기려면"**에서 시작한다. 세션·쿠키·토큰이
  이미 무엇인지 아는 독자를 전제로 인가 코드 흐름으로 바로 들어간다.

즉 **"내 서버가 직접 사람을 알아본다"는 층이 통째로 비어 있다.** 대부분의 개발자가 실제로
매일 다루는 층이 바로 그곳이고, OAuth를 이해하려 해도 그 층을 먼저 알아야 한다.
이 문서가 그 자리를 채운다.

동시에 두 문서를 잇는 다리가 된다. HTTPS 문서의 해시·서명·대칭/비대칭키가 이 문서의
비밀번호 저장(2장)과 JWT 서명(10장)에서 **다시 설명되지 않고 이름만 불린 채로 회수되고**,
마지막 장(14장)이 OAuth 문서의 첫 문장("내 비밀번호를 남의 앱에 알려줘도 될까?")으로
그대로 넘어간다.

## 2. 척추

> **"서버를 두 대로 늘렸더니 사용자들이 자꾸 로그아웃된다."**

Hero에서 이 증상을 던지고 곧바로 되감는다 — *"이 증상을 설명하려면, 서버가 애초에 나를
어떻게 기억하는지부터 봐야 한다."* 7장에서 정면으로 회수한다.

**전개 방식**: 문제의 사슬. `network_basics.html`의 전개를 계승한다. 계층 순서도 시간 순서도
아니고, **답 하나가 다음 문제를 만들어 내는 순서**로 간다.

각 장은 앞 장이 만든 문제 하나를 풀고, 풀면서 다음 문제를 만든다. 규칙 둘:

1. 장 제목은 그 장이 푸는 **문제**여야 한다. 개념 이름을 제목으로 쓰지 않는다.
2. 모든 장은 "그래서 다음이 필요해졌다"로 끝난다.

## 3. 독자와 선수 지식

- **대상**: Spring Boot로 로그인을 붙여 봤지만, `@AuthenticationPrincipal`에 무엇이 어떻게
  담기는지는 설명하지 못하는 주니어.
- **전제하는 것**: HTTP 요청/응답의 모양, HTTPS가 통신을 암호화한다는 사실. 해시와 서명의
  개념. 앞 두 문서 수준.
- **전제하지 않는 것**: Spring Security의 어떤 것도. 세션·쿠키·JWT의 정의도.
- **난이도 표시**: 제목 옆 🟢 필수 / 🔵 심화 (`iam_tutorial.html`의 `.lvl` 패턴).

### Spring을 어디에 두는가

이 문서의 결정 중 가장 중요한 것이다. **본문은 프레임워크 중립으로 쓰고, Spring은 각 장
끝의 `.spring` 블록으로 분리한다.** 그 블록은 개념을 가르치지 않고 이름만 잇는다 —
*"방금 그 개념, Spring에서는 이 이름이다."*

근거:

- 이 시리즈의 다른 문서 중 특정 프레임워크에 묶인 것이 하나도 없다. 축을 깨면 시리즈가 아니게 된다.
- 개념을 프레임워크 안에서 설명하면 독자가 **개념과 그 프레임워크의 선택을 구분하지 못한다.**
  세션 고정 방어는 개념이고, `changeSessionId`는 Spring의 선택이다.
- `.spring` 블록을 통째로 건너뛰어도 논지가 끊기지 않아야 한다. 이것이 이 결정의 검수 기준이다.

## 4. 구성 — 15장 + 부록 3

### Hero

증상 제시(`.diag` 자가진단) → 되감기 선언 → 지도(`.map-grid`) → 읽는 법.

### 1부 · 증표가 필요해지기까지 (1~6장)

#### 1장 · 🕳️ HTTP는 방금 그 사람을 기억하지 못한다 🟢

- 요청 둘은 서로 남남이다. keep-alive로 커넥션을 재사용해도 그것은 신원이 아니다.
- "IP로 구분하면 되지 않나" — NAT 뒤에서 수천 명이 한 IP를 쓰고, 모바일은 IP가 바뀐다.
- **데모**: 서버가 요청 하나에서 볼 수 있는 것을 전부 펼쳐 놓고, 그중 나를 특정할 수 있는
  것이 없음을 확인한다.
- **다음 문제**: 매 요청이 스스로 신원을 증명해야 한다.

#### 2장 · 🔐 그럼 매 요청에 아이디·비번을 보내면 안 되나 🟢

- 실제로 그런 방식이 있다 — HTTP Basic. `Authorization: Basic base64(id:pw)`.
- **base64는 암호가 아니다.** (→ HTTPS 문서 회수: 그래서 TLS가 전제다)
- 문제 셋: ① 비번이 매번 네트워크에 흐른다 ② 서버가 매번 검증해야 한다 ③ 로그아웃이라는
  개념 자체가 없다.
- ②에서 **비밀번호 저장**으로 들어간다: 평문 → 해시 → 레인보우 테이블 → salt →
  bcrypt·argon2의 work factor. 핵심 프레이밍은 **"느린 것이 버그가 아니라 기능이다."**
- **데모**: SHA-256 즉시 계산 vs bcrypt 체감 지연, 같은 비밀번호를 쓰는 두 계정이 salt로
  갈라지는 것.
- **회수를 심는 사실(V2)**: bcrypt는 **work factor를 해시 문자열 안에 함께 저장한다.** 그래서
  나중에 강도를 올려도 기존 비밀번호가 깨지지 않는다 — "느린 것이 기능이다"가 운영 가능한
  설계인 이유다. 기본 강도는 10, 범위는 4~31, salt 16바이트를 자체 포함한다.
- **`.spring`**: `PasswordEncoder`, `DelegatingPasswordEncoder`의 `{bcrypt}` 접두어. (→ V2 —
  접두어 문자열은 코드로 쓰기 전에 재확인할 것)
- **다음 문제**: 한 번만 확인하고 그 다음엔 다른 것을 쓰자.

#### 3장 · 🎟️ 한 번만 확인하고, 그 다음엔 증표를 쓴다 🟢

- 증표(credential이 아니라 token)라는 개념. 확인은 1회, 사용은 N회.
- **갈림길 제시** — (a) 서버가 기억하고 열쇠만 준다 (b) 증표 자체에 내용을 담는다.
  이 갈림길이 문서 나머지 전부를 결정한다. 지도로 못 박고 12장에서 회수한다.
- 어느 쪽이든 남는 공통 요구: 브라우저가 그것을 **매 요청에 붙여야 한다.**
- **다음 문제**: 어떻게 자동으로 붙이나.

#### 4장 · 🍪 쿠키 — 브라우저가 알아서 붙여 주는 것 🟢

- `Set-Cookie` / `Cookie` 헤더의 왕복.
- 속성을 정의 순서가 아니라 **각각이 막는 공격 순서**로 배열한다:
  `Secure`(평문 전송) · `HttpOnly`(XSS 탈취) · `SameSite`(CSRF) · `Domain`/`Path`(범위) ·
  `Max-Age`/`Expires`(수명).
- `Secure`에는 **localhost 예외**가 있다 — 로컬에서 되던 것이 배포하면 안 되는 이유 중 하나.
- **데모**: 속성 토글 시뮬레이터 — 어떤 요청에 붙고 안 붙는지.
- **`.spring`**: `server.servlet.session.cookie.*`. (→ V3, V6)
- **⚠️ 서술 주의(V6)**: "요즘 브라우저는 `SameSite` 기본이 `Lax`"라고 **단정하지 않는다.**
  MDN은 "*some* browsers"라고 쓴다.
- **다음 문제**: 그래서 그 쿠키에 무엇을 담나.

#### 5장 · 🗄️ 세션 — 서버가 기억하는 방식 🟢

- 세션 ID는 **뜻이 없는 난수**여야 한다. 추측 가능하면 나머지 전부가 무의미해진다.
- 서버 안의 `Map<sessionId, 사용자>`. 쿠키에는 열쇠만, 내용은 서버에.
- 세션 고정 공격(session fixation)과 **로그인 성공 시 세션 ID 재발급**.
- **데모**: 세션 저장소 들여다보기 + 세션 고정 재현.
- **`.spring`**: `HttpSession`, 세션 고정 방어 기본 전략. (→ V4)
- **다음 문제**: "자동으로 붙는다"는 편의에 대가가 있다.

#### 6장 · 🎣 자동으로 붙는다는 성질의 대가 — CSRF 🟢

- 쿠키는 *누가 그 요청을 만들었든* 붙는다. 남의 사이트가 만든 폼도 내 쿠키를 달고 간다.
- 방어 셋: `SameSite` / CSRF 토큰(동기화 토큰 패턴) / `Origin`·`Referer` 검사.
- **"`SameSite` 기본값이 생겼으니 CSRF는 끝난 문제"가 왜 틀린가** (V6이 근거를 준다):
  브라우저가 *기본으로* 적용하는 `Lax`는 개발자가 *명시한* `Lax`보다 느슨하다 —
  **설정된 지 2분 이내면 교차 사이트 `POST`에도 쿠키가 붙는다.** 기본값에 기대는 것과
  명시하는 것은 같지 않다.
- **복선**: `Authorization` 헤더 방식에는 왜 이 문제가 없나 — **자동으로 붙지 않기 때문이다.**
  12장 비교표에서 회수한다.
- **데모**: 공격 페이지 재현 — 방어를 하나씩 켜며 막히는 지점 확인.
- **`.spring`**: CSRF는 **기본 활성**이다. 보호 대상은 **서블릿이 `GET`·`TRACE`·`HEAD`·`OPTIONS`를
  제외한 전부**, **리액티브가 `PUT`·`POST`·`DELETE`** — **둘이 다르다**(V7). 뭉뚱그리지 않는다.
  `csrf().disable()`의 정당한 조건은 공식 표현 그대로 쓴다 — *"애플리케이션이 브라우저에서
  전혀 쓰이지 않을 때만 권장된다."*
- **다음 문제**: 여기까지는 서버가 한 대일 때의 이야기다.

### 2부 · 서버가 여러 대가 되면 (7~9장) ← 척추 회수

#### 7장 · 💥 서버를 두 대로 늘렸더니 자꾸 로그아웃된다 🟢

- Hero 회수. 세션은 **그 서버의 메모리 안에** 있다. LB가 B로 보내면 B는 모른다.
- 첫 답: **sticky session**(세션 어피니티). LB가 같은 사용자를 같은 서버로 보낸다.
- 그 대가 넷:
  1. 서버 하나가 죽으면 그 서버 몫의 사용자 전원이 로그아웃된다
  2. 스케일 아웃해도 기존 사용자는 옮겨가지 않아 부하가 풀리지 않는다
  3. **배포할 때마다 전원 로그아웃된다** — 가장 자주 겪는 증상
  4. 축소(scale in) 시 연결이 끊긴다
- **데모**: LB + 서버 2대 시뮬레이터 — 요청을 던지며 로그아웃이 나는 순간 확인.
- **다음 문제**: 그러면 증표를 나눠 갖게 하자.

#### 8장 · 🔗 증표를 나눠 갖기 — 세션 클러스터링과 공유 저장소 🟢

두 갈래를 **비용 곡선**으로 갈라 본다. 이 장의 논점은 "무엇이 있나"가 아니라 "무엇이 어디서
무너지나"다.

- **복제형 (세션 클러스터링)** — 서버끼리 세션을 복사한다. (→ V5, 수치 근거 확보됨)
  - all-to-all 방식은 **모든 세션을 다른 모든 노드에** 복제한다. 노드가 늘면 복제 대상이
    대수가 아니라 조합 수로 는다. **Tomcat 문서 자신이 "4대 남짓을 넘으면 권장하지 않는다"고
    쓴다.**
  - 낭비의 성격을 한 줄로 보여 주는 사실: all-to-all은 **그 애플리케이션이 배포되지도 않은
    노드에까지** 세션을 보낸다.
  - 백업본을 하나만 두는 방식으로 완화하지만, 메모리 중복과 GC 압박은 남는다.
- **중앙 저장소형** — 상태를 서버 밖으로 뺀다(Redis 등).
  - 서버가 진짜 무상태가 되고, 배포·오토스케일이 자유로워진다. 7장의 대가 넷이 전부 사라진다.
  - 대가: **매 요청마다 네트워크 왕복 한 번**, 직렬화 비용, 그리고 그 저장소가 새 단일
    장애점이 되어 그것도 이중화해야 한다.

- **데모**: 서버 수를 슬라이더로 늘리며 세 방식(sticky · 복제 · 중앙)에서 **한 세션이 몇 곳에
  복사되는지, 요청당 원격 조회가 몇 번인지**를 나란히 본다.
  **대역폭·지연의 절대 수치는 그리지 않는다** — 근거가 없다. 구조만 보인다.
- **`.spring`**: Spring Session — 애플리케이션 코드를 거의 바꾸지 않고 저장소만 갈아 끼운다.
  **단 기본 쿠키 이름이 `JSESSIONID`가 아니라 `SESSION`으로 바뀐다**(V3). 배포 직후 전원이
  로그아웃된 것처럼 보이는 실제 원인이 되므로, 이 함정을 이 장의 마무리로 쓴다.
- **다음 문제**: 이 답들은 "누가 기억하나"를 바꿨을 뿐, 여전히 누군가는 기억한다.

#### 9장 · 🕊️ 아무도 기억하지 않게 할 수는 없나 🟢 **[전환점]**

이 문서에서 가장 중요한 장이다. 대부분의 글이 "MSA니까 JWT"로 뭉개는 자리를 정면으로 다룬다.

- 8장의 중앙 저장소는 문제를 **옮겼을 뿐이다.** 그것으로도 안 되는 지점 넷:
  1. **서버가 수십·수백 대이고 오토스케일한다** — 요청 부하가 곧 저장소 부하다
  2. **서비스가 여러 개다** — 서비스마다 같은 저장소를 때리면 그것이 전 조직의 병목이자
     공통 장애점이 된다
  3. **도메인이 여러 개다** — 쿠키는 도메인에 갇힌다
  4. **클라이언트가 브라우저가 아니다** — 모바일 앱·CLI·서버 간 호출에는 쿠키 상자가 없다
- 그래서 질문을 뒤집는다: 조회가 필요한 이유는 증표가 **비어 있기** 때문이다. 증표 안에
  내용을 담고 **위조만 막으면** 조회가 사라진다. 위조를 막는 도구는 이미 배웠다 —
  **서명.** (→ HTTPS 문서 회수)
- 그리고 이 거래의 값을 **미리** 명시한다:
  > **조회 없음을 사고, 취소 가능성을 판다.**
  11장이 이 청구서를 받는다.
- **데모**: 같은 요청을 세션 방식과 무상태 방식으로 처리했을 때 서버가 하는 일 비교.

### 3부 · 상태 없는 증표 (10~12장)

#### 10장 · 🎫 JWT — 증표 안에 내용을 담는다 🟢

- `header.payload.signature`, base64url 인코딩.
- **암호화가 아니다 — 누구나 읽는다.** (2장의 "base64는 암호가 아니다"가 그대로 돌아온다)
- 서명이 보증하는 것: 위조 불가. 보증하지 않는 것: **비밀 유지, 최신성.**
- HMAC(대칭) vs RSA·ECDSA(비대칭) — 후자라야 검증 권한만 나눠 주고 발급 권한은 쥐고 있을
  수 있다. (→ HTTPS 문서의 대칭/비대칭 회수)
- `alg: none` — **검증할 알고리즘을 토큰이 스스로 고르게 두면 검증이 사라진다.** 방어는
  서버가 기대 알고리즘을 고정하는 것.
  **⚠️ 서술 제한(V8): CVE 번호도, 특정 라이브러리·버전도 쓰지 않는다.** 확인에 실패했다.
  공격의 원리와 방어 원칙만 쓴다.
- **데모**: JWT 해부기 — payload를 직접 고쳐 서명이 깨지는 것을 눈으로 확인.
  `alg`를 `none`으로 바꿔 보는 것도 여기에 붙이되, **실제 라이브러리의 동작이 아니라
  "검증자가 헤더를 믿으면 무슨 일이 생기는가"를 보인다.**

#### 11장 · ⏳ 청구서 — 취소할 수 없다는 것 🟢

- 발급한 순간 서버의 손을 떠난다. 로그아웃·권한 박탈·비밀번호 변경이 **즉시 반영되지 않는다.**
- 대응과 그 값:
  - 짧은 만료 + refresh 토큰
  - 블랙리스트 — **두는 순간 조회가 돌아온다. 9장의 거래가 무효화된다.**
  - 토큰 버전 / `iat` 기준 무효화
- refresh 토큰 회전(rotation)과 재사용 탐지.
- refresh 토큰은 어디에 두나 → `HttpOnly` 쿠키. **4장이 돌아온다.**
- **데모**: 만료·갱신 타임라인 — 권한을 박탈한 뒤 언제부터 실제로 막히는지.

#### 12장 · ⚖️ 그래서 세션이냐 토큰이냐 🟢

- 3장의 갈림길 회수. 정직한 결론부터: **브라우저를 상대하는 단일 서비스라면 세션이 기본값이다.**
- 흔한 오해 격파:
  - "SPA니까 JWT" — 무관하다. SPA도 쿠키 세션을 쓴다.
  - "MSA니까 JWT" — 게이트웨이에서 세션을 받아 내부 토큰으로 바꾸는 구성이 흔하다.
- `localStorage` vs 쿠키 논쟁의 실체: **XSS가 나면 둘 다 진다.** `HttpOnly`가 그나마 낫다.
- 비교표 + 선택 가이드. 6장의 복선(헤더는 자동으로 안 붙는다)을 CSRF 행에서 회수한다.

### 4부 · 코드 안의 자리 (13~15장)

#### 13장 · 🚧 이 검사는 요청 처리의 어디에 끼는가 🟢

- 컨트롤러가 아니다. **요청이 컨트롤러에 닿기 전에 끝나야 한다.**
- 필터/미들웨어 체인, 그리고 순서: 인증(누구냐) → 컨텍스트에 담기 → 인가(해도 되냐).
- 익명 사용자도 하나의 주체다.
- **`@AuthenticationPrincipal`에 대체 무엇이 어떻게 담기는가**에 여기서 답한다. 이 문서를
  찾아오는 독자의 실제 질문이다.
- **데모**: 요청이 필터 체인을 통과하는 재생기 — 어느 필터에서 무엇이 결정되는지.
- **`.spring`**: `SecurityFilterChain`, `SecurityContextHolder`. 그리고 Spring Security 6의
  변경 하나 — `SecurityContextPersistenceFilter`(읽고 **쓰던** 것)가
  `SecurityContextHolderFilter`(**읽기만** 하는 것)로 바뀌었다. (→ V1)
  **⚠️ 서술 제한(V1): "직접 `SecurityContextHolder`에 값을 넣는 커스텀 코드는 명시적으로
  저장해야 한다"까지만 쓴다.** 내장 폼 로그인 필터가 어떤 경로로 저장하는지는 확정하지
  못했으므로 서술하지 않는다.
- **다음 문제**: 여기까지 전부 한 가지 전제 위에 있었다.

#### 14장 · 🚪 그런데, 남의 비밀번호를 우리가 받아도 되나 🟢 **[인계]**

- 1~13장 전부가 *"우리 서버가 사용자의 비밀번호를 직접 받는다"* 위에 서 있었다.
  그 전제가 깨지는 상황 셋:
  1. 사용자가 우리를 믿지 않는다
  2. 우리 서비스가 **남의 서비스에 있는 데이터**에 접근해야 한다
  3. 회사 안에 서비스가 스무 개다 — 스무 번 로그인할 수는 없다
- 인증을 남에게 맡긴다 = **위임.** → `oauth2_tutorial.html`로.
- **못 하나를 박고 끝낸다**: 위임해도 4~13장은 그대로다. 위임의 결과를 받아서 **결국 세션이나
  토큰을 만든다.** 두 문서를 잇는 문장이 이것이다.

#### 15장 · 🏁 마무리 — 내 서비스는 지금 어느 쪽인가

체크리스트(`.ckl`) + Hero 자가진단 회수.

  `.spring` 조각들이 여기서 한 벌로 합쳐진다. (→ V1)

## 6. 구현 규약

| 항목 | 결정 |
|---|---|
| 파일 | `auth_basics.html` (신규 단일 파일) — `network_basics.html`과 대칭 |

카드끼리 혼동되지 않는다. 기존 `--auth`(amber)와 나란히 두면 인증 계열임도 읽힌다.

### 손대지 않는 것

`oauth2_tutorial.html`은 **건드리지 않는다.** 그 문서의 "인증 vs 인가", "등장인물 다섯",
"토큰은 증표다" 세 챕터가 새 문서와 겹치지만, 중복을 허용한다.

- 각 문서가 독립적으로 완결되는 것이 이 시리즈의 성격이다.
- 다루는 각도가 다르다 — 새 문서는 *"내 서버가 직접 묻는 인증"*, `oauth2`는 *"남에게 맡기는 인증"*.
- 기존 독자의 저장된 진행률과 퀴즈 기록이 섹션 id에 묶여 있다.
- 그 파일에는 별건으로 판단해야 할 알려진 결함이 이미 있다
  (`docs/superpowers/notes/2026-08-14-known-issues.md` §1, §2, §3).

## 7. 구현 전에 확인할 사실

`docs/superpowers/notes/2026-08-14-known-issues.md` §5의 교훈 — 지난 문서의 사실 오류 **네 건이
전부 기억으로 쓴 계획서에서 나왔다.** 아래는 공식 문서로 확인한 뒤에 쓴다. 특히 Spring
Security 6에서 바뀐 것들이 검색으로 나오는 낡은 글과 다르다.

검증 결과와 근거는 `docs/superpowers/notes/2026-08-14-auth-facts.md`에 기록한다.

| # | 확인 대상 | 영향받는 곳 | 결과 |
|---|---|---|---|
| V1 | `SecurityContext` 자동 저장이 사라진 변경(`requireExplicitSave`)의 기본값 | 13장, 부록 A | **확인됨** — 6에서 기본 true. `SecurityContextPersistenceFilter`(읽기+쓰기) → `SecurityContextHolderFilter`(**읽기 전용**). 단 내장 로그인 필터의 저장 경로는 확정 실패 → 13장은 "커스텀 코드는 명시 저장 필요"까지만 쓴다 |
| V2 | `BCryptPasswordEncoder` 기본 강도, `DelegatingPasswordEncoder` | 2장 | **확인됨** — 기본 강도 10 (범위 4~31), 16바이트 salt 자체 포함, **강도가 해시 안에 저장되어 나중에 올려도 기존 비번이 안 깨진다**. `{bcrypt}` 접두어 문자열만 원문 인용 실패 |
| V3 | Spring Session 사용 시 쿠키 이름, `SameSite` 기본값 | 4장, 8장 | **확인됨** — 기본 쿠키명이 `SESSION`이다. **`JSESSIONID`가 아니다.** `sameSite` 기본 `Lax`, `maxAge` 기본 `-1` |
| V4 | 세션 고정 방어의 기본 전략 | 5장 | **확인됨** — Servlet 3.1+ 기본은 `changeSessionId`. 그 외 `newSession`·`migrateSession` |
| V5 | Tomcat 세션 복제의 전파 방식과 실용 한계 대수 | 8장 — **복제 비용 데모의 근거** | **확인됨 · 공식 수치 있음** — `DeltaManager`는 all-to-all이고 **"more than 4 nodes or so"**는 권장하지 않는다. `BackupManager`는 백업 1개. DeltaManager는 **앱이 배포되지도 않은 노드에까지** 복제한다 |
| V6 | 브라우저의 `SameSite` 미지정 기본값, `None`에 `Secure` 필수 여부 | 4장, 6장 | **확인됨 · 통념과 다름** — "**Some** browsers use Lax as the default"이므로 전부라고 단정하면 안 된다. 그리고 **기본으로 적용된 Lax는 명시한 Lax보다 느슨하다**(설정 후 2분 내 POST 허용). `None`은 `Secure` 필수 |
| V7 | CSRF 기본 활성 여부와 적용 대상 HTTP 메서드 | 6장 | **확인됨** — 기본 활성. **서블릿은 `GET`·`TRACE`·`HEAD`·`OPTIONS` 제외한 전부, 리액티브는 `PUT`·`POST`·`DELETE`로 서로 다르다** |
| V8 | `alg: none`의 현재 상태와 JVM 라이브러리 대응 | 10장 | **부분 확인 → 서술 범위 축소** — 원리와 방어는 확인됨. **CVE 번호·특정 라이브러리·버전은 쓰지 않는다** (자료마다 `alg:none`과 알고리즘 혼동을 엇갈리게 설명하고, 확인된 사례가 전부 JVM 밖이다) |

전부 근거와 원문 인용을 `docs/superpowers/notes/2026-08-14-auth-facts.md`에 남겼다.

### 검증에서 드러난 것 — 구현자가 반드시 볼 것

- **V1은 검증 도중 한 번 정반대 결론이 나왔다.** 레퍼런스 페이지 요약으로는
  "`requireExplicitSave`는 기본값이 아니다"가 나왔고, 마이그레이션 가이드 원문으로 교차
  확인해 뒤집었다. **이 항목은 낡은 블로그 글이 특히 자주 틀린다.** 기억이나 요약으로
  고쳐 쓰지 말고 facts 파일의 인용문을 근거로 삼는다.
- **V3·V6은 통념과 다른 쪽이 사실이다.** 두 곳 다 "다들 그렇게 알고 있는 것"이 틀렸고,
  그 어긋남 자체가 4·6·8장의 좋은 재료다.
- **V5는 수치를 써도 된다.** 다만 "4대"는 Tomcat 문서의 권고치이지 물리 법칙이 아니다.
  데모는 **복제 대상 수가 노드 수에 따라 늘어나는 구조**를 보이는 데 쓰고, 대역폭이나
  지연의 절대 수치는 지어내지 않는다.
- **V1 후반과 V8은 확인에 실패한 부분이 있다.** 지난 문서의 교훈대로 "불확실하면 완화"가
  아니라 **"확인한 뒤 유지하거나, 아예 쓰지 않는다"**로 처리했다. 해당 서술 제한은 facts
  파일에 적혀 있고, 구현 중에 그 범위를 넓히지 않는다.
