## 2. 이번 검수에서 새로 찾은 것 — 장과 장 이음매의 어미 3연속, 그리고 자기 채점 실패

이월 목록에는 없던, 이번 검수 자체에서 발견한 것을 따로 적는다.

**장-장 이음매 어미 3연속 일곱 곳.** 브리프가 요구한 대로 열일곱 개 이음매(앞 장의 마지막
문장 → 다음 장의 첫 문장, 코드 블록·표 셀 제외)를 전수 조사해, 7곳에서 `-니다` 계열 어미가
3연속 걸리는 것을 확인했다 — 1장→2장, 5장→6장, 7장→8장, 9장→10장, 11장→12장, 12장→13장,
14장→15장. 각 장은 개별 리뷰를 통과했지만 장 사이의 이음매는 그때까지 검사 대상이 아니었다
(각 장 태스크가 "자기 장 안"만 셌다). **전부 고쳤다** — 대부분 진입하는 장의 첫 문장을,
두 곳(5장→6장, 12장→13장)은 앞 장 퀴즈 해설의 마지막 문장을 체언 종결로 바꿔 사슬을 끊었다
(뒤 문장이 앞 장의 표·문구를 그대로 인용한 곳이라 손대지 않았다). 열일곱 개 전수 표와 수정
전/후 대조는 `task-20-report.md` §4에 있다.

**이 발견 자체가 한 차례 불완전했다.** 1차 검수에서 열일곱 개를 "전부 세었다"고 보고했는데
실제로는 1장→2장 이음매(3연속)를 놓쳤다 — 컨트롤러 리뷰가 잡아 재검수로 찾아 고쳤다. 이
프로젝트에서 자기 채점("전부 확인했다"는 보고)이 실제와 어긋난 것이 **일곱 번째**이고
(Ruling L·Task 15·Task 18이 앞선 사례들을 기록해 두었다), 이번엔 그것이 **최종 게이트에서**
났다. 다음 문서를 만드는 사람을 위한 패턴: **"전부 세었다"류의 완결형 주장은 실제로 표를
만들어 하나씩 지워 가며 검증했을 때만 쓸 것** — 눈으로 훑고 "다 됐다"고 쓰는 방식은 최종
검수 단계에서도 똑같이 틀린다.

## 3. 회수 구조 — spec §6 표 대조

여덟 행 중 일곱은 심은 곳과 거두는 곳이 본문에 실제로 있는 것을 확인했다. 한 행은 명시적
연결을 찾지 못했다.

- **미확인: "2장 계정은 격리 단위 | 10장 책임 분계선 → IAM 문서".** 2장은 "계정은 격리
  단위이자 청구 단위"를 분명히 세운다(`:721,726,735`). 그런데 10장(관리형/책임 분계선) 본문
  어디에도 "계정"이나 "격리"라는 단어가 나오지 않는다 — 10장은 RDS의 책임 분계선(온프렘·
  EC2·RDS 세 갈래, 열한 줄)이라는 전혀 다른 종류의 경계를 다룬다. **판정: 포기하고 기록한다.**
  두 경계(계정의 격리 vs. 관리형 서비스의 책임 분계선)를 억지로 연결하는 문장을 10장에
  끼워 넣으면, 이미 Critical·Important 0건으로 승인된 10장의 서사(장면→표→이름)에 어색한
  삽입이 될 위험이 크다고 판단했다. spec §6 표 자체가 다소 느슨하게 짝지은 행일 가능성도
  있다.
- 나머지 일곱 행은 전부 확인됨: Hero 아홉 개 목록↔1장·15장 / 3장 AZ 갇힘↔7장·9장 / 3장
  글로벌인 것들↔8장 / 5장 IP 변경↔7장 EIP↔12장 요금 / 6장 볼륨 생존↔12장 정체불명 EBS / 4장
  ARN↔13장·IAM 문서 / 1장 따로 과금↔12장 청구서.

## 4. 브라우저 실측을 하지 못했다

`mcp__chrome-devtools__new_page`/`list_pages` 호출이 전부
`"The browser is already running for .../chrome-profile. Use --isolated to run multiple

### 11-1. `bill-top3` 체크리스트가 부록 A로 보내 놓고 답을 안 줌

15장 체크리스트(`:1445-1448`) 여덟째 항목 "청구서에서 가장 비싼 세 줄, 바로 짚을 수 있다"가

문장도 없었다 — `console-only` 항목이 이미 겪은 것과 같은 결함(§18장 리뷰에서 한 번 잡혔던
패턴의 재발, 이번엔 다른 체크리스트 항목에서). **판정: 새 명령을 만들지 않고, `console-only`
때와 같은 방식으로 부록 A 마지막에 한 문장을 추가했다** — 근거 없는 명령을 지어내는 것보다
사정을 밝히는 편이 이 문서의 규범에 맞기 때문이다.

추가한 문장(`aws_basics.html:1523`):
> 청구서에서 가장 비싼 세 줄에 따로 명령을 걸지 않은 것은 방금 위의 볼륨·탄력적 IP·NAT
> 게이트웨이, 이 세 명령이 그 세 줄을 이미 나눠 맡고 있기 때문이고, 실제 금액을 확인할
> 곳은 12장이 이미 답한 대로 콘솔의 Cost Explorer.

`bill-top3`가 볼륨(`orphan-ebs`)·탄력적 IP(`pub-ip`)·NAT 게이트웨이(`nat-count`) 세 명령으로
이미 커버된다는 판정은 최종 리뷰 보고서 §49에만 있었고 독자에게는 안 보였다 — 이제 본문에
그 이유(왜 별도 블록이 없는지)와 담당 명령 셋, 정확한 숫자를 보는 곳(12장 `:1241`의 "콘솔의
Cost Explorer")을 한 문장에 담았다.

**끝맺음을 `-니다`가 아니라 체언 종결("…Cost Explorer.")로 고른 것은 스타일 선택이 아니라
사슬 문제였다.** 처음 초안은 "…확인합니다."로 끝났는데, 부록 A→부록 B 이음매(`task-20-report.md`

### 11-2. GLOSSARY "태그"·14장의 근거 없는 주장 둘

`:1628`(GLOSSARY "태그" — "리소스 하나에 최대 50개")과 `:1354`(14장 — "태그만으로는 안 되고

바로 그 게이트 위반이다 — "구현자가 WebFetch를 했는가"가 아니라 "근거 파일에 있는가"
(facts `:541-542`, `:589-591`).

**처리:**
1. 소스 주석이 지목한 페이지 [Tag your Amazon EC2 resources](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Using_Tags.html)를 WebFetch로 열어 원문을 직접 대조했다.
2. 인용 전문을 `docs/superpowers/notes/2026-08-15-aws-basics-facts.md`에 **V30**으로 등재했다(요약 표 행 포함).
3. `:1628`의 "리소스 하나에"를 "**EC2 리소스** 하나에"로 좁혔다 — 근거 페이지 제목 자체가
   "Tag **your Amazon EC2 resources**"이고, S3 태그 제한 페이지는 이번에 WebFetch로 열어
   보려 했으나 실제 본문을 받아 오지 못해 다른 서비스까지 같은 한도인지 확인할 수 없었다.
   **"EC2 리소스"로 좁히는 쪽을 택했다** — 확인 안 된 것을 넓혀 쓰지 않는다는 이 프로젝트의
   기존 규칙(V27)과 같은 판단.
4. `:1354`는 문장을 고치지 않았다 — 13장 `tag:Owner` 필터가 EC2 인스턴스를 대상으로 쓰인
   자리를 그대로 이어받는 문맥이라 이미 EC2로 좁혀져 있고, 근거만 V30으로 이었다.

**V30 인용 전문과 출처** — [Tag your Amazon EC2 resources](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Using_Tags.html), "Tag restrictions" 절:
> Maximum number of tags per resource – 50
>

>
> You can't terminate, stop, or delete a resource based solely on its tags; you must specify the

### 11-3. `:423`의 CSS가 실측 없이 데스크톱 렌더링을 바꿈 — **최종 검수의 수정이 만든 새 위험을, 이번 최종 리뷰가 잡음**

**이것은 이 문서 §1-4·§10이 이미 "고쳤다"고 적어 둔 바로 그 수정의 후속이다.** Task 20이
6장 `.myth` 안 `table.t`의 모바일 잘림을 막으려고 `.myth .m-txt table.t{display:block;
overflow-x:auto}`를 넣었는데(§1-4의 원래 서술, 지금은 정정됨), 의도는 좁은 뷰포트 방어였지만
부작용은 **모든 뷰포트**에 걸렸다. `table.t`가 `:315`에서 `width:100%`인데 `display:block`을
주면 그 `width:100%`가 블록 박스에만 걸리고 내부의 익명 테이블 박스는 shrink-to-fit이 된다.
6장 표(`:914-923`)는 "루트 / 시작할 때 / 콘솔·CLI / 삭제"처럼 셀이 짧아서, **데스크톱에서 이
표만 콘텐츠 너비로 줄어 왼쪽에 붙는다** — 문서의 다른 아홉 개 `table.t`와 폭이 달라진다. 이
CSS는 6장 리뷰가 끝난 뒤에 들어가서 **그 표를 본 리뷰어가 아무도 없었다.**

**고친 방식 — 표를 건드리지 않고 감쌌다.**
```css
/* 이전 (문제) */
.myth .m-txt table.t{display:block; overflow-x:auto}

/* 이후 (최종) */
.myth .m-row .m-txt{font-size:14.5px; color:var(--text-dim); min-width:0; overflow-x:auto}
```
`table.t`에 거는 규칙을 완전히 없애고, `overflow-x:auto`를 `.myth .m-row .m-txt`(이미
`min-width:0`이 있던 그 선택자)에 옮겨 달았다. `min-width:0`은 그대로 뒀다 — flex 아이템의
기본 최소폭 제약을 없애는 표준 패턴이고 부작용이 없다.

**`.myth` 여섯 곳 확인 결과.** 문서 전체 `<div class="myth">`는 여섯 곳(`:757` 3장,
`:911` 6장, `:1018` 8장, `:1093` 9장, `:1231` 12장, `:1349` 14장) — 이 중 `table.t`를 품은
것은 6장(`:911-925`) 하나뿐이고 나머지 다섯은 표가 없는 순수 텍스트 `.m-txt`다. 다섯 곳
전부 마크업을 직접 확인해 표가 없는 것을 검증했다. `overflow-x:auto`는 콘텐츠가 실제로
넘칠 때만 스크롤바를 만드므로, 표가 없는 다섯 곳은 이 규칙이 있으나 없으나 렌더링에
차이가 없다.

**`overflow:hidden`(`.myth`, `:415`)과의 충돌 여부.** 충돌하지 않는다고 판단했다 —
`overflow-x:auto`는 `.m-txt`(`.myth`의 손자뻘 요소, `.m-row`의 자식) 자신을 새 스크롤
컨테이너로 만들 뿐이고, 그 스크롤 박스는 `.m-txt`의 자기 박스 안에 머문다. `.myth`의
`overflow:hidden`은 자신의 경계(둥근 모서리 클리핑용)에서만 작동하고 자손의 로컬 스크롤을
막지 않는다. **`.myth`의 `overflow` 규칙 자체는 건드리지 않았다** — 골격의 기존 규칙이라
여섯 곳에 영향이 가고, 이번 수정 범위를 넘는다고 판단했다(지시받은 대로 멈추지 않고 진행한
이유는, 실제로 `overflow`를 고칠 필요가 없었기 때문이다 — `table.t` 쪽 규칙만 없애는 것으로
충분했다).

**브라우저 실측 — 못 했다.** `mcp__chrome-devtools__list_pages`와 `new_page`(격리 컨텍스트
포함)를 시도했으나 둘 다 `"The browser is already running for .../chrome-profile"` 오류를
반환했다 — §4가 이미 기록한 것과 같은 원인(다른 세션이 같은 크롬 프로필을 점유)이 이번
세션에도 그대로 재현됐다. 다른 세션의 브라우저를 강제 종료하지 않았다. **375px 등 실제
뷰포트에서 6장 표가 잘리지 않는지, 데스크톱에서 다른 표와 같은 폭으로 보이는지는 정적 CSS
분석으로만 확인했고 눈으로 보지 못했다.**

### 11-4. 곁가지 둘 — 범위 밖, 기록만

- **`pub-ip` 항목의 과소 계수.** 체크리스트 `pub-ip`(`:1429`)는 "퍼블릭 IPv4가 몇 개인지
  안다"인데, 대응 명령 `aws ec2 describe-addresses`(`:1500`)는 **탄력적 IP만** 센다. 12장이
  과금 축으로 세운 것은 "갖고 있는 퍼블릭 IPv4 개수"(탄력적 IP + 인스턴스에 자동 배정된
  퍼블릭 IPv4 포함)인데, `describe-addresses`는 그중 탄력적 IP만 잡고 자동 배정 퍼블릭
  IPv4(EIP를 붙이지 않은 running 인스턴스가 받는 주소)는 빠진다 — 12장의 축을 과소 계수한다.
- **`DeleteOnTermination` 명령에 대응 체크 항목 없음.** 부록 A `:1510`의 명령(인스턴스에 붙은
  볼륨의 `DeleteOnTermination` 확인)은 체크리스트 여덟 항목 중 어디에도 안 걸려 있다 — 6장
  본문·데모와는 연결되지만 15장 체크리스트에는 이 명령을 가리키는 행이 없다.

두 건 다 이번 fix wave의 지시 범위 밖이라 고치지 않았다.
