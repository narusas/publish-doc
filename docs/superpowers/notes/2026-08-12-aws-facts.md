# AWS 동작 사실 검증 — 2026-08-12

이 문서는 `aws_network_security.html` 서술의 근거다. 튜토리얼에서 단정문으로
쓰는 모든 AWS 동작은 여기에 근거가 있어야 한다.

## V1 — Flow Logs와 NACL/SG 차단의 기록 비대칭

**결론:** 기획서(`§5` 7장 서술)의 가정 — "NACL이 인바운드를 막으면 ENI에 닿지도 않아
아무 줄도 남지 않는다" — 는 **틀렸다.** AWS 공식 문서는 `REJECT` 액션이 보안 그룹과
네트워크 ACL 중 어느 쪽이 막았든 동일하게 기록된다고 명시한다. "로그가 없다"가 단서가
되는 구조가 아니다.

검증한 네 가지 판정:

1. **인바운드가 NACL에 막혔을 때** → `REJECT` 레코드가 남는다 (무기록이 아니다). `action`
   필드의 공식 정의가 SG/NACL을 구분하지 않고 둘 다 `REJECT`의 원인으로 명시하므로 확정.
2. **인바운드가 SG에 막혔을 때** → `REJECT` 레코드 1건. 공식 예제로 직접 확정: "the flow log
   displays a single REJECT record, because the traffic was not permitted to reach your
   instance."
3. **아웃바운드가 NACL에 막혔을 때** → `ACCEPT`로 남지 않는다. `REJECT`로 정확히 기록된다
   (기획서가 우려한 "ACCEPT로 잘못 남을 수 있다"는 케이스는 이 방향에서는 발생하지 않는다).
   공식 ICMP 예제로 확정.
4. **아웃바운드가 SG에 막혔을 때**(신규 아웃바운드 연결 기준) → `REJECT`로 기록될 것으로
   추정된다. `action` 필드의 일반 정의에서 유추한 것으로, 이 방향을 전용으로 다루는 별도
   예제는 문서에 없다. **부분 확정.**

**진짜 비대칭은 "기록 여부"가 아니라 "레코드가 짝을 이루는가"다.** 이것이 이번 검증에서
가장 중요하게 뒤집힌 지점이다.

- SG가 인바운드를 막으면: 패킷이 인스턴스에 닿지 않으므로 응답 자체가 없다 → 단독 `REJECT`
  1건.
- NACL이 인바운드를 막아도: 마찬가지로 패킷이 인스턴스에 닿지 않으므로 응답이 없다 →
  단독 `REJECT` 1건. **즉 단독 REJECT 1건만 봐서는 Flow Log만으로 SG와 NACL을 구분할 수
  없다.**
- NACL이 **응답(아웃바운드 레그)**을 막으면: 요청은 인스턴스까지 도달했으므로 `ACCEPT`가
  먼저 남고, 그 응답이 막히면서 `REJECT`가 뒤따른다 → `ACCEPT` + `REJECT` 두 줄이 짝을
  이룬다. SG는 상태 저장이므로 허용된 인바운드의 응답을 아웃바운드 규칙과 무관하게 무조건
  통과시킨다 — 이 조합(`ACCEPT` 뒤에 오는 `REJECT`)을 SG는 원리상 만들어낼 수 없다.

따라서 **"REJECT 앞에 ACCEPT가 붙어 있는가"**가 SG와 NACL을 가르는 진짜 신호이지,
"REJECT가 있는가 없는가"가 아니다.

**근거:**
- Flow log record examples — https://docs.aws.amazon.com/vpc/latest/userguide/flow-logs-records-examples.html
  - 인용(보안 그룹과 NACL의 상태 저장 차이): "Security groups are stateful — this means
    that responses to allowed traffic are also allowed, even if the rules in your security
    group do not permit it. Conversely, network ACLs are stateless, therefore responses to
    allowed traffic are subject to network ACL rules."
  - 인용(핵심 실험 시나리오, ping 예제): "Your security group's inbound rules allow ICMP
    traffic but the outbound rules do not allow ICMP traffic. Because security groups are
    stateful, the response ping from your instance is allowed. Your network ACL permits
    inbound ICMP traffic but does not permit outbound ICMP traffic. Because network ACLs
    are stateless, the response ping is dropped and does not reach your home computer. In a
    default flow log, this is displayed as two flow log records: An ACCEPT record for the
    originating ping that was allowed by both the network ACL and the security group, and
    therefore was allowed to reach your instance. A REJECT record for the response ping
    that the network ACL denied."
  - 인용(SG 단독 REJECT): "If your security group denies inbound ICMP traffic, the flow log
    displays a single REJECT record, because the traffic was not permitted to reach your
    instance."
- Flow log records (action 필드 정의) — https://docs.aws.amazon.com/vpc/latest/userguide/flow-log-records.html
  - 인용: "REJECT — The traffic was rejected. For example, the traffic was not allowed by
    the security groups or network ACLs, or packets arrived after the connection was
    closed."

**튜토리얼 서술에 미치는 영향:** 7장 "로그의 비대칭" 문단을 다시 쓴다. "NACL이 막으면
로그가 안 남는다"는 문장을 삭제하고, "SG든 NACL이든 인바운드를 막으면 똑같이 REJECT 1건만
남아 Flow Log만으로는 범인을 못 가른다. 진짜 단서는 REJECT 앞에 ACCEPT가 붙어 있는지다 —
그 조합이 보이면 100% NACL이 응답을 막은 것이다. SG는 상태 저장이라 이 조합을 절대 만들 수
없기 때문이다"로 대체한다. 이 재구성은 §8 표와 §5 7장 본문에 이미 반영했다(아래 참고).
**확정도: 부분 확정** — 핵심 주장(1~3번, 짝짓기 논리)은 공식 문서로 확정. 4번(신규
아웃바운드가 SG에 막힐 때)은 일반 정의에서 유추한 것으로 전용 예제가 없어 부분 확정이다.
7장 서술에서는 4번을 단정하지 않는다.

## V2 — VPC Peering 너머의 SG 참조

**결론:** 같은 리전(intra-Region) peering에서만 SG 참조가 가능하다. 리전 간(inter-region)
peering에서는 불가하며, 이 경우 CIDR 블록을 써야 한다. 계정 간 참조는 같은 리전이라는
조건 하에 가능하고, 이때는 소스 필드에 `계정ID/sg-xxxx` 형식을 쓴다. "Allow DNS
resolution" 설정은 SG 참조 기능 자체의 전제조건으로 문서에 등장하지 않는다 — 이는 프라이빗
DNS 호스트네임 해석을 위한 별개의 peering 옵션이며, SG 참조 요건 목록에는 없다(기획서
초안의 추정은 부정확했다).

Transit Gateway를 통한 연결에서도 SG 참조가 지원된다(2024년 9월 GA). 다만 다음 제약이
있다: (a) 같은 리전 내에서만 — 두 VPC가 같은 트랜짓 게이트웨이에 붙어 있고 같은 리전에
있어야 한다, (b) **인바운드 규칙에서만** 참조 가능하고 아웃바운드 규칙에서는 지원되지
않는다, (c) 트랜짓 게이트웨이 자체와 각 VPC 어태치먼트 양쪽에서 "Security group
referencing support"를 명시적으로 활성화해야 동작한다.

**근거:**
- Update your security groups to reference peer security groups —
  https://docs.aws.amazon.com/vpc/latest/peering/vpc-peering-security-groups.html
  - 인용: "You can't reference the security group of a peer VPC that's in a different
    Region. Instead, use the CIDR block of the peer VPC."
  - 인용: "The peer VPC can be a VPC in your account, or a VPC in another AWS account. To
    reference a security group that is in another AWS account but the same Region, include
    the account number with the ID of the security group. For example,
    123456789012/sg-1a2b3c4d."
  - 이 페이지 전체에 "Allow DNS resolution" 관련 요구사항은 등장하지 않는다(직접 확인).
- Reference security groups across a transit gateway —
  https://docs.aws.amazon.com/vpc/latest/tgw/tgw-sg-updates.html — **이 페이지는 WebFetch로
  4회 시도했으나 본문이 렌더링되지 않아(제목 "Amazon VPC"만 반환) 직접 인용에 실패했다.**
  아래 두 개의 AWS 공식 보조 출처로 내용을 보강했다.
- (보조) AWS 공식 GA 발표 —
  https://aws.amazon.com/about-aws/whats-new/2024/09/general-availability-security-group-referencing-aws-transit-gateway/
  - 인용: "AWS announces the general availability for Security Group Referencing across VPCs
    connected by the AWS Transit Gateway. With this capability, customers can simplify
    management of Security Groups and gain a better security posture for their TGW based
    networks."
  - 인용: "Security Group Referencing on TGW is available in all AWS Regions where Transit
    Gateway is available"
- (보조) AWS 공식 네트워킹 블로그 —
  https://aws.amazon.com/blogs/networking-and-content-delivery/introducing-security-group-referencing-for-aws-transit-gateway/
  - 인용: "Outbound security rules referencing over Transit Gateway aren't supported at this
    time."
  - 인용: "To connect two VPCs, both VPCs must be attached to the same transit gateway and
    reside in the same Region."
  - 인용: "security group referencing support must be enabled on both the transit gateway
    and the Transit Gateway VPC attachment."

**튜토리얼 서술에 미치는 영향:** 12장에 "SG 참조는 같은 리전 peering에서만 동작하고,
리전 간에는 CIDR로 되돌아가야 한다"를 단정문으로 쓴다(확정). TGW 경유 SG 참조는 언급하되
"인바운드 전용, 활성화 필요, 같은 리전 한정"이라는 제약과 함께 완곡한 어투("~로 알려져
있다" 수준)로 쓴다 — `docs.aws.amazon.com` 원문을 직접 인용하지 못했기 때문이다.
**확정도: peering 부분은 확정, TGW 부분은 부분 확정.**

## V3 — CloudFront origin-facing managed prefix list

**결론:** 정확한 이름은 IPv4가 `com.amazonaws.global.cloudfront.origin-facing`, IPv6가
`com.amazonaws.global.ipv6.cloudfront.origin-facing`이다. 리전은 `global` — 특정 리전에
종속되지 않고 전역으로 하나만 존재한다(CloudFront가 글로벌 서비스이므로). ALB(오리진) SG에
적용하는 방법은 인바운드 규칙의 Source를 CIDR 대신 이 prefix list의 ID로 지정하는 것이다.
슬롯 가중치(weight)는 **55**다 — SG 규칙 기본 한도 60개 중 이 한 줄이 55개를 차지하여
나머지 규칙에 쓸 수 있는 여유는 5개뿐이다(한도 상향 요청 가능).

**근거:**
- Locations and IP address ranges of CloudFront edge servers —
  https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/LocationsOfEdgeServers.html
  - 인용: "If your origin is hosted on AWS and protected by an Amazon VPC security group,
    you can use the CloudFront managed prefix list to allow inbound traffic to your origin
    only from CloudFront's origin-facing servers, preventing any non-CloudFront traffic
    from reaching your origin."
  - 인용: "The CloudFront managed prefix lists are as follows: `com.amazonaws.global.
    cloudfront.origin-facing` (IPv4) / `com.amazonaws.global.ipv6.cloudfront.origin-facing`
    (IPv6)"
- AWS-managed prefix lists —
  https://docs.aws.amazon.com/vpc/latest/userguide/working-with-aws-managed-prefix-lists.html
  - 인용(표): "Amazon CloudFront — Prefix list name: com.amazonaws.global.cloudfront.
    origin-facing (IPv4) / com.amazonaws.global.ipv6.cloudfront.origin-facing (IPv6) —
    Weight: 55"
  - 인용: "For example, the weight of a Amazon CloudFront managed prefix list is 55. Here's
    how the this affects your Amazon VPC quotas: Security groups – The default quota is 60
    rules, leaving room for only 5 additional rules in a security group."

**튜토리얼 서술에 미치는 영향:** 10장에서 정확한 이름과 weight=55를 그대로 인용하고,
"SG 규칙 60개 한도 중 55개를 이 prefix list 하나가 먹는다 → 실무에서 규칙 폭발·한도 문제의
실제 원인"이라는 프레이밍을 강화한다. **확정도: 확정.**

## V4 — Network Firewall 삽입 라우팅 구성 (단일 AZ, IGW)

**결론:** 단일 AZ·인터넷 게이트웨이 구성에서 정답 순서는 다음과 같다.

1. **방화벽 전용 서브넷이 필요하다** — 워크로드(고객) 서브넷과 별도로 만든다. Network
   Firewall 엔드포인트가 이 서브넷에 생성된다.
2. **IGW의 edge-association 라우팅 테이블**에는 워크로드 서브넷 CIDR(예: `10.0.2.0/24`) →
   타깃: 방화벽 엔드포인트(`vpce-4114` 형식)로 가는 라우트를 새로 추가한다. 방화벽 도입
   전에는 이 라우팅 테이블에 이런 항목이 없었다(암묵적 local뿐).
3. **워크로드 서브넷 라우팅 테이블의 `0.0.0.0/0` 타깃**을 기존 IGW(`igw-1232`)에서 방화벽
   엔드포인트(`vpce-4114`)로 교체한다.
4. (부가) 방화벽 서브넷 자체의 라우팅 테이블도 새로 만든다: VPC 내부(`10.0.0.0/16`)는
   local, `0.0.0.0/0`은 IGW로 나간다.

VPC 엔드포인트 ID 형식은 `vpce-` 접두어를 쓴다(Network Firewall 엔드포인트는 Gateway Load
Balancer 엔드포인트 기반이라 `vpce-`로 표시되는 VPC 엔드포인트로 취급된다).

**근거:**
- Simple single zone architecture with an internet gateway using AWS Network Firewall —
  https://docs.aws.amazon.com/network-firewall/latest/developerguide/arch-single-zone-igw.html
  - 인용(IGW 라우팅 테이블): "Internet gateway route table – Routes traffic that's destined
    for the customer subnet (range 10.0.2.0/24) to the firewall subnet (named vpce-4114 in
    the figure)."
  - 인용(워크로드 서브넷 라우팅 테이블): "Customer subnet route table – Routes traffic
    that's destined for anywhere inside the VPC (10.0.0.0/16) to the local address. Routes
    traffic that's destined for anywhere else (0.0.0.0/0) to the firewall subnet
    (vpce-4114). ... Before the firewall inclusion, the customer subnet route table routed
    the 0.0.0.0/0 traffic to igw-1232."
  - 인용(방화벽 서브넷 라우팅 테이블): "Firewall subnet route table – Routes traffic that's
    destined for anywhere inside the VPC (10.0.0.0/16) to the local address. Routes traffic
    that's destined for anywhere else (0.0.0.0/0) to the internet gateway (igw-1232)."

**튜토리얼 서술에 미치는 영향:** 9장 데모의 정답 상태를 정확히 3단계 순서(방화벽 서브넷
신설 → IGW edge 라우팅 테이블에 워크로드 CIDR→vpce- 라우트 추가 → 워크로드 서브넷의
0.0.0.0/0을 IGW에서 vpce-로 교체)로 제시한다. **확정도: 확정.**

## V5 — Gateway Endpoint 지원 서비스 범위

**결론:** Gateway형 엔드포인트가 지원하는 서비스는 지금(2026-08-13 기준 공식 문서)도
**Amazon S3와 DynamoDB 두 가지뿐**이다 — 추가된 서비스는 없다. Interface형은 훨씬 많은
AWS 서비스를 지원하며 과금 방식이 다르다: Gateway 엔드포인트는 추가 요금이 없고, Interface
엔드포인트는 AZ당 시간당 요금 + 처리한 GB당 데이터 처리 요금이 부과된다. 라우팅 방식도
다르다 — Gateway는 라우팅 테이블에 prefix list 기반 경로로 나타나고(ENI 없음), Interface는
서브넷에 ENI가 생겨 SG가 붙는다(4장에서 심은 "ENI에 SG가 붙는다"가 여기서 회수된다).

**근거:**
- Gateway endpoints — https://docs.aws.amazon.com/vpc/latest/privatelink/gateway-endpoints.html
  - 인용: "Gateway VPC endpoints provide reliable connectivity to Amazon S3 and DynamoDB
    without requiring an internet gateway or a NAT device for your VPC. Gateway endpoints
    do not use AWS PrivateLink, unlike other types of VPC endpoints."
  - 인용(과금): "Pricing — There is no additional charge for using gateway endpoints."
  - 인용(라우팅): "The following route is automatically added to each route table that you
    select. The destination is a prefix list for the service owned by AWS and the target is
    the gateway endpoint."
- AWS PrivateLink concepts —
  https://docs.aws.amazon.com/vpc/latest/privatelink/vpc-endpoints.html
  - 인용: "There is another type of VPC endpoint, `Gateway`, which creates a *gateway
    endpoint* to send traffic to Amazon S3 or DynamoDB."
- (보조) AWS PrivateLink Pricing — https://aws.amazon.com/privatelink/pricing/
  - 인용: "You will be billed for each hour that your VPC endpoint remains provisioned in
    each Availability Zone" / "Data processing charges apply for each Gigabyte processed
    through the VPC endpoint regardless of the traffic's source or destination."

**튜토리얼 서술에 미치는 영향:** 11장에서 "Gateway형은 S3·DynamoDB 단 둘뿐"이라고 단정해도
된다. Interface형과의 과금 차이(무료 vs 시간당+GB당)를 한 줄로 대비시킨다. **확정도: 확정.**

## V6 — 리소스별 Security Group 부착

### V6-1 EC2 인스턴스

**결론:** 보안 그룹은 기술적으로 "인스턴스"가 아니라 "ENI(elastic network interface)"의 속성이다.
다만 EC2 콘솔·문서의 관용적 표현은 "인스턴스에 보안 그룹을 연결한다"고 말한다 — 대부분의
인스턴스가 ENI를 하나(기본 네트워크 인터페이스)만 갖기 때문에 "인스턴스의 보안 그룹"과 "기본
ENI의 보안 그룹"이 사실상 같은 것을 가리키기 때문이다. 인스턴스에 보조 ENI를 여러 개 붙이면
각 ENI마다 서로 다른 보안 그룹 집합을 지정할 수 있다. 인스턴스당 ENI 개수는 인스턴스 유형별로
다르며 기본 ENI도 그 한도에 포함된다(예: c5.large는 기본 3개, 그중 1개가 기본 ENI).

  - 인용: "You can associate each instance with multiple security groups, and you can associate each
    security group with multiple instances... When Amazon EC2 decides whether to allow traffic to
    reach an instance, it evaluates all rules from all security groups that are associated with the

  https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/scenarios-enis.html
  - 인용: "you can create and attach secondary network interfaces to instances... and configure the

**튜토리얼 서술에 미치는 영향:** 1장 도입부에서 "SG는 인스턴스가 아니라 ENI에 붙는다"를 핵심
개념으로 제시하되, "인스턴스 대부분은 ENI가 하나뿐이라 실무에서는 '인스턴스에 붙인다'고 말해도
틀리지 않는다 — 예외는 다중 ENI 인스턴스(NAT/방화벽 어플라이언스, 듀얼호밍 등)"로 보강한다.
**확정도: 확정.**

### V6-2 Application Load Balancer (ALB)

**결론:** ALB는 지정한 각 서브넷(가용영역)에 자체 ENI를 만든다. 이 ENI들은 콘솔에서 "ENI
reserved by ELB for subnet"이라는 설명으로 보이며, 서브넷의 여유 IP가 부족해도 유지보수 작업을
완료할 수 있도록 예비로 확보해 둔 것이다. 보안 그룹은 ALB 자체(로드밸런서)에 붙고, "리스너
포트와 헬스체크 포트 양방향 트래픽을 허용"해야 한다는 요건이 있다. 타깃(EC2 인스턴스) 쪽 보안
그룹은 별도로 관리하며, 공식 권장 방식은 타깃의 인바운드 규칙 Source를 "로드밸런서의 보안
그룹"으로 지정하는 것이다 — 이렇게 하면 로드밸런서를 거치지 않은 직접 트래픽은 차단된다.

**근거:**
- Application Load Balancers (서브넷 섹션) —
  https://docs.aws.amazon.com/elasticloadbalancing/latest/application/application-load-balancers.html
  - 인용: "Elastic Load Balancing creates network interfaces in the subnets where you configured
    your load balancer. These network interfaces are reserved so that the load balancer can
    complete maintenance actions even when the subnet is running low on available IP addresses.
    They have the description \"ENI reserved by ELB for subnet\"."
  - 인용(로드밸런서 SG): "A security group acts as a firewall that controls the traffic allowed to
    and from your load balancer... The rules for the security groups that are associated with your
    load balancer must allow traffic in both directions on both the listener and the health check
    ports."
- Register targets with your Application Load Balancer target group (Target security groups) —
  https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-register-targets.html
  - 인용: "When you register EC2 instances as targets, you must ensure that the security groups for
    your instances allow the load balancer to communicate with your instances on both the listener
    port and the health check port." 표의 권장 Source는 "{{load balancer security group}}"이다.
- (같은 ELBv2 계열 NLB 문서에서 "서브넷당 ENI 1개"가 명시적으로 확인됨 — ALB 문서 자체에는 이
  정확한 개수 문구가 없어 교차 인용) Register targets for your Network Load Balancer —
  https://docs.aws.amazon.com/elasticloadbalancing/latest/network/target-group-register-targets.html

**튜토리얼 서술에 미치는 영향:** "ALB도 결국 ENI를 갖는 리소스"라는 그림을 그릴 때 "서브넷마다
ENI가 생긴다"까지는 확정, "서브넷당 정확히 1개"는 NLB 문서에서만 명시적으로 확인되어 ALB에는
완곡하게("~로 보인다") 적는다. 타깃 SG의 Source에 "로드밸런서 SG"를 넣는 패턴은 확정문으로
써도 된다. **확정도: ALB의 ENI 존재·타깃 SG 참조 패턴은 확정, "서브넷당 정확히 1개"는 부분
확정(NLB 문서 교차 인용).**

### V6-3 Network Load Balancer (NLB) — critical

**결론:** NLB는 현재 보안 그룹을 지원한다(과거에는 지원하지 않았다). AWS 공식 What's New
발표에 따르면 이 기능은 **2023년 8월 10일**부터 제공되었다. 핵심 제약(비가역성)은 문서에
명확히 있다: **"로드밸런서를 생성할 때 보안 그룹을 하나도 지정하지 않으면, 이후에는 절대로
보안 그룹을 붙일 수 없다."** 반대로 생성 시 보안 그룹을 하나라도 지정했다면 이후 자유롭게
추가·변경·제거할 수 있다. 즉 "나중에 필요하면 그때 붙이자"는 전략이 통하지 않는, 생성
시점에만 열려 있는 창(one-shot window)이다.

타깃 쪽 보안 그룹과의 상호작용: NLB에 보안 그룹이 붙어 있으면, 타깃의 보안 그룹 인바운드
규칙 Source에 "NLB의 보안 그룹"을 참조로 넣을 수 있다 — 이는 **클라이언트 IP 보존(client IP
preservation)을 켜도** 그대로 동작한다. 반대로 NLB에 보안 그룹이 없다면, 타깃 SG는 클라이언트
IP 보존 여부에 따라 "승인된 클라이언트의 실제 IP"(보존 켬) 또는 "NLB 노드의 프라이빗
IP"(보존 끔)를 직접 Source로 허용해야 한다.

**근거:**
- Update the security groups for your Network Load Balancer —
  https://docs.aws.amazon.com/elasticloadbalancing/latest/network/load-balancer-security-groups.html
  - 인용(비가역성, 핵심): "You can associate security groups with a Network Load Balancer when you
    create it. If you create a Network Load Balancer without associating any security groups, you
    can't associate them with the Network Load Balancer later on. We recommend that you associate a
    security group with your Network Load Balancer when you create it."
  - 인용(생성 시 지정했다면 이후 변경 가능): "After you create a Network Load Balancer with
    associated security groups, you can change the security groups associated with the Network Load
    Balancer at any time."
  - 인용(클라이언트 IP 보존과의 상호작용): "Referencing the security group associated with your
    Network Load Balancer in the security groups associated with your targets ensures that your
    targets accept traffic from your Network Load Balancer even if you enable client IP preservation
    for your Network Load Balancer."
  - 인용(SG 미지정 시 기본 동작): "If you don't assign a security group to your Network Load
    Balancer, all client traffic can reach the Network Load Balancer listeners and all traffic can
    leave the Network Load Balancer."
- Register targets for your Network Load Balancer (Target security groups) —
  https://docs.aws.amazon.com/elasticloadbalancing/latest/network/target-group-register-targets.html
  - 인용(NLB에 SG가 없을 때 타깃 SG 권장 규칙): "Recommendations for target security groups if the

**튜토리얼 서술에 미치는 영향:** "NLB는 SG를 못 붙인다"는 과거 지식은 완전히 폐기하고, "지금은
지원하지만 생성 시점에 최소 1개를 지정하지 않으면 영원히 못 붙인다"는 비가역성을 핵심 함정으로
단정문으로 쓴다. 클라이언트 IP 보존과 SG 참조가 함께 동작한다는 점도 명시한다. **확정도: 확정.**

### V6-4 RDS DB 인스턴스

**결론:** RDS가 VPC 안에 DB 인스턴스를 만들 때, DB 서브넷 그룹에서 서브넷과 IP 주소를 고르고
그 IP로 **ENI를 생성해 DB 인스턴스에 연결한다** — EC2 인스턴스와 동일한 메커니즘이다. VPC 보안
그룹은 이 DB 인스턴스(=ENI)에 부착되며, 인바운드 규칙의 Source로 IP 대역뿐 아니라 다른 보안
그룹(예: 애플리케이션 서버의 SG)을 지정할 수 있다 — EC2↔RDS 연결의 표준 패턴은 "RDS SG의
인바운드 Source에 EC2 SG를 참조"하는 것이다.

**근거:**

  https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_VPC.WorkingWithRDSInstanceinaVPC.html
  - 인용: "When you create a DB instance in a VPC, you can choose a DB subnet group. Amazon RDS
    chooses a subnet and an IP address within that subnet to associate with your DB instance...
    Amazon RDS creates and associates an Elastic Network Interface to your DB instance with that IP
    address."
- Controlling access with security groups —
  https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Overview.RDSSecurityGroups.html
  - 인용: "VPC security groups control the access that traffic has in and out of a DB instance. By

  - 인용(EC2↔RDS 표준 패턴, 시나리오): "Create a second VPC security group (for example,
    sg-6789rdsexample) and create a new rule by specifying the VPC security group that you created

**튜토리얼 서술에 미치는 영향:** RDS를 "ENI가 없는 특수 리소스"로 오해하지 않도록, EC2와
동일하게 ENI 기반이라는 점을 명시한다. EC2→RDS 접근 데모에서 "RDS SG의 Source에 EC2 SG를
참조"하는 패턴을 정답으로 제시한다. **확정도: 확정.**

### V6-5 Lambda(VPC 연결) — 흔히 오해되는 지점

**결론:** Lambda를 VPC에 연결하면 "동시 실행(concurrent execution)마다 ENI 하나씩" 만들어지는
게 아니다. AWS는 **Hyperplane ENI**라는 공유 자원 모델을 명시적으로 문서화한다: 특정 "서브넷+
보안 그룹 조합"마다 Hyperplane ENI가 하나 생성되고, **같은 조합을 쓰는 계정 내 다른 함수들도
이 ENI를 공유**한다. 즉 ENI 개수를 결정하는 것은 동시성이 아니라 "서로 다른 서브넷·보안 그룹
조합의 개수"다. Hyperplane ENI 하나는 최대 65,000개 연결/포트를 지원하며, 이를 넘으면 Lambda가
자동으로 ENI를 추가 확장한다. 보안 그룹은 함수를 VPC에 붙일 때 지정한 서브넷·SG 조합 그대로
Hyperplane ENI에 적용된다.

**근거:**
- Giving Lambda functions access to resources in an Amazon VPC (Understanding Hyperplane Elastic
  Network Interfaces) — https://docs.aws.amazon.com/lambda/latest/dg/configuration-vpc.html
  - 인용: "The network interfaces that Lambda creates are known as Hyperplane Elastic Network
    Interfaces, or Hyperplane ENIs."
  - 인용(공유 모델, 핵심): "The first time you attach a function to a VPC using a particular subnet
    and security group combination, Lambda creates a Hyperplane ENI. Other functions in your
    account that use the same subnet and security group combination can also use this ENI. Wherever
    possible, Lambda reuses existing ENIs to optimize resource utilization and minimize the creation
    of new ENIs."
  - 인용(용량): "Each Hyperplane ENI supports up to 65,000 connections/ports. If the number of
    connections exceeds this limit, Lambda scales the number of ENIs automatically based on network
    traffic and concurrency requirements."
  - 인용(모범사례 절, 조합 개념 재확인): "Hyperplane ENIs are associated with a particular
    combination of security groups and VPC subnets. If you've already attached one function to a
    VPC, specifying the same subnets and security groups when you attach another function means
    that Lambda can share the network resources and avoid the need to create a new Hyperplane ENI."
  - 인용(수명주기 함정 — idle 회수): "if a Lambda function remains idle for 14 days, Lambda reclaims
    any unused Hyperplane ENIs and sets the function state to Inactive. The next invocation attempt
    will fail, and the function re-enters the Pending state until Lambda completes the creation or
    allocation of a Hyperplane ENI."
  - 인용(삭제 지연 함정): "When you update a function to remove its VPC configuration, Lambda
    requires up to 20 minutes to delete the attached Hyperplane ENI."

**튜토리얼 서술에 미치는 영향:** "Lambda 동시 실행 1000개 = ENI 1000개"라는 흔한 오해를 정면으로
반박하는 문단을 쓴다 — "ENI는 동시성이 아니라 서브넷+SG 조합 단위로 공유된다. 같은 SG·서브넷을
쓰는 함수를 늘려도 ENI가 늘지 않는다"를 단정문으로 쓴다. idle 14일 회수, 함수 Pending 상태(최초
생성 시 수 분 소요), VPC 설정 제거 시 최대 20분 지연 등은 실무 함정으로 별도 박스에 넣는다.
**확정도: 확정.**

### V6-6 Interface VPC Endpoint (PrivateLink)

**결론:** Interface 엔드포인트는 지정한 서브넷마다 "엔드포인트 네트워크 인터페이스"(ENI)를
만들고 서브넷 IP 대역에서 프라이빗 IP를 하나 할당한다. 이 ENI는 "requester-managed"(AWS가
관리하는 ENI)라 계정에서 조회는 되지만 직접 관리(수정)는 불가능하다. 보안 그룹은 이 엔드포인트
ENI에 붙으며, 엔드포인트 생성 시 지정하거나(기본은 VPC의 default SG) 이후 변경할 수 있다.

**근거:**
- Access an AWS service using an interface VPC endpoint —
  https://docs.aws.amazon.com/vpc/latest/privatelink/create-interface-endpoint.html
  - 인용: "For each subnet that you specify from your VPC, we create an endpoint network interface
    in the subnet and assign it a private IP address from the subnet address range. An endpoint
    network interface is a requester-managed network interface; you can view it in your AWS account,
    but you can't manage it yourself."
  - 인용(SG 필요성): "Create a security group for the endpoint network interface that allows the
    expected traffic from the resources in your VPC. For example, to ensure that the AWS CLI can
    send HTTPS requests to the AWS service, the security group must allow inbound HTTPS traffic."
  - 인용(생성 절차, 기본 SG): "For Security groups, select the security groups to associate with the
    endpoint network interfaces. By default, we associate the default security group for the VPC."
  - 인용(서브넷 제약): "You can select one subnet per Availability Zone. You can't select multiple
    subnets from the same Availability Zone."

**튜토리얼 서술에 미치는 영향:** V5에서 이미 "Interface형은 ENI가 생겨 SG가 붙는다"고 심어둔
복선을 여기서 회수한다 — "서브넷당 1개, AZ당 1개만 선택 가능, requester-managed라 콘솔에서
보이지만 못 건드린다"는 세부까지 단정문으로 보강한다. **확정도: 확정.**

### V6-7 Gateway VPC Endpoint (S3 / DynamoDB) — V5 교차 확인

**결론:** Gateway 엔드포인트는 ENI를 만들지 않는다 — 라우팅 테이블에 prefix list 기반
경로(target)로만 나타난다. 따라서 보안 그룹을 붙일 대상 자체가 없다. 대신 접근 통제는 (a)
라우팅 테이블에 어떤 서브넷을 연결할지, (b) 엔드포인트 정책(endpoint policy), (c) 필요하다면
S3 버킷 정책의 `aws:sourceVpce` 조건으로 이루어진다. 이 결론은 V5에서 이미 확정한 내용과
완전히 일치하며 모순이 없다 — 이번 검증에서도 동일한 두 문서를 다시 확인했다.

**근거 (V5와 동일 출처, 재확인):**
- Gateway endpoints — https://docs.aws.amazon.com/vpc/latest/privatelink/gateway-endpoints.html
  - 인용: "Gateway endpoints do not use AWS PrivateLink, unlike other types of VPC endpoints."
  - 인용(라우팅): "The following route is automatically added to each route table that you select.
    The destination is a prefix list for the service owned by AWS and the target is the gateway
    endpoint."
- AWS PrivateLink concepts — https://docs.aws.amazon.com/vpc/latest/privatelink/vpc-endpoints.html
  - 인용: "There is another type of VPC endpoint, Gateway, which creates a gateway endpoint to send
    traffic to Amazon S3 or DynamoDB."

**튜토리얼 서술에 미치는 영향:** 1장에서 "SG가 붙는 리소스" 목록을 만들 때 Gateway 엔드포인트는
"ENI가 없어서 SG 목록에서 아예 빠지는 예외 사례"로 명시적으로 대비시킨다(Interface 엔드포인트와
짝을 이루는 대조 예시). **확정도: 확정 — V5와 완전히 일치, 모순 없음.**

### V6-8 ECS on Fargate (awsvpc 네트워크 모드)

**결론:** awsvpc 모드에서 각 태스크는 자신만의 ENI를 하나 받는다("Each task can only have one
ENI"). 이 ENI는 ECS가 전적으로 관리하며 계정에서 직접 detach·수정할 수 없다(실행 중인 태스크의
ENI가 실수로 삭제되는 걸 막기 위함). 보안 그룹은 태스크 실행/서비스 생성 시
`networkConfiguration`의 `awsVpcConfiguration`에서 지정하며, 이 ENI에 그대로 적용된다. 서브넷은
최대 16개, 보안 그룹은 최대 5개까지 지정할 수 있다는 하드 리밋이 있다.

**근거:**
- Allocate a network interface for an Amazon ECS task —
  https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-networking-awsvpc.html
  - 인용: "The task elastic network interface (ENI) is a fully managed feature of Amazon ECS. Amazon
    ECS creates the ENI and attaches it to the host Amazon EC2 instance with the specified security
    group... Each task can only have one ENI."
  - 인용(관리 제약): "These ENIs are visible in the Amazon EC2 console for your account. Your
    account can't detach or modify the ENIs. This is to prevent accidental deletion of an ENI that
    is associated with a running task."
  - 인용(SG 적용 방식): "when you run a task or create a service, use the networkConfiguration
    parameter that includes one or more subnets to place your tasks in and one or more security
    groups to attach to an ENI... the specified security groups are associated with the ENI that's
    provisioned for the task."
  - 인용(하드 리밋): "There is a limit of 16 subnets and 5 security groups that are able to be
    specified in the awsVpcConfiguration when running a task or creating a service that uses the
    awsvpc network mode."
  - 인용(타깃 타입 함정): "tasks that use the awsvpc network mode are associated with an ENI, not
    with an Amazon EC2 Linux instance... you must choose ip as the target type. Do not use
    instance."

**튜토리얼 서술에 미치는 영향:** "Fargate 태스크 = EC2 인스턴스와 똑같이 SG가 ENI 단위로 붙는
독립 리소스"라는 그림을 확정문으로 쓴다. ALB/NLB 타깃 그룹에 Fargate 태스크를 등록할 때 타깃
타입을 반드시 `ip`로 해야 한다는 함정도 명시한다. **확정도: 확정.**

### V6-9 보안 그룹은 서브넷에 붙는가? ENI당 SG 개수 한도는?

**결론:** 보안 그룹은 **서브넷에 붙지 않는다** — ENI(및 그 ENI를 통해 리소스)에만 붙는다.
서브넷 단위로 붙는 것은 네트워크 ACL이다. 공식 비교표는 이를 "Level of operation: Security
group=Instance level / Network ACL=Subnet level"로 명시한다. ENI 하나에 붙일 수 있는 보안 그룹
개수의 기본 한도는 **5개**이며, 서비스 할당량 상향으로 **최대 16개**까지 늘릴 수 있다(단, "SG당
규칙 수 × ENI당 SG 수 ≤ 1,000"이라는 곱셈 상한이 함께 걸려 있다).

**근거:**
- Compare security groups and network ACLs (Infrastructure security in Amazon VPC) —
  https://docs.aws.amazon.com/vpc/latest/userguide/infrastructure-security.html
  - 인용(표): "Level of operation | Security group: Instance level | Network ACL: Subnet level" /
    "Scope | Security group: Applies to all instances associated with the security group | Network
    ACL: Applies to all instances in the associated subnets"
- Control traffic to your AWS resources using security groups —
  https://docs.aws.amazon.com/vpc/latest/userguide/vpc-security-groups.html
  - 인용: "You can assign a security group to resources created in the same VPC as the security
    group or to resources in other VPCs if using the Security Group VPC Association feature... You
    can also assign multiple security groups to a single resource."
  - 인용(한도 존재 고지): "There are quotas on the number of security groups that you can create per
    VPC, the number of rules that you can add to each security group, and the number of security
    groups that you can associate with a network interface."
- Amazon VPC quotas — https://docs.aws.amazon.com/vpc/latest/userguide/amazon-vpc-limits.html
  - 인용(표, 정확한 숫자): "Security groups per network interface | Default: 5 | Adjustable: Yes (up
    to 16) ... This quota multiplied by the quota for rules per security group cannot exceed 1,000."
  - 인용(대조, 규칙 수 기본값): "Inbound or outbound rules per security group | Default: 60"

**튜토리얼 서술에 미치는 영향:** 1장의 핵심 정의 문장으로 "SG는 서브넷이 아니라 ENI에 붙는다.
서브넷 단위 방화벽이 필요하면 NACL을 써야 한다"를 단정문으로 쓴다. "ENI 하나에 SG 5개까지(기본
값), 최대 16개"라는 구체적 숫자도 데모에 그대로 쓸 수 있다. **확정도: 확정.**

## V7 — WAF SQL database 관리형 규칙 그룹의 SQLi_BODY 규칙

**결론:** AWS WAF의 SQL database 관리형 규칙 그룹(`AWSManagedRulesSQLiRuleSet`)에는 `SQLi_BODY`라는
이름의 규칙이 실제로 존재한다. 이 규칙은 AWS WAF 내장 SQL 인젝션 탐지 룰 스테이트먼트를 민감도
(sensitivity level) Low로 사용해 **요청 본문(request body)**을 검사하고, 악성 SQL 코드 패턴과
일치하면 매치로 판정한다(Rule action: Block). 10장 데모의 `sqli` 시나리오 — "본문에 SQL 인젝션"
요청을 WAF는 막고 SG는 볼 수 없다 — 가 정확히 이 규칙이 다루는 케이스다. 처음 초안에서는 이 이름이
암기 기반 작성 과정에서 들어간 것인지 확인할 수 없어 일반화된 표현("SQL 인젝션 패턴을 탐지하는
관리형 규칙")으로 순화했으나, 이번 검증으로 실재가 확인되어 원래 표현으로 되돌렸다.

**근거:**
- Use-case specific rule groups (SQL database managed rule group) —
  https://docs.aws.amazon.com/waf/latest/developerguide/aws-managed-rule-groups-use-case.html
  - 인용(규칙 그룹 식별자): "VendorName: `AWS`, Name: `AWSManagedRulesSQLiRuleSet`, WCU: 200"
  - 인용(SQLi_BODY 행, 표 원문): "SQLi_BODY | Uses the built-in AWS WAF SQL injection attack rule
    statement, with sensitivity level set to Low, to inspect the request body for patterns that
    match malicious SQL code. ... Rule action: Block<br />Label:
    `awswaf:managed:aws:sql-database:SQLi_Body`"

**튜토리얼 서술에 미치는 영향:** 10장(WAF) 데모의 `sqli` 케이스에서 WAF 판정 사유로
`<code>SQLi_BODY</code> 관리형 규칙에 매치`를 그대로 쓴다 — 실제로 존재하는 규칙 이름이므로
안전하다. 같은 표에 있는 다른 규칙 이름(`SQLi_QUERYARGUMENTS` 등), 규칙 그룹 이름
(`AWSManagedRulesSQLiRuleSet`), 버전, WCU 같은 용량 단위는 튜토리얼 본문에는 추가하지 않는다 —
이번에 확인이 필요했던 것은 `SQLi_BODY` 하나뿐이다. **확정도: 확정.**
