## 1. 실제 프로젝터 가독성은 아직 아무도 보지 않았다: 리허설 전에 알 것

파일럿 노트 5번과 같은 미검증 항목이다. 이 덱은 도해 열 장 전부가 SVG 문자열로
이름표와 캡션을 그리고, 좌표계는 파일럿과 같은 1280×720을 통째로 확대·축소한다.
활자 하한 예외 목록의 `[svg, svg *]` 줄이 SVG 글자를 24px 본문 하한에서 빼 주는
근거는 "같은 말이 `.dia-cap`에 26px로 다시 실린다"는 것이고, 코드상으로는 성립한다.
그러나 **회의실 뒷자리에서 실제로 읽어 본 사람이 아직 없다.** 화면 크기와 거리,
조명, 프로젝터 명암비는 계산으로 답이 나오지 않는 변수이므로, 리허설에서 한 번은
실제 방에서 봐야 한다.

## 2. `Store`는 스텁이라 `s25`에서 고른 답이 장을 떠나면 사라진다

`const Store = { get(k, d){ return d; }, set(){} };`(3157행)로, 저장을 흉내만 내고
아무것도 담지 않는다. `s25`(빨리 죽을 자리와 버틸 자리 여덟 장 고르기, `judgeLab25`)
에서 카드를 판정한 뒤 다른 장으로 넘어갔다가 `←`로 돌아오면, 판정 결과는 남지 않고
처음부터 다시 고르게 된다. **의도한 동작이다.** 발표 중 되짚어 보일 필요가 없는
연습 화면이라 영속 저장소를 따로 두지 않았다.

## 3. 죽은 CSS 보고서의 생존자는 `.wrong` 하나다

Task 8 시점의 `python3 tools/check_dead_css.py --report`는 미사용 셀렉터 셋을
남겼다: `.cl-togs`·`.paused`·`.wrong`. 이번 마무리 검사에서 마크업의 `class` 속성과
JS의 `classList` 호출, 템플릿 리터럴 안의 `class` 문자열을 셋 다 확인한 뒤 판정했다.

- **`.cl-togs`는 지웠다.** CSS 정의(옛 433행) 한 줄 말고는 마크업에도 JS에도 이
  이름을 쓰는 자리가 없었다.
- **`.paused`도 지웠다.** `.dia.paused .dia-dot.on` 규칙(옛 523행)은 원본
  `defensive_programming.html`의 자동재생 버튼을 가리키던 것인데, 이 덱의 `wireDia`는
  자동재생 자체를 걷어냈다고 주석에 적혀 있다(`if(btn) btn.remove()`). `dia` 요소에
  `paused` 클래스를 붙이는 코드가 어디에도 없어, 그 규칙은 처음부터 닿을 길이 없는
  죽은 길이었다.
- **`.wrong`은 남겼다.** `wireQuizzes`가
  `btn.classList.add(btn.dataset.opt===q.dataset.answer?'correct':'wrong')`로 클릭
  시점에 문자열을 조립해 붙인다. 검사기는 정적 마크업만 세므로 이런 런타임 부여를
  구조적으로 보지 못한다. 파일럿 노트 6번이 세운 규칙 그대로, 지우면 오답을 고를 때
  빨간 테두리가 사라진다.

가지치기 전후 수치: 정의 109 · 사용 106 · 미사용 3 → 정의 107 · 사용 106 · 미사용 1.
지운 뒤 `python3 -m pytest tools/test_deck_behavior.py -k "defensive and (font_floor or
overflow)"`를 다시 돌려 화면이 그대로인지 확인했고, 3개 전부 통과했다. 화면에는
아무 변화도 없었다.

## 5. 완주 기록의 누름 수가 대장 계산과 하나 어긋난 이유를 확인했다

브리핑이 제시한 완주 스크립트를 그대로 돌리면 **누름 230 · 방문 67장 · 오류 0건**이
나온다. 대장(설계 문서의 슬라이드 대장)의 비트를 더하면 본편 183 + 부록 47 = 230이고,
"장 사이 이동은 마지막 비트에서 한 번만 더 누르면 된다"는 셈법으로는 230 − 1 = 229가
예상값이었다. 어느 장의 비트가 대장과 어긋난 것인지 찾기 위해
`Deck.slides.map(s=>[s.id, beatCount(s)])`로 67장 전부를 대장과 한 장씩 대조했는데,
**어긋난 장은 없었다.** 실측 `beatCount` 합계도 정확히 230으로, 대장과 완전히
일치했다.

어긋남의 원인은 슬라이드 쪽이 아니라 **완주 스크립트 자체의 종료 판정**에 있었다.
스크립트는 `→`를 누른 뒤에야 상태가 바뀌었는지를 확인하므로, 마지막 상태에 도달한
뒤 상태가 바뀌지 않는 것을 확인하는 탐침용 누름이 한 번 더 세어진다. 즉 이 스크립트가
세는 값은 "장 전환에 실제로 필요한 누름 수"(229)가 아니라 "실제로 필요한 누름 수 +
종료를 확인하는 누름 한 번"(230)이다. 같은 스크립트를 파일럿(`oauth2_slides.html`)에
그대로 돌려 봐도 184가 나와, 그 노트에 적힌 183보다 정확히 하나 많았다. 두 덱 모두
같은 폭으로 어긋나므로, 이것은 이 덱의 결함이 아니라 스크립트의 셈법이 갖는 고유한
특성이다. 발표 진행에는 영향이 없다. 발표자는 화살표를 실제로 필요한 횟수만큼만
누르면 되고, 스크립트가 한 번 더 세는 것은 눈에 보이지 않는 확인 절차일 뿐이다.

## 6. 코드 판 한 줄은 45자가 아니라 42자다 (아직 CSS 주석에 적지 않았다)

설계 문서는 코드 판의 폭을 45자로 어림잡아 두었다. 실측 결과 `.pair pre`가 차지하는
너비는 509px이고, 이 너비와 지금 쓰는 글자 크기·서체 조합에서 한 줄에 들어가는
글자 수는 42자다. 이 45라는 값은 설계 단계의 추정치였고, 이번 마무리 검사 시점까지
덱의 CSS 주석에는 정확한 42라는 값이 아직 적히지 않았다. 코드를 채워 넣을 때 줄
길이를 넘겨도 검사기가 잡아내지 못하므로, 다음에 코드 예제를 손보는 사람은 이
숫자를 CSS 주석에 옮겨 적어 두는 편이 안전하다.

## 7. 퀴즈 해설 `.explain`은 150px 스크롤 상자 안에 있다

파일럿의 퀴즈 해설은 한 줄이었지만, 이 덱의 해설은 오답마다 문단이 하나씩 붙어
길이가 세 배 가까이 된다. 글자 크기를 24px 본문 하한 아래로 내리지 않고 줄 간격과
안팎 여백만 좁혀도 여전히 720px 무대를 넘기므로, `.slide .quiz .explain`에
`max-height:150px; overflow-y:auto`를 주어 해설만 스크롤 상자에 담았다(248행). 질문과
보기 전부는 언제나 한 번에 보이고, 그 아래 해설만 필요할 때 그 상자 안에서 굴러간다.
CSS 주석(240행 부근)에도 이 판단의 근거가 남아 있다.
