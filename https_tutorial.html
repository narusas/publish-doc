HTTPS는 새로 발명된 기술이 아닙니다. "남이 못 읽게"(기밀성), "중간에 못 바꾸게"(무결성), "엉뚱한 상대와 말하지 않게"(인증) — 이 세 가지 오래된 요구를 각각 해결한 부품들을 순서대로 조립한 결과물입니다. 그래서 부품을 하나씩 이해하면, TLS 핸드셰이크는 외울 것이 아니라 당연한 순서로 읽히기 시작합니다.

01 · 문제

📡 평문으로 보낸 로그인은,
회선 위에서 이렇게 생겼습니다 🟢 필수

카페 와이파이에서 로그인 버튼을 누르는 순간을 떠올려 봅시다. 브라우저는 아이디와 비밀번호를 담은 요청을 서버로 보냅니다. 그 요청은 노트북에서 공유기로, 공유기에서 통신사 장비로, 다시 몇 개의 라우터를 거쳐 서버에 닿습니다. 중간에 놓인 장비는 열 개가 넘을 때도 있습니다. 그 장비들 앞을 지나가는 동안, 내 비밀번호는 어떤 모습을 하고 있을까요?

평문 HTTP라면 답은 허무할 정도로 간단합니다. 글자 그대로 지나갑니다. 암호도, 인코딩도, 아무런 가림막도 없이 사람이 읽을 수 있는 텍스트로요. tcpdump 같은 도구를 켜 두면 그 자리에서 읽힙니다. 아래 스위치를 눌러 같은 요청이 HTTP일 때와 HTTPS일 때 회선에서 어떻게 달라지는지 직접 비교해 보세요.

👂 읽는다

비밀번호, 세션 쿠키, 결제 정보, 주고받은 메시지. 지나가는 걸 그대로 복사해 갑니다. 기밀성(confidentiality)이 깨진 상태죠.

✂️ 바꾼다

응답 HTML에 광고 스크립트를 끼워 넣거나, 계좌번호 한 글자를 슬쩍 고칩니다. 무결성(integrity)이 깨진 상태입니다.

🎭 흉내 낸다

아예 자기가 그 은행 서버인 척 응답합니다. 나는 은행과 대화한다고 믿지만 상대는 공격자죠. 인증(authentication)이 없는 상태입니다.

세 번째가 특히 고약합니다. 통신 내용을 아무리 튼튼하게 암호화해도, 애초에 잘못된 상대와 완벽하게 암호화된 대화를 나누고 있다면 아무 의미가 없으니까요. 비밀 이야기를 속삭이는 상대가 사실 도둑이었다면, 목소리를 낮춘 게 무슨 소용일까요.

🎯 그래서 목표는 세 개다

HTTPS가 해결해야 하는 건 결국 이 셋입니다. 기밀성은 03·04장의 암호화와 키 교환이, 무결성은 05장의 해시와 인증 암호화가, 인증은 06·07장의 인증서와 체인이 각각 담당합니다. 하나라도 빠지면 나머지 둘이 무너진다는 점이 중요합니다.

"내용을 남이 못 읽게 하자"는 발상 자체는 컴퓨터보다 2천 년쯤 앞섭니다. 다만 무엇을 비밀로 할 것인가에 대한 답이 그 2천 년 동안 완전히 뒤집혔습니다. 이 전환을 이해하면 TLS 명세가 왜 알고리즘을 전부 공개하면서도 안전하다고 주장하는지가 자연스럽게 풀립니다.

카이사르는 알파벳을 세 칸 밀었다

기원전 로마, 카이사르는 전령이 붙잡힐 경우를 대비해 편지의 각 글자를 알파벳 순서로 세 칸씩 밀어 적었습니다. ATTACK은 DWWDFN이 됩니다. 받는 쪽은 세 칸 되돌리면 그만이고요. 규칙이 단순한 만큼 강력하진 않지만, 여기엔 오늘날까지 살아남은 뼈대가 이미 다 들어 있습니다. 평문 · 알고리즘(밀기) · 키(세 칸) · 암호문이라는 네 조각이요.

문제는 이 방식의 비밀이 사실상 "세 칸 민다"는 방법 자체였다는 점입니다. 방법이 들통나면 끝입니다. 게다가 키가 25가지뿐이라 하나씩 다 넣어 봐도 금방 풀리죠. 아래에서 직접 밀어 보세요. 그리고 키를 모르는 상태로 깨는 것도 해볼 수 있습니다.

🔤 고전 암호 실습기 — 밀기와 빈도 분석

💡 카이사르 상태에서 키 없이 깨보기를 눌러 보세요. 막대 하나가 유독 튀어나와 있고, 그게 E라고 가정하는 순간 키가 그대로 드러납니다. 비제네르 키워드를 넣으면 막대가 평평해지면서 이 수법이 통하지 않게 되는데 — 그래서 비제네르는 300년 동안 "깰 수 없는 암호"로 불렸습니다.

비제네르 암호는 키워드의 글자마다 다른 칸수로 밀어 빈도의 봉우리를 뭉갭니다. 실제로 오랫동안 난공불락으로 여겨졌고요. 그런데 19세기에 카시스키와 배비지가 키워드의 길이만 알아내면 그 길이만큼 쪼개어 각각 카이사르로 풀 수 있다는 걸 보였습니다. 깨지지 않는 암호처럼 보였을 뿐, 구조가 반복되는 한 언젠가는 무너진다는 교훈이 여기서 나옵니다.

기계가 등장하고, 원칙이 등장했다

20세기에 들어서면서 암호는 기계의 일이 됐죠. 독일의 에니그마는 회전자를 돌려 매 글자마다 치환 규칙을 바꿨고, 경우의 수는 천문학적이었습니다. 그런데도 블레츨리 파크의 팀은 이걸 깼습니다. 수학이 부족해서가 아니라 운용이 허술했기 때문입니다. 매일 같은 형식의 일기예보를 보내고, 설정을 반복해서 전송하고, 같은 인사말로 전문을 시작했거든요. 암호를 무너뜨린 건 알고리즘의 결함이 아니라 사람이 만든 규칙성이었습니다.

그 전에 이미, 한 네덜란드 언어학자가 이 모든 걸 예견하는 원칙을 적어 두었습니다.

🗝️ 케르크호프스의 원칙 (1883)

"암호 시스템은 키를 제외한 모든 것이 공개되어도 안전해야 한다."
방법을 감추는 데 기대는 보안(security through obscurity)은 방법이 새는 순간 전부 무너집니다. 반대로 알고리즘을 공개하면 전 세계 연구자가 달려들어 약점을 찾아 주고, 살아남은 알고리즘만 남습니다. 오늘날 AES·RSA·TLS 명세를 누구나 인터넷에서 읽을 수 있는 이유가 바로 이겁니다. 비밀은 오직 키 하나뿐이어야 합니다.

이 원칙이 자리 잡은 뒤에야 암호는 학문이 됐습니다. 1949년 클로드 섀넌은 정보이론으로 암호를 다시 정의했고, 키가 평문만큼 길고, 완전히 무작위이고, 단 한 번만 쓰이면 이론적으로 절대 깨지지 않는다는 것을 증명했습니다. 일회용 난수표(one-time pad)라고 부르는 방식이죠. 완벽한 답이 이미 1949년에 나와 있었던 셈입니다.

그런데 아무도 그걸 쓰지 않습니다. 왜일까요. 1GB짜리 파일을 보내려면 1GB짜리 키를 먼저 안전하게 전달해야 하기 때문입니다. 키를 안전하게 전달할 방법이 있었다면 애초에 그 방법으로 원본을 보내면 됐을 테고요. 완벽한 암호는 자기 꼬리를 무는 문제로 되돌아옵니다.

정답 B. 케르크호프스의 원칙입니다. 클라이언트 바이너리를 디컴파일하면 알고리즘은 드러나고, 그 순간 검증 한 번 받지 않은 설계가 통째로 노출됩니다. AES가 안전하다고 여겨지는 건 20년 넘게 전 세계가 공격해도 실용적으로 깨지지 않았기 때문이에요. "직접 만든 암호를 쓰지 말라(don't roll your own crypto)"는 업계 격언이 괜히 있는 게 아닙니다.

글자를 미는 방식은 컴퓨터에겐 어울리지 않습니다. 컴퓨터가 다루는 건 알파벳이 아니라 비트니까요. 그래서 현대 대칭키 암호는 훨씬 단순하고 훨씬 사나운 연산에서 출발합니다. 바로 XOR입니다.

비트를 뒤집는 한 번의 연산

XOR(배타적 논리합)은 두 비트가 다르면 1, 같으면 0을 내놓습니다. 이 연산에는 암호에 쓰기 딱 좋은 성질이 하나 있습니다. 같은 값을 두 번 XOR하면 원래대로 돌아온다는 것이죠.

평문   0 1 1 0 1 0 0 1   ← "A"에 해당하는 비트라고 하자
키     1 1 0 1 0 1 1 0   ← 무작위 비트열
────────────────────── XOR
암호문 1 0 1 1 1 1 1 1   ← 회선에 흘러가는 값

암호문 1 0 1 1 1 1 1 1
키     1 1 0 1 0 1 1 0   ← 같은 키를 다시 XOR
────────────────────── XOR
평문   0 1 1 0 1 0 0 1   ← 원래 값 복구

잠그는 연산과 푸는 연산이 똑같습니다. 그래서 보내는 쪽과 받는 쪽이 같은 키를 가지고 있어야 하고, 이 성질 때문에 대칭(symmetric)이라 부릅니다. 키가 평문만큼 길고 매번 새로 뽑은 난수라면 이게 바로 앞 장의 일회용 난수표고요. 현실에서는 짧은 키(16바이트나 32바이트)에서 난수처럼 보이는 긴 비트열을 만들어 내는 쪽으로 타협합니다.

DES에서 AES까지 — 키 길이가 생명이었다

1977년 미국 표준으로 채택된 DES는 56비트 키를 썼습니다. 당시 기준으로는 넉넉했습니다. 2의 56제곱을 다 시도하려면 수천 년이 걸릴 계산이었으니까요. 그런데 컴퓨터가 빨라졌습니다. 1998년 전자프런티어재단이 25만 달러짜리 전용 기계를 만들어 56시간 만에 DES 키를 찾아냈습니다. 급한 대로 DES를 세 번 겹쳐 쓰는 3DES가 나왔지만, 세 배 느린 임시방편일 뿐이었죠.

그래서 미국 표준기술연구소는 공개 공모를 엽니다. 전 세계에서 후보를 받고, 몇 년에 걸쳐 서로 공격하게 하고, 살아남은 것을 표준으로 삼는 방식으로요. 1997년에 시작해 2001년에 벨기에 연구자들의 Rijndael이 AES로 확정됐습니다. 전 과정이 공개된 채로 진행됐다는 점에 주목할 만합니다. 케르크호프스의 원칙이 제도로 굳어진 순간이었거든요.

🤔 128비트면 짧지 않나요?

2의 128제곱은 약 3.4×10³⁸입니다. 초당 1조 개의 키를 시도하는 기계를 지구 인구수만큼(80억 대) 돌려도 전수 조사에는 우주 나이의 수십억 배가 걸립니다. 키 길이를 늘리는 것보다 구현을 제대로 하는 게 훨씬 중요한 이유죠. 실제로 깨진 사례는 대부분 알고리즘이 아니라 난수 생성기, 키 관리, 코드 버그 쪽이었습니다.

블록을 어떤 순서로 이어 붙이느냐가 결과를 바꾼다 🔵 심화

AES는 한 번에 16바이트씩 처리하는 블록 암호입니다. 그런데 우리가 보내려는 데이터는 16바이트보다 훨씬 길죠. 그래서 데이터를 블록으로 자른 뒤 어떻게 이어 붙일지 정하는 규칙이 따로 필요합니다. 이걸 운용 모드(mode of operation)라고 부릅니다. 가장 순진한 방법은 블록마다 똑같이 암호화하는 것인데 — 이게 왜 재앙인지는 말보다 그림이 빠릅니다.

키는 세 번 모두 동일합니다

💡 ECB는 같은 평문 블록이 항상 같은 암호문 블록이 됩니다. 그래서 내용은 못 읽어도 윤곽이 그대로 남습니다. 1996년 이 현상을 리눅스 마스코트 이미지로 보여준 예시가 유명해져서, 지금도 "ECB 펭귄"이라 부릅니다.

  • ECB — 블록마다 따로 암호화. 구조가 새어 나가므로 어떤 경우에도 쓰면 안 됩니다.
  • CBC — 각 블록을 직전 암호문과 XOR한 뒤 암호화. 첫 블록에는 난수 IV를 씁니다. 같은 평문도 매번 다른 암호문이 되지만, 앞 블록을 기다려야 해서 병렬 처리가 안 됩니다.
  • CTR — 카운터를 암호화해 키스트림을 만들고 평문과 XOR. 블록끼리 독립적이라 병렬 처리가 되고 아주 빠릅니다.
  • GCM — CTR로 암호화하면서 인증 태그까지 함께 계산. 지금의 사실상 표준입니다.

암호화만으로는 위조를 막지 못한다

여기서 01장의 세 번째 위협이 돌아옵니다. CTR 모드는 평문과 키스트림을 XOR하는 방식이죠. 그렇다면 공격자가 암호문의 특정 비트를 뒤집으면, 복호화된 평문에서도 정확히 같은 위치의 비트가 뒤집힙니다. 키를 몰라도, 내용을 못 읽어도 됩니다. 전문의 형식만 알면 충분하죠. 직접 해보는 편이 빠르겠습니다.

정리하면 이렇습니다. 둘은 공개된 기준값 g, p에 각자의 비밀값을 "섞어서" 보냅니다. 그리고 받은 값에 다시 자기 비밀값을 섞습니다. 섞는 순서가 달라도 결과는 같은 색이 되죠. 수학으로 쓰면 (gb)a = (ga)b = gab, 지수의 교환법칙 하나가 전부입니다.

데모의 기본값(a = 6, b = 15)을 손으로 따라가면 이렇게 됩니다.

회선에 나가는 값 (누구나 본다)
  A = g^a mod p = 5^6  mod 23 = 15625       mod 23 = 8
  B = g^b mod p = 5^15 mod 23 = 30517578125 mod 23 = 19

각자 혼자 계산하는 값 (아무에게도 안 보낸다)
  앨리스: B^a mod p = 19^6 mod 23 = 2   ┐
  밥    : A^b mod p = 8^15 mod 23 = 2   ┘  같은 값 → 이게 공유 비밀

도청자가 가진 것: p=23, g=5, A=8, B=19
  → 2를 만들려면 5^x mod 23 = 8 을 만족하는 x(=6)를 찾아야 한다

도청자는 g, p, A, B를 전부 듣습니다. 그런데 A = ga mod p에서 a를 되찾는 일 — 이걸 이산 로그 문제라고 하는데, 숫자가 충분히 크면 현실적인 시간 안에 풀 방법이 알려져 있지 않습니다. 위 데모는 p가 23이라 하나씩 넣어 보면 금방 풀리지만, 실제로는 2048비트, 그러니까 617자리 수를 씁니다.

타원곡선이 판을 바꿨다 🔵 심화

2048비트짜리 거듭제곱은 모바일 기기에 부담스러웠습니다. 그래서 등장한 게 타원곡선 위에서 같은 논리를 펴는 ECDH입니다. 곱셈 대신 곡선 위의 점을 더하는 연산을 쓰는데, 되돌리기가 훨씬 더 어려워서 256비트만으로 3072비트 DH와 비슷한 강도가 나옵니다. 키가 짧으니 계산도, 전송할 바이트도 줄어들죠. 요즘 TLS 핸드셰이크에서 압도적으로 많이 쓰이는 X25519가 바로 이 방식입니다.

여기서 p와 g의 자리는 곡선 하나가 통째로 대신합니다. "X25519로 하죠"라는 이름 한 줄이 곧 기준값 합의라서, 요즘 핸드셰이크에서는 소수와 밑을 직접 실어 보내지 않습니다. 비밀값 a, b가 매 접속마다 새로 뽑히는 난수라는 점만 그대로고요. 09장의 핸드셰이크 재생기에서 key_share라는 이름으로 오가는 값이 바로 위 데모의 A와 B에 해당합니다.

매번 새 키를 버리는 이유 — 전방향 비밀성

디피–헬먼에는 잘 드러나지 않는 미덕이 하나 더 있습니다. 매 접속마다 a와 b를 새로 뽑아 쓰고 끝나면 버릴 수 있다는 점입니다. 끝에 붙는 E는 임시(ephemeral)의 약자고요. 그래서 ECDHE라고 씁니다.

이게 왜 중요한지는 반대 경우를 보면 확실해집니다. TLS 1.2까지는 RSA 키 전송이라는 방식도 쓸 수 있었습니다. 클라이언트가 대칭키를 하나 만들어 서버의 공개키로 암호화해 보내는 방식이죠. 간단하고 잘 동작했습니다. 문제는 서버의 개인키 하나가 모든 세션의 마스터키였다는 점입니다.

⏳ 지금 저장해 두고 나중에 해독한다

공격자가 오늘 오간 암호문을 전부 녹화해 창고에 쌓아 둡니다. 지금은 못 읽습니다. 그런데 3년 뒤 그 서버의 개인키가 유출되면? RSA 키 전송 방식이었다면 3년 치 통신이 한꺼번에 전부 열립니다. ECDHE라면 세션마다 쓴 임시 키는 이미 메모리에서 사라졌으니, 개인키가 털려도 과거 기록은 그대로 잠겨 있습니다. 이 성질을 전방향 비밀성(Forward Secrecy)이라 부르고, TLS 1.3은 RSA 키 전송을 아예 삭제해서 이걸 강제했습니다.

그런데 상대가 진짜 그 서버가 맞나

키 교환은 우아하게 끝났습니다. 여기서 만족하고 넘어가고 싶어지는데, 한 가지가 걸립니다. 앨리스는 자기가 받은 값 B가 정말 밥이 보낸 것인지 확인한 적이 한 번도 없습니다. 회선에서 날아온 숫자를 그냥 믿었을 뿐이죠. 중간에 앉은 누군가가 양쪽과 각각 디피–헬먼을 하면 어떻게 될까요.

"이 데이터가 오는 도중에 바뀌지 않았다"와 "이 데이터를 보낸 사람이 진짜 그 사람이다". 비슷해 보이지만 완전히 다른 두 문장입니다. 앞의 것을 해결하는 게 해시, 뒤의 것을 해결하는 게 전자서명이고, 서명은 해시 위에 올라타는 구조라서 순서대로 보는 편이 좋습니다.

어떤 데이터든 같은 길이의 지문으로

해시 함수는 아무리 긴 데이터를 넣어도 정해진 길이의 값을 뱉습니다. SHA-256이라면 언제나 256비트, 즉 64자리 16진수죠. 쓸모는 다음 세 성질에서 나옵니다.

  • 일방향 — 해시값을 보고 원본을 되돌릴 방법이 없습니다. 계산은 한쪽으로만 흐릅니다.
  • 쇄도 효과(avalanche) — 입력을 한 글자, 아니 한 비트만 바꿔도 출력이 완전히 달라집니다. 절반쯤 닮은 결과 같은 건 나오지 않습니다.
  • 충돌 저항성 — 같은 해시값을 갖는 서로 다른 두 입력을 찾기가 현실적으로 불가능해야 합니다.

💀 MD5와 SHA-1은 왜 쓰면 안 되나

충돌 저항성이 깨졌기 때문입니다. MD5는 2004년에 서로 다른 두 입력이 같은 해시를 갖도록 만드는 방법이 나왔고, 2012년 Flame 악성코드는 이 성질을 이용해 마이크로소프트 서명을 위조한 뒤 윈도우 업데이트를 가장했습니다. SHA-1은 2017년 구글이 실제 충돌 PDF 두 개를 만들어 공개(SHAttered)하면서 사망 선고를 받았고요. 내용이 다른 두 문서가 같은 지문을 가질 수 있다면, 지문으로 문서를 보증하는 일 자체가 성립하지 않습니다. 지금은 SHA-256 이상을 씁니다.

🔐 비밀번호 저장은 다른 이야기입니다

"비밀번호를 SHA-256으로 해싱해서 저장했으니 안전하다"는 흔한 오해가 있습니다. SHA-256은 빠르라고 만든 함수라서, GPU로 초당 수십억 개를 시도할 수 있습니다. 흔한 비밀번호는 순식간에 뚫리죠. 비밀번호에는 일부러 느리게 만든 bcrypt, scrypt, Argon2를 쓰고 사용자마다 다른 솔트를 붙입니다. 같은 해시라는 단어를 써도 용도가 다르면 도구가 다릅니다.

지문만으로는 부족한 이유

해시를 데이터 뒤에 붙여 보내면 무결성이 확인될 것 같습니다. 저도 잠깐 그렇게 생각했습니다. 그런데 중간자를 다시 떠올려 보면 금방 무너집니다. 그 사람은 데이터를 바꾼 뒤 해시도 다시 계산해서 붙이면 그만이거든요. 해시 함수는 누구나 계산할 수 있으니까요.

그래서 비밀을 하나 섞습니다. 데이터와 공유 비밀키를 함께 해싱하는 방식을 HMAC이라 부릅니다. 키를 모르면 올바른 값을 만들 수 없으니, 이제 "바뀌지 않았다"와 "키를 아는 쪽이 보냈다"가 동시에 보증됩니다. 03장의 AEAD가 내부에서 하는 일이 정확히 이거고요.

다만 HMAC은 대칭입니다. 검증할 수 있는 사람은 위조도 할 수 있습니다. 둘 다 같은 키를 가지고 있으니까요. 은행이 나에게 보낸 전문을 내가 검증할 수 있다면, 나도 은행 흉내를 낼 수 있다는 뜻이 됩니다. 제3자에게 "이건 은행이 보낸 게 맞다"고 증명할 수도 없고요. 비대칭이 필요해지는 지점이 여기입니다.

열쇠를 두 개로 쪼갠다 — 공개키 암호

1977년 리베스트·샤미르·에이들먼이 발표한 RSA는 열쇠를 한 쌍으로 만듭니다. 한쪽으로 잠근 것은 반드시 다른 쪽으로만 열립니다. 하나는 온 세상에 뿌리고(공개키), 하나는 절대 내주지 않습니다(개인키). 쌍이지만 공개키에서 개인키를 계산해 낼 수는 없습니다. 큰 수의 소인수분해가 어렵다는 사실이 그 벽을 세우고 있죠.

발표된 지 반세기가 다 되어 갑니다. 그런데도 아직 현역입니다. 지금 여러분의 ~/.ssh 폴더에 있는 키, 로그인 서버가 발급하는 JWT의 RS256, 브라우저가 방금 검증한 인증서 — 여기저기에 그 이름이 박혀 있습니다. 이렇게 오래 버틴 암호는 흔치 않습니다. 그만큼 잘 만들어졌다는 뜻이기도 하고, 그만큼 많이 두들겨 맞았다는 뜻이기도 하고요.

여기서 헷갈리기 쉬운 게 방향입니다. 쓰는 순서를 뒤집으면 용도가 완전히 달라집니다.

🔒 암호화 — 공개키로 잠그고 개인키로 연다

누구나 그 사람의 공개키로 잠글 수 있지만, 열 수 있는 건 개인키를 가진 본인뿐입니다.
목적: 비밀 유지. 아무나 우체통에 편지를 넣을 수 있지만 꺼내는 건 열쇠 가진 사람뿐인 것과 같습니다.

✍️ 서명 — 개인키로 잠그고 공개키로 연다

개인키를 가진 본인만 만들 수 있고, 공개키를 가진 누구나 확인할 수 있습니다.
목적: 신원 증명. 아무나 도장을 대조해 볼 수 있지만 찍을 수 있는 건 도장 주인뿐인 셈이죠.

열쇠 한 쌍은 어떻게 만들어지나 🔵 심화

"공개키에서 개인키를 못 구한다"는 말이 처음엔 마술처럼 들립니다. 둘은 명백히 한 쌍인데 말이죠. 실제로 RSA의 키 생성은 중학교 수준의 곱셈 하나에서 출발합니다. 마술은 그 곱셈을 되돌리기가 어렵다는 데 있고요.

절차는 다섯 줄입니다. 아래에서 소수를 직접 골라 가며 따라가 보세요.

🔬 RSA 키 생성기 — 소수 두 개에서 열쇠 한 쌍까지

핵심은 네 번째 줄입니다. d를 구하려면 φ(n)을 알아야 하고, φ(n)을 알려면 p와 q를 알아야 합니다. 공개된 것은 n뿐이니, 개인키를 구하려면 n을 소인수분해하는 수밖에 없죠. 그리고 이 분해가 바로 "쉬운 방향과 어려운 방향"의 그 어려운 쪽입니다.

🔢 한쪽으로만 쉬운 계산

300자리 소수 두 개를 곱하는 데는 1밀리초도 안 걸립니다. 그런데 그 곱을 다시 두 소수로 쪼개는 일은요?
공개된 도전 과제 중 지금까지 분해된 가장 큰 수는 RSA-250(829비트, 250자리)이고, 2020년에 여러 연구팀이 클러스터를 동원해 약 2,700 코어-년을 태워서 풀었습니다. 실무에서 쓰는 2048비트(617자리)는 그보다 까마득히 큽니다. 알려진 방법으로는 손댈 수 없는 영역이죠.
이렇게 한 방향은 쉽고 반대 방향은 사실상 불가능한 계산을 일방향 함수라 하고, 비밀을 아는 사람에게만 뒷문이 열려 있으면 트랩도어가 붙습니다. RSA의 뒷문이 바로 p와 q입니다.

교과서대로 쓰면 깨진다 — 패딩이 필요한 이유

지금까지 설명한 me mod n 방식을 그대로 쓰면 어떻게 될까요. 실제로 그렇게 쓰면 안 됩니다. 이걸 교과서 RSA(textbook RSA)라 부르는데, 이름부터가 "교과서에서만 쓰라"는 뜻이거든요. 구멍이 최소 두 개입니다.

  • 결정론적이다 — 같은 m은 언제나 같은 c가 됩니다. "예" / "아니오" 두 가지만 오가는 통신이라면, 공격자는 두 값을 미리 암호화해 두고 대조만 하면 내용을 알아냅니다. 키는 건드릴 필요도 없죠.
  • 곱셈이 그대로 통과한다 — 암호문 두 개를 곱하면 평문 두 개를 곱한 결과가 나옵니다 (c₁·c₂ = (m₁·m₂)e). 위 실습기의 😈 암호문에 손대 보기가 이걸 보여줍니다. 공격자가 암호문에 2e를 곱해 두면, 받는 쪽이 복호화한 값은 정확히 원래의 두 배가 됩니다. 03장에서 본 그 가변성이 여기서도 똑같이 나타나는 셈입니다.

그래서 실제 RSA는 원문에 난수와 정해진 구조를 덧대고 나서 거듭제곱을 겁니다. 이 덧대는 규칙이 패딩이고요. 암호화에는 OAEP, 서명에는 PSS를 씁니다. 둘 다 난수를 섞기 때문에 같은 입력이라도 매번 다른 결과가 나옵니다.

💀 패딩 하나가 20년을 끌었다

1998년 블라이헨바허는 낡은 PKCS#1 v1.5 패딩에 흥미로운 공격을 걸었습니다. 서버에 암호문을 조금씩 바꿔 보내면서 "패딩 형식이 틀렸다"는 오류가 나오는지만 관찰하는 방식이었죠. 오류 하나가 정보 한 조각이 되고, 그걸 백만 번쯤 반복하면 개인키 없이도 평문이 복원됩니다.
더 인상적인 건 뒷이야기입니다. 대응책이 나왔는데도 구현들이 미묘하게 어긋나 있어서, 19년 뒤인 2017년에 ROBOT이라는 이름으로 같은 공격이 되살아났습니다. 페이스북과 페이팔을 포함한 대형 사이트들이 영향을 받았고요. 알고리즘이 아니라 그 주변을 감싸는 규칙에서 사고가 난다는 것을, RSA만큼 반복해서 보여준 사례도 드뭅니다.

왜 하필 65537인가, 그리고 왜 서명은 느린가

실제 인증서를 열어 보면 공개 지수가 거의 항상 65537입니다(06장 뷰어에도 그렇게 적혀 있죠). 우연이 아닙니다. 65537 = 216 + 1이라 이진수로 쓰면 1이 딱 두 개뿐이거든요. 거듭제곱은 1의 개수만큼 곱셈이 늘어나니, 이 값이면 검증이 아주 빠릅니다. 그렇다고 3처럼 너무 작지도 않아서, 작은 지수를 노리는 공격도 피해 갑니다. 빠르면서 안전한 절충점인 셈입니다.

여기서 RSA의 독특한 성격이 하나 드러납니다. 검증은 아주 빠르고, 서명은 아주 느립니다. 검증은 17비트짜리 e로 거듭제곱하지만, 서명은 n만큼 거대한 d로 거듭제곱해야 하니까요. 차이가 수십 배까지 납니다.

이 차이가 실무에 그대로 나타납니다. TLS 핸드셰이크에서 서명하는 쪽은 서버이므로, RSA 인증서를 쓰면 접속마다 서버 CPU가 그 값을 치릅니다. 트래픽이 많은 서비스가 ECDSA 인증서로 옮겨 가는 이유고요. 반대로 한 번 서명해 두고 수억 번 검증하는 상황 — 코드 서명이나 펌웨어 검증 같은 — 에서는 RSA의 빠른 검증이 오히려 유리합니다.

키 길이는 왜 자꾸 늘어나기만 하나

RSA의 가장 곤란한 점이 여기 있습니다. 분해 기술이 조금 좋아질 때마다 키 길이를 크게 늘려야 같은 안전 수준이 유지됩니다. 그런데 늘어나는 폭이 선형이 아닙니다.

마지막 줄이 RSA의 한계를 압축해서 보여줍니다. 256비트 강도를 원하면 타원곡선은 512비트 키면 되는데, RSA는 15360비트가 필요합니다. 30배죠. 키 파일도, 핸드셰이크에 실리는 바이트도, 연산 시간도 함께 부풀어 오릅니다. 04장에서 "타원곡선이 판을 바꿨다"고 한 이유가 이 표에 그대로 들어 있습니다.

🧭 그래서 RSA는 지금 어디에 있나

여전히 넓게 쓰입니다. 오래된 표준일수록 호환성의 무게가 크고, 이미 배포된 키를 바꾸는 일은 느리니까요. 개발자가 RSA를 만나는 자리는 대개 이 넷입니다.

  • TLS 인증서 — 서버 인증서의 상당수가 아직 RSA 키입니다. ECDSA로 옮겨 가는 중이고요
  • JWT의 RS256 — 비대칭 서명 JWT의 사실상 기본값. ES256(ECDSA)이 대안입니다
  • SSH 키 — id_rsa. 다만 SHA-1을 쓰는 옛 ssh-rsa 방식은 OpenSSH 8.8(2021)에서 기본 비활성화됐으니, 새로 만든다면 ed25519를 권합니다
  • 코드·문서 서명 — 검증이 압도적으로 많은 영역이라 RSA가 잘 맞습니다

다만 방향은 정해져 있습니다. 새로 만드는 것에는 타원곡선을 고르고, 15장에서 볼 양자내성 암호로 넘어갈 때 RSA는 가장 먼저 정리될 자리에 있습니다. 소인수분해와 이산 로그를 동시에 무너뜨리는 것이 바로 그 알고리즘이거든요.

🔀 TLS에서 "RSA"라는 말이 두 가지를 가리킨다

혼동이 잦은 지점이라 한 번 갈라 두는 편이 좋겠습니다. 04장과 09장에서 본 두 자리가 서로 다릅니다.

  • RSA 키 전송(키 교환용) — 클라이언트가 대칭키를 서버 공개키로 암호화해 보내던 방식. 전방향 비밀성이 없어서 TLS 1.3에서 삭제됐습니다.
  • RSA 서명(신원 증명용) — 서버가 인증서 개인키로 CertificateVerify에 서명하는 자리. TLS 1.3에서도 그대로 쓰입니다. 패딩만 PSS로 바뀌었고요.

즉 "TLS 1.3이 RSA를 없앴다"는 말은 절반만 맞습니다. 없어진 건 키 교환용 RSA고, 서명용 RSA는 현역입니다.

실제로 서명할 때 문서 전체를 개인키로 처리하지는 않습니다. 공개키 연산은 무겁고, 다룰 수 있는 크기에도 제한이 있거든요. 그래서 ① 문서를 해싱해 지문을 만들고 ② 그 지문에만 개인키 연산을 겁니다. 검증하는 쪽은 ① 받은 문서를 직접 해싱하고 ② 서명을 공개키로 풀어 나온 지문과 비교합니다. 두 값이 같으면 통과입니다.

📜 인증서가 담고 있는 주장

"도메인 www.example.com의 공개키는 이 값이 맞습니다. — 인증기관 XYZ가 보증하며, 이 문장 전체에 우리 개인키로 서명했습니다. 유효기간은 여기까지입니다."

그러니까 인증서의 본질은 공개키와 이름을 한데 묶어 제3자가 서명한 것입니다. 05장에서 배운 서명이 여기에 그대로 쓰이죠. 묶는 대상이 무엇인지가 중요합니다. 인증서는 "이 사이트가 안전하다"거나 "이 회사가 정직하다"를 보증하지 않습니다. 이름과 열쇠의 연결만 보증합니다. 이 구분이 15장까지 계속 따라옵니다.

형식은 X.509라는 국제 표준을 따릅니다. 1988년에 만들어진 오래된 규격이라 지금 보면 어색한 구석도 있지만, 전 세계가 같은 형식을 쓰기 때문에 브라우저·서버·언어 라이브러리가 모두 같은 문서를 읽을 수 있습니다. 안을 직접 열어 봅시다.

발급은 어떻게 이뤄지나

순서는 생각보다 단순합니다. 그리고 이 순서에서 개인키가 한 번도 서버 밖으로 나가지 않는다는 점이 중요합니다.

1
키쌍 생성

내 서버에서 개인키와 공개키를 만듭니다. 개인키는 이 서버를 절대 떠나지 않습니다.

2
CSR 작성

공개키 + 도메인 이름 + 조직 정보를 묶어 인증서 서명 요청서(CSR)를 만들고, 내 개인키로 서명해 "이 공개키의 짝을 내가 갖고 있다"를 보입니다.

3
도메인 소유 확인

CA가 "정말 이 도메인의 주인이 맞냐"를 확인합니다. 지정한 경로에 파일을 올리게 하거나(HTTP-01), 특정 TXT 레코드를 DNS에 넣게 합니다(DNS-01).

4
CA가 서명

확인이 끝나면 CA가 자기 개인키로 서명해 인증서를 발급합니다. 여기서 비로소 문서가 완성됩니다.

5
서버에 설치

인증서와 중간 인증서를 함께 배치합니다. 이 "함께"를 빠뜨려서 나는 사고가 실무에서 가장 흔합니다(07장).

예전에는 3~5번이 사람 손을 거쳤습니다. 서류를 내고, 전화를 받고, 며칠 기다리고, 돈을 냈죠. 2016년 Let's Encrypt가 이 과정을 ACME라는 프로토콜로 자동화하고 무료로 풀면서 판이 바뀌었습니다. 명령 한 줄로 발급과 갱신이 끝나니, HTTPS를 안 쓸 이유가 사라졌고요. 2015년 전체 웹 트래픽의 절반 이하였던 HTTPS 비율이 지금은 90%대입니다.

프로토콜은 왜 계속 깨졌나 🔵 심화 · 교양

1994년 넷스케이프는 급했습니다. 웹에서 신용카드를 받으려면 암호화가 필요한데, 표준이 나오길 기다릴 시간은 없었죠. 그래서 사내에서 직접 만든 것이 SSL(Secure Sockets Layer)입니다. 버전 1.0은 결함이 너무 많아 공개조차 못 했고, 1995년의 2.0도 곧 심각한 문제가 드러나 1996년 3.0으로 다시 쓰였습니다. 급하게 만든 것을 고쳐 쓰는 패턴은 이때 시작됐습니다.

1999년 IETF가 표준으로 받아들이면서 이름이 TLS(Transport Layer Security)로 바뀝니다. 특정 회사의 상표를 표준 이름으로 쓸 수 없었거든요. 그래서 TLS 1.0은 사실상 SSL 3.1입니다. 지금도 사람들이 습관처럼 "SSL 인증서"라고 부르는데, 정확히는 TLS 인증서죠. 이름만 남은 셈입니다.

🩸 Heartbleed가 특별했던 이유 (2014)

서버에게 "이 64KB짜리 데이터를 그대로 돌려줘"라고 요청하면서 실제로는 1바이트만 보냅니다. OpenSSL은 길이를 검사하지 않고 메모리에서 64KB를 긁어 그대로 응답했습니다. 그 안에는 다른 사용자의 세션 쿠키, 비밀번호, 심지어 서버 개인키가 들어 있었죠. 전 세계 웹서버의 17%가 영향을 받았고, 흔적도 남지 않았습니다. 암호학이 아무리 견고해도 그 아래 C 코드의 배열 인덱스 하나가 전부를 무너뜨릴 수 있다는 사실을 각인시킨 사건입니다.

TLS 1.3은 기능을 더한 게 아니라 걷어냈다

2018년 나온 TLS 1.3(RFC 8446)의 설계 철학은 명확했습니다. 선택지를 없앤다. 깨진 것들을 고치는 대신 아예 제거해 버렸습니다.

  • RSA 키 전송 삭제 — 전방향 비밀성이 없는 방식은 협상 자체가 불가능해졌습니다(04장).
  • AEAD가 아닌 암호 전부 삭제 — CBC 조합, RC4, 3DES가 사라졌습니다(03장).
  • 압축 삭제 — 압축률로 평문을 추측하는 CRIME 공격을 원천 차단했습니다.
  • 재협상 삭제 — 세션 중간에 조건을 다시 흥정하는 기능이 반복해서 사고를 냈거든요.
  • 암호 스위트 5개 — 300개가 넘던 조합이 다섯 개로 줄었습니다. 고민할 여지를 없앤 겁니다.
  • 다운그레이드 방지 — 서버가 보내는 난수에 표식을 심어, 공격자가 버전을 끌어내리면 클라이언트가 알아챕니다.
  • 핸드셰이크 1왕복 — 덤으로 빨라지기까지 했습니다(09장).

🧭 여기서 얻을 실무 원칙

"안전한 설정"이란 강한 옵션을 켜는 일이라기보다 약한 옵션을 끄는 일에 가깝습니다. TLS 1.0/1.1은 2021년에 주요 브라우저가 모두 제거했고요. 지금 서버에서 켜 둘 이유는 없습니다. TLS 1.2 이상만 허용하고, 1.2에서는 ECDHE + AEAD 조합만 남기는 것이 기본값입니다(14장에서 설정으로 확인합니다).

여기서 미묘한 문제 하나가 남습니다. 핸드셰이크 초반 메시지들은 아직 키가 없어서 평문으로 오갑니다. 중간자가 그 목록을 슬쩍 고쳐 "이 클라이언트는 약한 암호밖에 못 씁니다"라고 속이면 어떻게 될까요.

그래서 양쪽은 마지막에 Finished 메시지를 주고받습니다. 이건 지금까지 주고받은 모든 핸드셰이크 메시지를 이어 붙여 해시하고, 방금 합의한 키로 MAC을 건 값입니다. 중간에 한 바이트라도 달라졌다면 양쪽이 계산한 값이 어긋나고, 연결은 즉시 끊깁니다. 대화의 내용이 아니라 대화의 이력에 서명하는 셈이죠. 05장의 HMAC이 여기에 쓰입니다.

🔑 하나의 비밀에서 여러 개의 키가 나온다

키 교환으로 얻은 값을 그대로 암호화 키로 쓰지는 않습니다. HKDF라는 키 유도 함수에 넣어 용도별로 여러 키를 뽑아냅니다. 핸드셰이크 구간용 키, 애플리케이션 데이터용 키, 클라이언트→서버 방향과 서버→클라이언트 방향이 각각 다른 키를 씁니다. 방향마다 키를 나누는 이유는, 공격자가 서버가 보낸 패킷을 그대로 클라이언트에게 되돌려 보내는 반사 공격을 막기 위해서입니다.

두 번째 접속은 더 빠르다 — 그리고 그 대가

한 번 핸드셰이크를 끝낸 상대와 다시 만날 때, 처음부터 다 하는 건 낭비입니다. 그래서 서버는 접속을 끝내며 세션 티켓을 하나 발급합니다. 다음에 그걸 제시하면 이미 합의된 비밀(PSK)에서 키를 되살려 인증 과정을 건너뛸 수 있죠.

TLS 1.3은 여기서 한 발 더 나갑니다. 0-RTT는 클라이언트가 첫 패킷에 이미 HTTP 요청까지 실어 보냅니다. 왕복 대기 없이 데이터가 출발하니 체감 속도가 확 달라지죠. 다만 공짜는 아닙니다.

⚠️ 0-RTT 데이터는 재전송 공격에 노출된다

0-RTT 구간의 데이터에는 이번 연결에만 유효하다는 증거가 없습니다. 공격자가 그 패킷을 그대로 복사해 두었다가 서버에 여러 번 재전송하면, 서버는 같은 요청을 여러 번 처리할 수 있습니다. 조회 요청이면 상관없지만 "1만원 이체"였다면 이야기가 다르죠.
그래서 규칙은 명확합니다 — 0-RTT에는 GET처럼 멱등한 요청만 실어야 합니다. 상태를 바꾸는 요청은 핸드셰이크가 끝난 뒤로 미뤄야 하고, 프레임워크가 이걸 자동으로 처리해 주지 않는다면 직접 막아야 합니다.

📛 SNI — 어느 도메인을 찾는지 먼저 말한다

한 IP에 수백 개 사이트가 올라가는 시대에, 서버는 어느 인증서를 보내야 할지부터 알아야 합니다. 그래서 ClientHello에 도메인 이름을 평문으로 적어 보냅니다. 편리한 대신, 암호화 이전이라 도청자에게 노출됩니다. 이 구멍을 막는 게 ECH(Encrypted Client Hello)인데, 아직 확산 중입니다.

🗣️ ALPN — 어떤 언어로 말할지 미리 정한다

TLS를 맺으면서 "그 위에서 HTTP/2로 말할까요, 1.1로 말할까요?"를 함께 협상합니다. h2, http/1.1 같은 문자열을 주고받죠. 별도 왕복 없이 프로토콜이 정해지기 때문에, HTTP/2 도입이 이렇게 매끄러웠던 겁니다. 12장에서 다시 만납니다.

10 · 합체

🔒 HTTP를 TLS 위에 얹으면,
무엇이 감춰지고 무엇이 남나 🟢 필수

막상 정의는 허탈할 만큼 간단합니다. HTTPS = HTTP + TLS. HTTP 문법은 한 글자도 바뀌지 않습니다. 평소 TCP에 그대로 쓰던 요청을, TLS가 만들어 준 암호화된 통로에 대신 흘려보낼 뿐입니다. 포트만 80에서 443으로 바뀌고요.

HTTPGET /login · 헤더 · 쿠키 · 본문 — 문법은 그대로
TLS암호화 · 무결성 태그 · 서버 인증 — 09장에서 만든 통로
TCP순서 보장 · 재전송 · 혼잡 제어
IP출발지·목적지 주소로 라우팅

그래서 "HTTPS를 붙인다"는 건 애플리케이션 코드를 고치는 일이 아니라 서버 앞에 TLS 종단점을 두는 일에 가깝습니다. Nginx나 로드밸런서가 TLS를 풀어 주고, 뒤쪽 애플리케이션은 평범한 HTTP를 받죠. 이 구조를 TLS 종단(termination)이라 부르는데, 뒤쪽 구간이 사내망이라고 방심하면 그 구간이 평문으로 남는다는 점은 기억해 둘 만합니다.

"암호화하면 URL도 안 보인다"는 절반만 맞다

제가 오래 헷갈렸던 부분입니다. 암호화된다니 주소창의 모든 게 감춰지는 줄 알았습니다. 실제로는 경로와 쿼리스트링은 감춰지지만, 도메인은 여러 경로로 새어 나갑니다. 직접 확인해 보시죠.

👁️ 도청자는 어디까지 볼 수 있나

💡 위 항목 중 붉은 것은 같은 와이파이의 옆자리 사람도 볼 수 있는 정보입니다. 경로와 파라미터는 안전하지만, "이 사람이 bank.example.com에 접속했다"는 사실 자체는 대체로 드러납니다.

도메인이 새는 통로는 셋입니다. DNS 질의(어느 도메인의 IP를 묻는지 평문으로 오갑니다), 목적지 IP(패킷 헤더는 절대 암호화할 수 없습니다. 그래야 라우팅이 되니까요), 그리고 SNI(09장에서 본, ClientHello에 평문으로 실리는 도메인 이름)입니다.

앞의 둘은 DoH(DNS over HTTPS)와 CDN 공유 IP로 상당 부분 가려집니다. 마지막 SNI를 가리는 게 ECH고요. 셋이 다 갖춰지면 도청자에게는 "이 사람이 어떤 CDN에 접속했다" 정도만 남습니다. 다만 그때도 패킷의 크기와 타이밍은 남습니다. 트래픽 패턴만으로 어떤 영상을 봤는지 추정하는 연구가 있을 정도라, 암호화는 내용을 가릴 뿐 통신했다는 사실까지 지우지는 못합니다.

첫 접속이라는 빈틈

사용자는 주소창에 https://를 또박또박 입력하지 않습니다. bank.com이라고만 치죠. 브라우저는 일단 평문 HTTP로 접속하고, 서버가 301 리다이렉트로 HTTPS로 보냅니다. 그 첫 요청 하나가 평문이라는 게 문제입니다. 중간자가 그 순간 가로채 리다이렉트를 지워 버리면 사용자는 계속 평문으로 통신하게 됩니다. SSL 스트리핑이라 부르는 고전적인 수법이죠.

🛡️ HSTS — "다음부터는 물어보지도 말고 HTTPS로 와라"

서버가 응답 헤더에 Strict-Transport-Security를 실어 보내면, 브라우저는 그 도메인을 목록에 적어 둡니다. 이후로는 사용자가 http://를 입력해도 요청을 보내기 전에 브라우저가 알아서 HTTPS로 바꿉니다. 인증서 오류가 나도 "무시하고 진행" 버튼이 사라지고요.

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

그래도 맨 처음 한 번은 여전히 빈틈입니다. 이걸 없애려면 hstspreload.org에 도메인을 등록해 브라우저 소스코드에 미리 박아 넣는 방법밖에 없습니다. 대신 되돌리기가 매우 어려우니, 모든 서브도메인이 HTTPS를 확실히 지원할 때만 신청하세요.

페이지 하나만 안전해도 소용없다

HTTPS 페이지 안에서 이미지 하나를 http://로 불러오면 어떻게 될까요. 그 이미지 요청은 평문으로 나가고, 중간자가 이미지를 바꿔치기할 수 있습니다. 스크립트라면 더 심각합니다 — 페이지 전체를 장악당하는 거죠. 이걸 혼합 콘텐츠(mixed content)라 하고, 요즘 브라우저는 스크립트·CSS 같은 능동적 리소스는 아예 차단하고 이미지는 자동으로 HTTPS로 승격시키려 시도합니다.

쿠키도 같은 맥락에서 손봐야 합니다. Secure 속성이 없는 쿠키는 평문 HTTP 요청에도 그대로 실려 나갑니다. 사이트 전체가 HTTPS라도, 어쩌다 발생한 평문 요청 하나에 세션 쿠키가 딸려 나가면 그걸로 끝입니다.

Set-Cookie: session=abc123; Secure; HttpOnly; SameSite=Lax; Path=/
#                            │       │         └ 크로스사이트 요청에 쿠키를 붙이지 않음 (CSRF 완화)
#                            │       └ 자바스크립트에서 접근 불가 (XSS로 탈취 방지)
#                            └ HTTPS 연결에서만 전송

🏢 회사 노트북에서 사내 프록시가 통신을 들여다보는 원리

기업 보안 장비는 종종 TLS를 중간에서 풀어 검사합니다. 어떻게 가능할까요. 회사가 자체 루트 CA를 만들어 사원 노트북의 신뢰 저장소에 미리 설치했기 때문입니다. 그러면 프록시가 즉석에서 google.com 인증서를 발급해도 브라우저가 정상으로 받아들이죠. 07장에서 말한 "신뢰의 뿌리는 미리 심어져 있다"의 정확한 응용입니다 — 그 저장소를 통제하는 쪽이 곧 신뢰를 통제합니다. 출처가 불분명한 루트 인증서를 설치하라는 요구를 절대 가볍게 받아들이면 안 되는 이유이기도 합니다.

🧩 안전은 얻었는데 체감이 무겁다

TCP 악수 한 번, TLS 악수 한 번. 여기에 인증서 몇 KB가 오가고, 페이지 하나에 딸린 리소스가 80개쯤 되고요. HTTPS로 바꿨더니 사이트가 느려졌다는 불평이 2010년대 초반에 실제로 많았습니다. 그 느려짐의 정체는 암호화 연산이 아니었습니다. 범인은 다른 곳에 있었고, 11장에서 그 정체가 드러납니다.

✅ 체크포인트
사내 위키에 https://wiki.corp.com/pages/salary?year=2026 로 접속했습니다. 같은 와이파이의 공격자가 알 수 있는 것은?
정답 C. 경로 /pages/salary와 쿼리 ?year=2026은 암호화된 본문 안에 있어 보이지 않습니다. 하지만 DNS 질의·목적지 IP·SNI를 통해 도메인은 드러나요. 그래서 도메인 이름 자체가 민감한 정보라면(예: 특정 질병 상담 사이트) HTTPS만으로는 부족하고 ECH나 DoH 같은 추가 장치가 필요합니다.

🚶 느려진 범인은
암호화 연산이 아니었다 🟢 필수

HTTPS로 바꾸면 느려진다는 말이 한동안 정설처럼 돌았습니다. 저도 CPU가 암호화하느라 바쁜 줄 알았습니다. 측정해 보면 그렇지 않더군요. AES-NI 같은 전용 명령어를 쓰는 요즘 서버에서 대칭키 암·복호화가 차지하는 비용은 1% 안팎입니다. 진짜 범인은 연산이 아니라 기다림이었습니다.

HTTP/1.0은 요청 하나마다 연결을 새로 열었다

초기 웹은 문서 하나를 받아 오면 끝이었습니다. 1996년의 HTTP/1.0은 그 시절에 맞게 요청 하나 → 응답 하나 → 연결 종료였고요. 그런데 웹페이지에 이미지가 붙기 시작합니다. 이미지 30개짜리 페이지라면 TCP 연결을 서른 번 열고 닫아야 했죠. HTTPS라면 여기에 TLS 악수까지 서른 번입니다. 왕복 지연이 곱하기로 늘어납니다.

1997년 HTTP/1.1이 keep-alive를 기본값으로 만들면서 이 부분은 크게 나아졌습니다. 연결 하나를 열어 두고 여러 요청을 재사용하는 거죠. 악수 비용을 한 번만 내면 되니 즉효였습니다. 그런데 새 문제가 따라옵니다.

🚧 한 줄로 서서 기다린다 — HTTP 수준의 HOL 블로킹

연결 하나에서는 요청을 보내고 응답을 다 받아야 다음 요청을 보낼 수 있습니다. 앞의 응답이 느린 API 하나라면, 뒤에 줄 선 CSS와 이미지는 그게 끝날 때까지 아무것도 못 합니다. 은행 창구 하나에 줄을 선 상황과 똑같죠. 앞사람이 오래 걸리면 뒤는 그냥 기다립니다. 이걸 Head-of-Line 블로킹이라 부릅니다.

해결책으로 파이프라이닝이 명세에 들어갔습니다. 응답을 기다리지 않고 요청을 연달아 보내는 방식인데, 응답은 반드시 보낸 순서대로 돌아와야 한다는 제약이 남아 있었습니다. 첫 응답이 느리면 결국 뒤가 막히죠. 중간 프록시들의 구현도 제각각이라 실패하는 경우가 많았고, 결국 모든 브라우저가 기본으로 꺼 버렸습니다. 명세에는 있지만 아무도 안 쓰는 기능으로 남은 겁니다.

그래서 브라우저는 창구를 여섯 개 열었다

줄이 막히면 줄을 여러 개 만들면 됩니다. 브라우저는 같은 출처(origin)당 연결을 6개까지 동시에 엽니다. 숫자가 6인 데 대단한 이유는 없습니다. 경험적으로 정해진 값이고, 더 늘리면 서버와 네트워크에 부담이 커지거든요. HTTPS에서는 이게 TLS 핸드셰이크 6번을 뜻합니다. 아래에서 연결 수를 바꿔 가며 직접 보시죠.

연결을 1개에서 6개로 늘리면 확실히 빨라집니다. 그런데 6개에서 8개로 늘려도 별로 나아지지 않죠. 악수 비용이 연결마다 새로 들고, 각 연결은 느린 시작(slow start) 때문에 처음엔 조금씩만 보내기 때문입니다. 연결을 늘려서 얻는 이득은 금방 한계에 부딪힙니다.

🧰 그 시절의 최적화 기법들

연결 6개라는 벽 안에서 요청 수를 줄이려고 온갖 기법이 동원됐습니다. 아이콘 수십 개를 이미지 한 장에 몰아넣는 스프라이트, JS·CSS를 하나로 합치는 번들링, 작은 이미지를 data: URI로 HTML에 인라인, 그리고 도메인을 여러 개로 쪼개 연결 제한을 우회하는 도메인 샤딩까지. 전부 프로토콜의 한계를 애플리케이션에서 우회하는 임시방편이었습니다. HTTP/2 이후로는 오히려 해가 되는 기법도 있으니, 오래된 빌드 설정을 그대로 쓰고 있다면 한 번 점검해 볼 만합니다.

HTTP/1.1에서 브라우저가 출처당 연결을 6개로 제한하는데, 이걸 20개로 늘리면 항상 빨라질까요?
정답 B. 연결은 공짜가 아닙니다. TCP+TLS 악수, 커널 자원, 각 연결의 혼잡 윈도우가 따로 놀면서 전체 대역폭을 나눠 먹습니다. 병렬성을 늘리는 방향이 아니라, 연결 하나를 잘 쓰는 방향이 옳다는 판단에서 HTTP/2가 나왔습니다.

텍스트를 버리고 프레임을 택했다

HTTP/1.1은 사람이 읽을 수 있는 텍스트였습니다. GET /index.html HTTP/1.1 하고 줄바꿈으로 구분하는 식이죠. 읽기 편하지만 어디서 끝나는지 알려면 끝까지 읽어야 한다는 게 문제입니다. 뒤섞어 보낼 수가 없거든요.

HTTP/2는 모든 걸 프레임이라는 이진 단위로 자릅니다. 각 프레임에는 길이, 종류, 그리고 어느 스트림에 속하는지가 적혀 있습니다. 길이를 미리 알고 소속이 표시돼 있으니, 여러 요청의 프레임을 마음대로 뒤섞어 보내도 받는 쪽이 다시 조립할 수 있습니다. 이게 멀티플렉싱이고, HTTP/2의 거의 전부입니다.

📊 같은 리소스 12개 — HTTP/1.1과 나란히

💡 HTTP/2 쪽은 악수를 한 번만 하고, 12개 요청이 동시에 출발합니다. 대역폭은 나눠 쓰므로 개별 리소스는 조금씩 느려지지만, 전체가 끝나는 시각이 앞당겨집니다.

헤더가 생각보다 무겁다

요청 하나에 붙는 헤더는 보통 수백 바이트에서 1KB를 넘나듭니다. 쿠키, User-Agent, Accept 목록… 문제는 페이지 하나에 요청이 80개면 거의 똑같은 헤더를 80번 반복해서 보낸다는 점입니다. 작은 이미지 요청에서는 헤더가 본문보다 클 때도 있고요.

그래서 HTTP/2는 HPACK이라는 헤더 압축을 씁니다. 자주 쓰는 헤더는 번호표로 대체하고, 한 번 보낸 헤더는 양쪽이 표에 적어 두었다가 다음부터는 인덱스 번호만 보냅니다. user-agent: Mozilla/5.0 (...) 100바이트가 62 한 바이트가 되는 식이죠. 실측에서 헤더 트래픽이 80~90% 줄어듭니다.

🗜️ 왜 gzip이 아니라 HPACK인가

일반 압축을 헤더에 그대로 쓰면 CRIME 공격에 노출됩니다. 공격자가 요청에 추측 문자열을 끼워 넣고 압축 결과의 크기 변화만 관찰해서 쿠키를 한 글자씩 알아내는 수법이었죠. HPACK은 정적 테이블과 허프만 부호화를 조합해 이 위험을 피하도록 다시 설계한 방식입니다. 08장의 "TLS 1.3이 압축을 삭제한 이유"와 같은 뿌리에서 나온 대응입니다.

실패한 기능도 있었다 🔵 심화

HTTP/2에는 서버 푸시가 있었습니다. HTML을 요청받은 서버가 "어차피 CSS도 필요할 테니 미리 보내 준다"는 기능이었죠. 아이디어는 좋았지만 실전에서는 이미 브라우저 캐시에 있는 파일을 또 보내는 낭비가 잦았고, 제어도 까다로웠습니다. 결국 크롬이 2022년에 기본 비활성화했고, 지금은 사실상 사라진 기능이죠. 대신 103 Early Hints로 "이것들을 미리 받아 두면 좋겠다"고 힌트만 주는 방식이 자리를 잡았습니다.

우선순위(priority) 기능도 비슷했습니다. 명세는 복잡했는데 구현이 제각각이라 기대만큼 동작하지 않았고, 결국 단순한 방식으로 재설계됐습니다. 프로토콜에 넣었다고 다 쓰이는 건 아니라는 사례로 기억해 둘 만합니다.

🔗 HTTP/2는 왜 사실상 HTTPS 전용인가

명세상으로는 평문 HTTP/2(h2c)도 있습니다. 그런데 어떤 브라우저도 지원하지 않습니다. 이유는 현실적입니다 — 중간의 낡은 프록시들이 알 수 없는 이진 데이터를 보고 연결을 끊어 버리거든요. TLS 안에 넣으면 중간 장비가 내용을 볼 수 없으니 간섭도 못 합니다. 09장의 ALPN으로 협상까지 깔끔하게 되고요. 결과적으로 "HTTP/2를 쓰고 싶으면 HTTPS를 켜라"가 됐습니다. HTTPS 보급률이 급등한 데는 이 실용적인 압력도 한몫했습니다.

🧩 그런데 아직 한 군데가 막힌다

스트림은 논리적으로 완전히 독립됐습니다. 그런데 그 아래 TCP는 여전히 순서가 보장된 바이트 하나의 흐름일 뿐입니다. 중간에 패킷 하나가 유실되면 TCP는 그게 도착할 때까지 그 뒤의 모든 데이터를 애플리케이션에 넘기지 않습니다. 스트림 1의 패킷이 빠졌다는 이유로, 이미 도착해 있는 스트림 3·5의 데이터까지 커널 버퍼에 묶여 대기하죠. HOL 블로킹을 HTTP 층에서 걷어냈더니 TCP 층에 그대로 남아 있었습니다.

HTTP/2로 전환한 뒤에도 유지할 가치가 있는 옛 최적화는 무엇일까요?
정답 A. 도메인 샤딩은 해롭습니다. HTTP/2의 장점은 연결 하나에 몰아넣는 데서 나오는데, 도메인을 쪼개면 연결이 다시 늘어나고 압축 테이블도 공유되지 않습니다. 과도한 번들링도 파일 하나만 바뀌어도 전체가 캐시 무효화되니 손해고요. 반면 바이트를 줄이는 최적화는 프로토콜과 무관하게 항상 유효합니다.

🚀 TCP를 고칠 수 없다면,
TCP를 쓰지 않으면 된다 🟢 필수

TCP의 순서 보장이 문제라면 TCP를 고치면 될 것 같습니다. 그런데 그럴 수가 없습니다. TCP는 운영체제 커널 안에 있고, 전 세계 라우터·방화벽·공유기가 그 동작에 맞춰져 있거든요. 새 기능을 넣어도 모든 기기가 업데이트되기까지 10년이 걸립니다. 실제로 그런 시도가 여러 번 좌초했고요.

구글의 선택은 우회였습니다. UDP 위에 새 전송 프로토콜을 처음부터 다시 만든다. UDP는 "받는 쪽에 던진다"는 것 말고는 아무 규칙이 없어서 중간 장비가 간섭하지 않습니다. 필요한 기능은 전부 애플리케이션 영역에서 구현하면 되고요. 그렇게 나온 것이 QUIC이고, 그 위에 HTTP를 얹은 게 HTTP/3(RFC 9114, 2022)입니다.

QUIC이 한 번에 해결한 것들

  • 스트림별 독립 손실 복구 — 스트림 1의 패킷이 빠져도 스트림 3·5는 그대로 전달됩니다. TCP HOL 블로킹이 사라집니다.
  • 악수의 통합 — TCP 악수와 TLS 악수를 하나로 합쳤습니다. 연결과 암호화가 동시에 완료되어 첫 접속이 1왕복, 재접속은 0왕복입니다.
  • 연결 마이그레이션 — 연결을 IP·포트가 아니라 Connection ID로 식별합니다. 지하철에서 와이파이가 끊겨 LTE로 바뀌어도 연결이 그대로 유지됩니다. TCP였다면 끊기고 처음부터 다시 맺어야 했죠.
  • 더 나은 손실 복구 — 재전송 패킷에 새 번호를 붙여, 응답이 원본에 대한 것인지 재전송에 대한 것인지 명확히 구분합니다. TCP의 오래된 모호함 하나가 해소됩니다.
  • 암호화 범위 확대 — TCP는 헤더가 평문이라 중간 장비가 들여다보고 조작했지만, QUIC은 대부분의 헤더까지 암호화합니다.

헤더 압축도 QPACK으로 바뀝니다. HPACK은 "헤더를 보낸 순서대로 처리한다"를 전제로 하는데, 스트림이 순서 없이 도착하는 QUIC에서는 그 전제가 깨지거든요. 순서에 의존하지 않도록 다시 설계한 것이 QPACK입니다.

💡 손실률 0%에서는 HTTP/2와 3의 차이가 크지 않습니다. 손실을 2~3%로 올려 보세요. HTTP/2는 하나의 손실이 전체를 멈춰 세우지만, HTTP/3는 해당 스트림만 잠깐 멈추고 나머지는 계속 흐릅니다.

브라우저는 HTTP/3를 어떻게 알아내나

주소창에 https://를 치는 순간에는 서버가 HTTP/3를 지원하는지 알 수 없습니다. UDP로 먼저 찔러 봤다가 실패하면 시간만 버리고요. 그래서 순서는 이렇습니다. 먼저 평소처럼 TCP + TLS로 접속하면, 서버가 응답에 이런 헤더를 붙입니다.

Alt-Svc: h3=":443"; ma=86400
#        │            └ 이 정보를 24시간 기억해 두라
#        └ 나는 같은 443 포트에서 HTTP/3(QUIC)도 받는다

브라우저는 이걸 기억해 두었다가 다음 접속부터 QUIC을 시도합니다. 요즘은 DNS의 HTTPS 레코드로 처음부터 알려 주는 방식도 쓰이고요. 어느 쪽이든 실패하면 조용히 TCP로 되돌아가므로, 사용자가 눈치챌 일은 없습니다.

🚧 현실의 제약

UDP를 막아 놓은 기업 방화벽이 아직 많습니다. 그런 환경에서는 HTTP/3 시도가 실패하고 TCP로 되돌아가죠. 그리고 QUIC은 커널이 아닌 사용자 영역에서 돌기 때문에 같은 트래픽을 처리할 때 CPU를 더 씁니다. 대형 서비스에서는 이 비용이 유의미해서, 커널 오프로딩 같은 최적화가 계속 나오고 있습니다. 모든 상황에서 HTTP/3가 빠른 건 아닙니다 — 손실이 거의 없는 유선 환경에서는 HTTP/2와 차이가 미미하고, 이득은 모바일·불안정 회선에서 큽니다.

🛠️ 내 서버에서는
무엇을 켜고 무엇을 끄나 🟢 필수

원리를 다 쌓고 나면 남는 질문은 하나입니다. 그래서 내 서버의 설정 파일에는 결국 무엇을 적어야 하나? 좋은 소식은 외울 게 별로 없다는 겁니다. 08장에서 얻은 원칙 하나 — 약한 선택지를 끈다 — 만 지키면 대부분 해결되거든요.

Nginx 설정, 한 줄씩

server {
    listen 443 ssl;
    listen 443 quic reuseport;              # HTTP/3 (nginx 1.25+)
    http2 on;
    server_name example.com;

    # ── 인증서: fullchain(리프+중간)을 써야 07장의 체인 누락을 피한다 ──
    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    # ── 버전: 1.0/1.1은 켜지 않는다 ──
    ssl_protocols TLSv1.2 TLSv1.3;

    # ── 1.2에서 쓸 암호: ECDHE(전방향 비밀성) + GCM(AEAD)만 남긴다 ──
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-CHACHA20-POLY1305;
    ssl_prefer_server_ciphers off;          # 1.3에서는 클라이언트 선호를 존중하는 편이 낫다

    # ── 재접속 비용 절감 ──
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;
    ssl_session_tickets off;                # 티켓 키를 안전히 순환할 자신이 없다면 끄는 쪽이 안전

    # ── OCSP 스테이플링(07장) ──
    ssl_stapling on;
    ssl_stapling_verify on;

    # ── HSTS(10장): 사이트 전체가 HTTPS인 것을 확인한 뒤 켤 것 ──
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header Alt-Svc 'h3=":443"; ma=86400' always;   # HTTP/3가 있다고 알리기(13장)
}

server {                                     # 평문으로 들어온 요청은 곧장 올려 보낸다
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

서버만 증명하는 게 아니라면 — mTLS 🔵 심화

지금까지 인증은 한 방향이었습니다. 서버가 자기 신원을 증명하고, 클라이언트는 익명이었죠. 웹에서는 그게 맞습니다. 사용자 인증은 로그인이 담당하니까요. 그런데 서버끼리 통신하는 상황이라면 이야기가 다릅니다. 마이크로서비스 A가 B를 부를 때, B는 상대가 정말 A인지 알고 싶어 하죠.

mTLS(상호 TLS)는 핸드셰이크 중에 서버가 클라이언트에게도 인증서를 요구합니다. 양쪽 다 인증서를 내고, 양쪽 다 검증하죠. 06·07장의 구조가 그대로 반대 방향으로 한 번 더 적용될 뿐, 새로운 개념은 없습니다. 서비스 메시(Istio, Linkerd)가 내부 통신에 기본으로 거는 게 이거고요. 비밀번호나 API 키와 달리 개인키가 네트워크를 오가지 않는다는 게 강점입니다.

❌ 자물쇠가 보증하지 않는 것

그 사이트가 선량하다는 것.
피싱 사이트도 Let's Encrypt에서 무료로 인증서를 받습니다. gοogle.com(o가 그리스 문자)의 주인도 그 도메인의 통제권을 증명할 수 있으니, 자물쇠는 당당히 뜹니다. 자물쇠는 "당신이 보고 있는 그 도메인과 안전하게 연결됐다"고 말할 뿐, 그 도메인이 당신이 의도한 곳인지는 말해 주지 않습니다.

04장에서 "지금 저장해 두고 나중에 해독한다"는 공격을 이야기했습니다. 그때는 개인키 유출을 가정했죠. 그런데 충분히 큰 양자컴퓨터가 나오면 이야기가 달라집니다. 쇼어 알고리즘은 소인수분해와 이산 로그를 다항 시간에 풉니다. RSA와 타원곡선이 딛고 선 두 개의 벽이 동시에 무너진다는 뜻입니다. 대칭키(AES)는 키 길이를 두 배로 늘리면 버티지만, 공개키 암호는 통째로 갈아야 합니다.

그래서 이미 움직이고 있습니다. 미국 표준기술연구소가 2024년에 ML-KEM(구 Kyber)을 격자 기반 표준으로 확정했고, 크롬과 클라우드플레어는 X25519MLKEM768이라는 하이브리드 방식을 이미 기본으로 켜 두었습니다. 기존 타원곡선과 새 알고리즘을 둘 다 써서 공유 비밀을 만드는 방식이죠. 어느 한쪽이 깨져도 나머지가 버티도록요. 오늘 당신의 브라우저가 어떤 사이트에 접속할 때, 그 핸드셰이크에는 이미 양자내성 알고리즘이 섞여 있을 가능성이 높습니다.

서두르는 이유는 단순합니다. 양자컴퓨터가 내일 나오지 않더라도, 오늘 오간 트래픽을 지금 녹화해 두었다가 10년 뒤에 푸는 일은 오늘부터 가능하기 때문입니다. 10년 뒤에도 비밀이어야 할 데이터를 다루고 있다면, 그 문제는 미래의 일이 아닙니다.

# ── 인증서 만들기 ──────────────────────────────
openssl genrsa -out private.key 2048                    # RSA 키 생성
openssl ecparam -genkey -name prime256v1 -out ec.key     # 타원곡선 키 (더 가볍다)
openssl req -new -key private.key -out request.csr       # CSR 만들기
openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout dev.key -out dev.crt \
  -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"    # 개발용 자체 서명 (SAN 필수!)

# ── 인증서 들여다보기 ───────────────────────────
openssl x509 -in cert.pem -noout -text                   # 전체 필드
openssl x509 -in cert.pem -noout -subject -issuer -dates # 요약 3줄
openssl x509 -in cert.pem -noout -fingerprint -sha256    # 지문
openssl verify -CAfile chain.pem cert.pem                # 체인 검증

# ── 키와 인증서가 짝인지 확인 (배포 사고 1순위) ──
openssl x509 -noout -modulus -in cert.pem | openssl md5
openssl rsa  -noout -modulus -in private.key | openssl md5   # 두 값이 같아야 한다

# ── 형식 변환 ──────────────────────────────────
openssl x509 -inform DER -in cert.der -out cert.pem       # DER(이진) → PEM(텍스트)
openssl pkcs12 -export -out bundle.p12 -inkey key.pem -in cert.pem  # 윈도우·자바용 묶음

📁 파일 확장자 정리

.pem — Base64 텍스트. -----BEGIN CERTIFICATE-----로 시작합니다. 가장 흔한 형식이고요.
.der — 같은 내용의 이진 형태. 자바와 윈도우 계열에서 자주 보입니다.
.crt / .cer — 보통 인증서. 내용은 PEM일 수도 DER일 수도 있으니 열어 봐야 압니다.
.key — 개인키. 절대 저장소에 커밋하지 마세요.
fullchain.pem — 리프 + 중간 인증서를 이어 붙인 것. 서버에는 이걸 지정합니다.
.p12 / .pfx — 인증서와 개인키를 비밀번호로 묶은 꾸러미.
