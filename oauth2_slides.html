배우는 다섯입니다 — 이름은 딱딱해도 하는 일은 단순해요

  • 👤 사용자 Resource Owner — 권한의 주인
  • 🌐 브라우저 User-Agent — 사용자와 서버 사이를 오가는 통로
  • 📱 클라이언트 Client — 권한을 빌려 쓰려는 앱
  • 🔐 인증 서버 Authorization Server — 신원을 확인하고 토큰을 발급
  • 📦 API 서버 Resource Server — 토큰을 검사하고 데이터를 내줌

용어를 외우는 대신, 배우 사이에 그어진 선을 보세요

비밀번호가 지나는 선은 이 그림에 딱 하나뿐입니다

사용자 → 브라우저 → 인증 서버 — 클라이언트는 이 선 위에 없다

그래서 앱 서버가 통째로 털려도 비밀번호는 그 안에 없습니다

토큰은 "이미 확인받았다"는 증표입니다

access_token = 입장 팔찌 — 한 번 확인받고 나면, 안에서는 팔찌만

Bearer = 지참인. 주운 사람도 쓸 수 있다

같은 요청인데, 토큰의 모양 하나로 검증하는 자리가 달라진다

같은 자리에 두 가지 모양이 옵니다

Opaque

뜻이 없는 문자열. API 서버는 발급한 인증 서버에 introspection으로 물어봐야 압니다 — 호출마다 왕복 +1

JWT

필요한 내용이 서명과 함께 토큰 안에 적혀 있습니다. 나갈 곳 없이 그 자리에서 서명만 검사해요

JWT가 없앤 왕복은, 곧 즉시 끊을 자리이기도 합니다

그래서 JWT 는 수명을 짧게 잡습니다 — 만료 시간이 곧 "폐기가 반영되기까지"

둘 중 무엇이 낫다가 아니라, 무엇과 무엇을 맞바꿨나

여기까지가 배우와 소품입니다 — 이제 한 바퀴 돌려 봅니다

여기부터 열여섯 단계 — 새 개념은 없습니다. 방금 본 다섯이 순서대로 말을 주고받을 뿐입니다

로그인 버튼 한 번에 일어나는 열여섯 단계

코드가 주소창으로 돌아오는데, 왜 훔쳐도 토큰을 못 받을까요?

정답은 A. code 자체는 '교환권'에 불과합니다. 토큰으로 바꾸려면 백채널에서 code_verifier와 클라이언트 인증이 더 필요하죠.

코드가 노출된 통로로 오는 것은 사고가 아니라 설계입니다 — 노출돼도 그것만으로는 못 쓰게 만들어 두었으니까요.

로그인 버튼이 하는 일은, 사실 URL 하나를 만드는 것입니다

앱은 브라우저를 인증 서버로 보냅니다 — 그 주소에 실린 파라미터 하나하나가 보안의 핵심입니다

scope 를 켜고 끄면 URL 이 이렇게 달라집니다

🛠 Authorization URL 빌더

요청할 권한(scope) 고르기




🔒 auth.example.com/oauth/authorize

      

    

  

  

    
URL 에 실리는 여섯, 각자 맡은 일이 다릅니다

    
    
      
  • response_type=code — "코드 방식으로 줘". 요즘 표준입니다
    • 
      
  • redirect_uri — 끝나면 돌아올 주소. 미리 등록된 값과 정확히 일치할 때만 허용
    • 
      
  • scope — 요청하는 권한 목록. 동의 화면에 그대로 보입니다
    • 
      
  • state — 위조 방지용 일회성 난수
    • 
      
  • nonce — 뒤에서 볼 id_token을 지키는 일회성 값
    • 
      
  • code_challenge — 아홉 장 뒤 PKCE 가 쓸 자물쇠

지금 비밀번호를 넣는 이 화면, 누가 그린 걸까요?

    
주소창을 보세요 — accounts.google.com. 앱이 아니라 인증 서버가 만들어 보낸 화면입니다.

    
그래서 비밀번호가 앱으로 샐 길이 없습니다. 앱 안에 로그인 폼을 그리는 순간, 이 성질이 통째로 사라집니다.

돌아오는 건 토큰이 아니라 authorization code입니다

    
    
code = 번호표

    
수명이 짧고, 그것만으로는 아무것도 열지 못합니다

보낸 도장과 돌아온 도장이 다르면, 그 요청은 버립니다

    
요청을 보낼 때 만든 임의의 state를 세션에 저장해 두고, 콜백으로 돌아온 값과 대조합니다.

    
다르면 다른 흐름의 응답이거나 CSRF 공격입니다. 조건 없이 즉시 중단하세요.

그런데 공격자가 그 code를 통째로 훔쳤다면요?

    
    
표준은 코드를 숨기는 대신, 훔쳐도 못 쓰게 만드는 쪽을 골랐습니다.

  

  

    
PKCE — 코드의 주인을 지킨다

    
  

  

    
열쇠 원본이 없으면, 훔친 코드는 종잇조각이 됩니다

    

      
🧪 직접 해보기 — 실제 SHA-256 해싱

      
      

        
        
      

      

      
    

  

  

    
기준은 하나입니다 — client_secret을 숨길 수 있나

    
    
숨길 수 있다 — 서버 앱 · confidential　　못 숨긴다 — SPA · 모바일 · CLI · public

    
못 숨기는 쪽은 그 자리를 PKCE 로 메웁니다 → 플랫폼별 선택은 부록 B

  

  

    
code는 훔쳤지만 code_verifier는 모릅니다. 교환의 결과는?

    

      
      
      
      
정답은 A. PKCE는 client_secret을 숨길 수 없는 SPA·모바일(public client)에 필수이고, 요즘은 서버 앱에서도 함께 쓰는 것이 권장됩니다.

    

    
PKCE가 지키는 것은 코드가 아니라 코드의 주인입니다.

  

  

    
지금까지 오간 값은 두 종류의 통로를 지났습니다

    
┄ 프론트채널 — 브라우저(주소창)를 거칩니다. 사용자에게 보이고, 가로채일 수도 있는 노출된 통로.

    
━ 백채널 — 서버끼리 직접 주고받습니다. 이 줄에는 브라우저가 아예 없습니다.

  

  

    
가르는 기준은 하나 — 브라우저가 그 줄에 있느냐

    
  

  

    
백채널을 통과하면 비로소 진짜 토큰이 돌아옵니다

    
{
  "access_token": "at_eyJh...",   // API 호출용
  "token_type": "Bearer",
  "expires_in": 3600,            // 1시간 뒤 만료
  "refresh_token": "rt_8xM...",   // 재발급용
  "id_token": "eyJhbGc..."      // 누구인지(OIDC)
}

    
셋이 한꺼번에 옵니다. 그중 access_token 하나를 어떻게 실어 보내느냐부터 봅니다.

  

  

    
토큰은 헤더로만 보냅니다 — URL에 넣는 순간 기록에 남습니다

    
GET /invoices HTTP/1.1
Host: api.example.com
Authorization: Bearer at_eyJhbGciOiJSUzI1NiJ9...

    
가진 사람이 곧 권한자입니다. 쿼리스트링·서버 로그·콘솔에 한 번 흘리면 그 자리에서 끝나요.

로그인할 '사람'이 없는 호출은 이 흐름이 통째로 필요 없습니다

    
    
배치 · 마이크로서비스 · CI/CD — 동의 화면도, id_token 도, redirect 도 없다

여기까지 왔는데도, 아직 '누가 로그인했는지'는 모릅니다

그 답을 주려고 OAuth2 위에 신원 계층을 얹은 것이 OIDC입니다.

"id_token을 디코딩해서 그 사람으로 로그인시키자" — 무엇이 문제일까요?

    

      
      
      
      
정답은 B. JWT의 payload는 그냥 base64라 아무나 만들 수 있습니다. 그 위조를 잡아내는 서명 검증이 신뢰의 전부예요.

    

    
디코딩은 읽는 일이고 검증은 믿어도 되는지 따지는 일입니다. 둘은 다릅니다.

  

  

    
사고는 늘 같은 다섯 자리에서 납니다

    
    
      
  • access_token으로 로그인 판단 → 로그인 여부는 반드시 id_token으로
    • 
      
  • id_token을 API로 전송 → API에는 access_token만
    • 
      
  • JWT를 디코딩만 하고 신뢰 → 서명·iss·aud·exp 검증은 생략 불가
    • 
      
  • state·nonce 생략 → CSRF와 재생 공격에 그대로 노출
    • 
      
  • 토큰을 URL·로그에 노출, 과도한 scope 요청, secret을 코드에 커밋
    • 
    

  

  

    
저장 위치는 피해 범위를 정할 뿐, XSS를 없애지 않습니다

claude login 은 콜백을 어디로 받을까요?

    
CLI 에는 redirect_uri 를 받아 줄 웹서버가 없습니다. 그래서 자기 안에 하나를 잠깐 띄웁니다.

    
① 비어 있는 포트를 하나 잡는다        → 127.0.0.1:53219
② 그 주소를 redirect_uri 로 적어 인가 요청을 만든다
③ 시스템 브라우저를 연다               → 로그인 · 동의
④ 브라우저가 127.0.0.1:53219/callback?code=… 로 돌아온다
⑤ 코드를 받은 그 자리에서 로컬 서버를 닫는다

    
포트를 고정하지 않는 것이 요점입니다. 그래서 인증 서버는 루프백 주소에 한해서만 포트를 뺀 일치를 허용합니다.

  

  

    
CLI 로그인은 웹 로그인과 같은 흐름입니다 — 콜백 주소만 다릅니다

    

  

  

    
브라우저조차 못 띄우는 기기는, 입력을 폰으로 넘깁니다

🧭 플랫폼별 설계 탐색기

      

        
        
        
        
      

      

    

  

  

    
public 클라이언트는 secret 을 버리고, 그 자리를 PKCE 로 메웁니다

    
    
      
  • secret 이 하던 일 — "이 토큰 요청을 보낸 것이 그 인가 요청의 주인이 맞다"를 증명
    • 
      
  • public 에서는 못 한다 — 배포된 코드에 박은 값은 누구나 꺼낼 수 있으니 증명이 안 됩니다
    • 
      
  • PKCE 가 대신한다 — 흐름마다 새로 만드는 code_verifier 는 앱 메모리에만 있습니다
    • 
      
  • 그래서 성질이 다릅니다 — secret 은 오래 사는 하나, verifier 는 한 번 쓰고 버리는 값
    • 
    

    
새는 순간의 피해가 다릅니다. secret 이 새면 그 클라이언트가 통째로 털리고, verifier 가 새면 그 흐름 하나가 끝납니다.

  

  

    
사람이 없는 호출은, 서비스가 자기 자격으로 토큰을 받습니다

    

  

  

    
머신 토큰 세 가지는, 주체가 누구냐로 갈립니다

    
    
      
  • Client Credentials — 주체는 service:billing-worker. OAuth2 표준 grant 이고, 동의 화면도 id_token 도 없습니다
    • 
      
  • Service token — 제품이 발급하는 서비스용 토큰. 저장소·환경 단위로 scope 를 끊고 만료를 답니다
    • 
      
  • PAT — 주체가 사람 계정입니다. 그래서 그 사람이 가진 권한을 그대로 물려받습니다
    • 
    

    
운영 서비스의 기본값은 앞의 둘입니다. PAT 는 로컬 스크립트까지가 자리예요.

  

  

    
PAT 가 위험한 이유는, 그것이 사람의 권한이기 때문입니다

    
    
      
  • 권한이 과합니다 — 그 사람이 들어갈 수 있는 저장소 전부에 들어갑니다. 필요한 하나가 아니라요
    • 
      
  • 퇴사하면 멈춥니다 — 계정이 닫히는 순간 그 토큰을 쓰던 배치도 같이 죽습니다
    • 
      
  • 잘 샙니다 — 커밋 기록, 로그, 스크린샷. 사고 보고서에 가장 자주 나오는 이름입니다
    • 
      
  • 추적이 흐려집니다 — 감사 로그에는 사람 이름이 남습니다. 실제로 부른 것은 배치인데요
    • 
    

    
그래도 써야 한다면 fine-grained · 만료일 · 최소 scope · secret manager 넷을 함께 겁니다.

발표에서 내지 못한 문제 다섯 — 앞쪽 절반을 되짚습니다

    

      
① OAuth2가 풀려는 가장 근본적인 문제는?

      
      
      
      
정답은 B. OAuth2는 암호화 알고리즘이 아니라 권한을 빌려주는 약속입니다. "전부 아니면 전무"를 "딱 필요한 만큼"으로 바꿔 줍니다.

    

    

      
② access_token이 유효한지, scope가 충분한지를 최종 판단하는 쪽은?

      
      
      
      
정답은 C. 발급은 인증 서버가 하지만, 요청마다 유효성·scope·만료·대상을 검증해 데이터를 줄지 정하는 쪽은 API 서버입니다.

    

    

      
③ 공격자가 redirect_uri를 자기 사이트로 바꿔 코드를 가로채려 합니다. 1차 방어선은?

      
      
      
      
정답은 B. 인증 서버는 등록해 둔 목록과 완전 일치할 때만 코드를 보냅니다. 부분 일치는 허용하지 않습니다.

    

    

      
④ 콜백으로 돌아온 state가 세션에 저장해 둔 값과 다르면?

      
      
      
      
정답은 C. state 검증은 CSRF와 응답 섞임을 막는 기본 방어선입니다. 불일치하면 무조건 중단하세요.

    

    

      
⑤ rotation 중에 공격자가 훔친 '옛' refresh token을 쓰면, 무엇이 가장 바람직한가?

      
      
      
      
정답은 B. 한 번 쓴 토큰이 또 들어오면 "유출됐다"는 신호입니다. 체인을 통째로 끊어 둘 다 로그아웃시키고 재로그인을 시킵니다.

    

  

  

    
남은 문제 넷 — OIDC 와 머신 인증을 되짚습니다

    

      
⑥ 공개된 jwks_uri의 키로 id_token 서명을 검증할 수 있는데, 왜 위조는 못 할까요?

      
      
      
      
정답은 B. 비대칭 서명은 생성=비공개키, 검증=공개키로 역할이 나뉩니다. 그래서 JWKS가 공개돼도 위조는 불가능합니다.

    

    

      
⑦ CLI 도구는 왜 client_secret 없이도 비교적 안전하게 토큰을 받을까요?

      
      
      
      
정답은 B. 배포된 CLI에 박은 secret은 비밀이 아닙니다. 그래서 앱만 쥐고 있는 code_verifier가 그 자리를 대신합니다.

    

    

      
⑧ 운영 백엔드가 매시간 billing API를 자기 권한으로 호출해야 합니다. 가장 적절한 선택은?

      
      
      
      
정답은 C. 사람이 없는 호출은 서비스 자신을 주체로 삼습니다. A는 사람 의존·과권한, B는 id_token을 API에 쓰는 흔한 오용입니다.

    

    

      
⑨ access_token · id_token · PAT를 가장 정확히 설명한 것은?

      
      
      
      
정답은 A. 토큰은 주체 · 소비자 · 용도 셋으로 갈립니다. 그 셋을 구분하는 순간 설계가 또렷해집니다.
