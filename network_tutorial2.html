🖥️ EchoServer.java

서버
import java.io.*;
import java.net.*;

public class EchoServer {
    public static void main(String[] args) throws IOException {
        // socket() + bind() + listen() 이 한 줄에 다 들어 있다
        ServerSocket server = new ServerSocket(8080);
        System.out.println("Started on port 8080");

        while (true) {
            Socket conn = server.accept();   // accept(): 손님 하나. 없으면 블록
            new Thread(() -> handle(conn)).start();  // 연결마다 워커+fd
        }
    }

    static void handle(Socket conn) {
        try (conn;
             var in  = new BufferedReader(
                 new InputStreamReader(conn.getInputStream()));
             var out = conn.getOutputStream()) {

            String requestLine = in.readLine();   // "GET /hello HTTP/1.1"
            System.out.println("요청: " + requestLine);
            String h;                              // 나머지 헤더는 빈 줄까지
            while ((h = in.readLine()) != null && !h.isEmpty()) { }

            String body = "Hello from EchoServer\n";
            String res =
                "HTTP/1.1 200 OK\r\n" +
                "Content-Type: text/plain\r\n" +
                "Content-Length: " + body.getBytes().length + "\r\n" +
                "\r\n" + body;
            out.write(res.getBytes());   // write(): 송신 버퍼로
            out.flush();
        } catch (IOException e) { e.printStackTrace(); }
    }
}

import java.io.*;
import java.net.*;

public class EchoClient {
    public static void main(String[] args) throws IOException {
        // socket() + connect(): 서버에 연결.
        // 이때 OS가 클라 임시 포트를 자동 배정한다
        try (Socket sock = new Socket("127.0.0.1", 8080);
             var out = sock.getOutputStream();
             var in  = new BufferedReader(
                 new InputStreamReader(sock.getInputStream()))) {

            String req =
                "GET /hello HTTP/1.1\r\n" +
                "Host: localhost:8080\r\n" +
                "Connection: close\r\n" +
                "\r\n";
            out.write(req.getBytes());   // 요청 한 덩이를 써 보낸다
            out.flush();

            String line;
            while ((line = in.readLine()) != null) {  // 응답 끝까지
                System.out.println(line);
            }
        }
    }
}

01 · 서버 머신의 내부

🧩 서버가 8080을 여는 순간

tomcat을 띄우면 콘솔에 Started on port 8080 한 줄이 뜹니다. 익숙하죠. 그런데 "그 한 줄이 커널 안에서 실제로 무슨 일을 벌이느냐"를 설명해 보라면 말문이 막히는 분이 많아요.

이게 사소한 빈틈이 아닙니다. 앞으로 볼 HTTP·TLS·프락시·로드밸런싱 — 전부 "서버가 포트를 열고 연결을 받는다"는 이 토대 위에 서 있거든요. 토대가 흐릿하면 그 위가 다 흔들립니다. 그래서 이 장은 서두르지 않고, "포트를 연다"는 말의 실체를 시스템콜 → 큐 → 버퍼 순서로 천천히 쌓아 올립니다. Tutorial ①의 소켓·fd를 한 단계 더 깊이 파는 셈이에요.

먼저, 앱은 네트워크를 직접 만지지 못한다

방금 본 코드의 첫 줄로 시작합시다. new ServerSocket(8080) 한 줄이면 서버가 열렸죠. 그런데 이 자바 코드가 정말로 랜카드한테 직접 "8080 들어오면 나한테 줘"라고 명령하는 걸까요? 아닙니다. 그리고 그 "아니다"가 이 장 전체의 출발점이에요.

왜 직접 못 만질까. 컴퓨터 한 대엔 tomcat만 도는 게 아니죠. 크롬, 다른 자바 프로세스, OS 백그라운드 작업 수십 개가 같은 랜카드 하나, 같은 메모리를 나눠 씁니다. 만약 아무 프로그램이나 랜카드를 직접 주무를 수 있다면, tomcat의 사소한 버그 하나가 옆 프로세스의 통신을 망가뜨리고 시스템 전체를 내려버릴 수 있어요. 그래서 OS는 아예 선을 하나 긋습니다.

그 선이 바로 유저 공간과 커널 공간입니다. 하드웨어(랜카드·디스크·메모리)에 실제로 손대는 일은 커널(OS의 핵심부)만 할 수 있게 막아둡니다. tomcat 같은 보통 프로그램은 그 바깥, 유저 공간에서만 돌고요. 비유하자면 커널은 은행 금고 안에서 일하는 직원이고, 앱은 창구 밖의 손님이에요. 손님은 금고에 직접 못 들어가고, 창구에 요청서를 내밀 뿐입니다.

그 요청서가 바로 시스템콜입니다. "소켓 하나 만들어 줘", "이 포트로 오는 거 나한테 줘", "데이터 왔으면 읽어 줘" — 앱이 커널에 넣는 이런 공식 요청이 socket()·bind()·read() 같은 시스템콜입니다. 그러니 new ServerSocket(8080)도 속을 까보면, 결국 이 시스템콜들을 대신 호출해 주는 것뿐이에요.

🔑 그래서 잡고 갈 결론 하나

"소켓"은 자바 객체가 아니라 사실 커널 안에 있는 객체입니다. 앱이 손에 쥔 건 그 객체를 가리키는 번호표 하나, 바로 파일 디스크립터(fd)예요. 이 한 문장을 잡고 가면, 잠시 뒤 "포트를 연다"가 왜 커널 테이블에 등록하는 일인지 자연스럽게 이어집니다.

"8080을 연다"를 네 걸음으로 쪼개기

앞에서 "앱은 시스템콜로 부탁만 한다"고 했죠. 그럼 서버를 여는 데는 정확히 어떤 부탁들이 필요할까요? 손님 받을 가게를 차린다고 생각하면 순서가 자연스럽게 나옵니다.

  1. 전화기를 산다 → socket(): 통신할 도구(소켓)를 하나 만들어 달라.
  2. 전화번호를 받는다 → bind(): "8080번은 내 거"라고 커널에 등록해 달라.
  3. "영업 중" 팻말을 건다 → listen(): 이제 손님(연결) 받을 테니 대기 줄을 만들어 달라.
  4. 손님을 맞는다 → accept(): 줄 선 손님을 하나 데려와 달라.

네 걸음 모두 커널에 넣는 부탁(시스템콜)이라는 점이 핵심입니다. 아래에서 한 걸음씩 누르며, 각 부탁이 커널 내부 상태(fd 테이블·포트 테이블·대기 큐)를 어떻게 바꾸는지 직접 보세요. 오른쪽이 커널의 머릿속입니다.

🎬 시작 전

그래서 "포트를 연다"가 정확히 뭐였나

"포트를 연다"는 말을 들으면 뭔가 물리적인 문을 여는 느낌이 들지만, 실제로는 훨씬 사무적입니다. bind(8080)은 커널이 들고 있는 포트 → 소켓 매핑 장부에 "TCP 8080번으로 들어오는 건 이 소켓(fd)에게 배달해"라고 한 줄 등록하는 일이에요. 문을 여는 게 아니라, 우편함에 이름표를 붙이는 것에 가깝습니다.

이 "장부에 한 줄" 관점을 잡으면 그동안 외우던 규칙들이 전부 당연해집니다.

🔑 장부 한 줄로 설명되는 것들

  • 왜 포트 충돌이 나나 — 장부의 8080 칸엔 주인을 하나만 적을 수 있어요. 이미 누가 적혀 있으면 등록 거부 → EADDRINUSE(Address already in use). 위 데모의 충돌 체크가 이걸 보여줍니다.
  • 왜 80·443은 권한이 필요한가 — 1024 미만(특권 포트)은 아무나 못 적게 막아뒀습니다(root 권한 필요). 그래서 tomcat을 8080에 띄우는 거예요.
  • listen 다음은? — 등록만으론 부족하고, "이제 받을게"라고 LISTEN 상태로 바꿔야 커널이 손님을 줄 세우기 시작합니다. 그 줄 이야기가 이 장 뒤에서 나와요.

이번엔 반대 방향 — 도착한 패킷이 내 코드까지

지금까지는 서버가 받을 준비를 하는 쪽이었죠. 이제 실제로 클라이언트가 보낸 패킷 하나가 도착했다고 합시다. 그 패킷이 read()로 내 코드에 닿기까지, 사이에 뭐가 있을까요?

"랜카드 → 바로 내 앱"이 아닙니다. 앞에서 봤듯 앱은 하드웨어를 직접 못 만지니, 패킷은 먼저 커널을 한참 거쳐야 해요. 체크섬 검사, 순서 맞추기, ACK 보내기, 방화벽 통과... 이 모든 걸 커널이 끝낸 다음에야 앱이 받습니다. 그 길목을 한 정거장씩 따라가 봅시다. 중간에 Tutorial ①의 netfilter 훅이 그대로 등장하는 것도 확인하세요 — ①과 이 장이 같은 그림이라는 증거입니다.

📦 패킷 도착 전

"한 정거장"을 누르면 8080으로 온 패킷이 커널을 통과해 read()에 닿는 과정을 한 단계씩 보여줍니다.

🚚 관찰 포인트

패킷은 유저 공간이 아니라 커널 안에서 대부분의 일(체크섬·순서·ACK·방화벽)을 끝냅니다. 앱의 read()는 마지막에 소켓 수신 버퍼에 쌓인 바이트를 유저 공간으로 복사해 가는 것뿐이에요. 그래서 read()가 메시지 경계를 모르는 겁니다(① 복습).

손님이 한꺼번에 몰리면? — 두 개의 대기 줄

여기서 현실적인 질문. tomcat이 accept()로 손님 하나를 맞아 응답하는 그 짧은 순간에도 새 손님이 계속 들이닥칩니다. 앱이 미처 못 받는 동안 도착한 연결들은 어디서 기다릴까요? 그냥 버려지면 곤란하겠죠.

그래서 listen(fd, backlog)를 부를 때 커널이 대기 줄을 만들어 둡니다. 그런데 줄이 하나가 아니라 둘이에요. 연결이 만들어지는 데 ①의 3-way handshake가 필요하다는 걸 떠올리면 이유가 보입니다 — 악수 중인 손님과 악수를 끝낸 손님은 상태가 다르니까요.

  • SYN 큐 — 아직 3-way handshake가 진행 중인(half-open) 연결이 기다리는 곳. "악수하는 중".
  • accept 큐 — 악수가 끝나(ESTABLISHED) 이제 앱이 accept()로 데려가기만 하면 되는 연결의 줄. 이 줄의 최대 길이가 바로 그 숫자, backlog입니다.

핵심은 accept 큐가 꽉 차면 무슨 일이 나느냐예요. 앱이 너무 느리게 accept()하면 줄이 넘치고, 그러면 악수까지 끝낸 멀쩡한 연결도 커널이 버립니다. 아래에서 직접 줄을 채워 터뜨려 보세요.

02 · 이름 해석

🧭 DNS — 이름이 주소가 되기까지

출발점 코드의 클라이언트는 new Socket("127.0.0.1", 8080)처럼 IP를 직접 박아 넣었죠. 하지만 우리가 브라우저에 실제로 치는 건 www.example.com 같은 이름입니다.

그런데 패킷은 이름을 모릅니다. ① 에서 봤듯 길 찾기는 오직 IP 주소로만 이뤄지거든요. 그렇다면 누군가는 그 사이에서 이름을 IP로 바꿔줘야 합니다. 그 일을 하는 게 DNS예요. 흔히 "인터넷 전화번호부"라 부르는데, 이 번호부엔 반전이 하나 있습니다 — 한 권이 아니라는 것.

왜 번호부가 한 권이 아닐까

잠깐 상상해 봅시다. 지구상 모든 도메인(수억 개)을 한 서버가 다 들고 있다면? 그 서버가 죽는 순간 인터넷 전체의 이름 해석이 멈추고, 전 세계 질의가 거기로 몰려 곧장 터질 겁니다. 누구도 그렇게 안 만들어요.

그래서 DNS는 책임을 계단처럼 위임합니다. 핵심 트릭은, 각 단계가 "최종 답"을 알 필요가 없다는 거예요. "다음엔 누구한테 물어볼지"만 알면 됩니다.

  • 루트(.) — 최종 답은 모름. ".com은 저쪽 TLD 서버한테 물어봐" 만 알려줍니다.
  • TLD(.com) — 여기도 모름. "example.com은 저쪽 권한 서버한테" 만 알려줍니다.
  • 권한 서버 — 드디어 진짜 답: "www = 93.184.216.34".

그래서 한 번의 조회는 루트 → TLD → 권한, 이 세 칸짜리 계단을 밟아 내려갑니다. 한 서버에 권한이 집중되지 않으니 튼튼하고, 각자 자기 구역만 책임지니 관리도 쉬워요.

그런데 이 계단을 누가 올라가나

여기서 의문이 생깁니다. 내 PC가 직접 루트·TLD·권한에 세 번 따로 물어볼까요? 보통은 아닙니다. 내 PC 안의 스텁 리졸버는 게으르거든요. "난 잘 모르겠고, 알아서 답만 가져와" 하고 일을 통째로 떠넘깁니다.

💡 그 일을 떠맡는 게 재귀 리졸버

스텁이 일을 맡기는 상대가 재귀 리졸버(보통 ISP가 주거나, 8.8.8.8 같은 공개 리졸버)입니다. 재귀 리졸버가 대신 루트→TLD→권한 계단을 다 밟아 답을 받아다 주고, 받은 답을 캐시에 저장해 둬요. 그래서 다음에 같은 질문이 오면 계단을 안 밟고 즉답합니다. 이 전 과정을 아래에서 한 단계씩 따라가 보세요.

📦 재귀 리졸버 캐시

TTL — 캐시는 언제까지 믿어도 되나

방금 데모에서 봤듯, 캐시 덕분에 두 번째 조회는 즉답이었습니다. 그런데 여기서 곤란한 질문이 하나 생겨요. 그 캐시를 언제까지 믿어야 할까요? 서버 IP는 언젠가 바뀔 텐데, 영원히 캐시를 믿으면 옛 주소로 계속 가버릴 테니까요.

그래서 모든 DNS 답에는 유효기간이 붙어 옵니다. 이게 TTL(Time To Live, 초 단위)이에요. "이 답은 N초 동안만 믿어도 돼"라는 뜻이죠. TTL을 길게 잡느냐 짧게 잡느냐는 trade-off입니다.

⏱️ TTL 짧게 (예: 60초)

서버를 옮기면 변경이 빨리 퍼집니다. 대신 질의가 잦아져 부하·지연이 늘어요. 장애 대비 전환(failover) 직전에 미리 줄여두는 기법.

🕰️ TTL 길게 (예: 24시간)

질의가 줄어 빠르지만, IP를 바꿔도 옛 주소가 하루 동안 캐시에 남아 사용자 일부가 옛 서버로 갈 수 있어요.

🔑 한 줄 정리

DNS는 계층 위임 + 캐시로 굴러갑니다. 그래서 "DNS 바꿨는데 왜 아직 옛날로 가요?"의 답은 대개 어딘가의 TTL 캐시예요. 그리고 Anycast·GeoDNS로 "가장 가까운 서버 IP"를 돌려주는 것도 DNS의 일입니다(뒤의 CDN과 연결).

✅ 체크포인트
웹 서버 IP를 바꿨는데, 일부 사용자가 한참 동안 옛 IP로 접속됩니다. 가장 흔한 원인은?
정답 C. 변경은 권한 서버에 즉시 반영돼도, 전 세계 재귀 리졸버·OS·브라우저 캐시에는 TTL이 만료될 때까지 옛 IP가 남습니다. 그래서 IP 변경/장애 전환 전에 미리 TTL을 짧게 낮춰두는 게 정석입니다.
03 · HTTP의 탄생

📜 HTTP/0.9 — 날것의 HTTP

출발점 코드의 클라이언트를 다시 보세요. 한 일이라곤 "GET /hello HTTP/1.1\r\n..."이라는 문자열을 소켓에 써 보낸 것뿐입니다. 잠깐 — HTTP 요청이라는 게 정말 그냥 저 글자들을 소켓에 쓰는 거라고요?

네, 정확히 그렇습니다. 그리고 그 단순한 진실을 가장 적나라하게 보여주는 게 첫 버전 HTTP/0.9(1991)예요. 충격적일 만큼 단순해서, "HTTP를 안다"면서도 흐릿했던 전선 위의 실체가 여기서 또렷해집니다.

먼저 — 소켓엔 대체 무엇이 흐르나

① 에서 본 소켓을 다시 떠올려요. TCP 연결이 맺어지면, 그건 그냥 양쪽을 잇는 바이트 통로입니다. 그런데 이 통로는 자기가 나르는 게 HTML인지 그림인지 "HTTP"인지 전혀 모릅니다. 그냥 바이트를 순서대로 실어 나를 뿐이에요.

그러니 "HTTP"란 건 통로 안에 들어있는 특별한 장치가 아닙니다. "우리 이런 모양의 글자를 주고받자"고 양쪽이 미리 합의한 약속일 뿐이에요. 0.9의 약속은 충격적으로 단순합니다. 이게 전부예요:

요청:  GET /경로<CRLF>          ← 딱 한 줄. 그게 끝.
응답:  <html>...본문...</html>   ← 헤더도 상태코드도 없이 본문만
       (그리고 서버가 연결을 닫음 = 응답의 끝)

✅ 0.9에 있는 것

GET 메서드 하나, 요청 경로 한 줄, 그리고 HTML 본문 응답. 끝.

🚫 0.9에 없는 것

상태코드(200/404) ❌ · 헤더(Host·Content-Type) ❌ · GET 외 메서드 ❌ · 연결 재사용 ❌. 전부 나중에 추가됩니다(다음 장).

✅ 체크포인트
HTTP/0.9에서 클라이언트는 응답이 어디서 끝나는지 어떻게 알았을까요?
정답 B. 0.9엔 헤더가 없어 Content-Length도 없습니다. 서버는 본문을 다 보내고 연결을 닫고(FIN), 클라이언트는 "연결이 닫혔으니 응답 끝"으로 판단했어요. 그래서 연결당 한 요청만 가능했고, 이게 1.1의 keep-alive가 풀어야 할 숙제가 됩니다(다음 장).
04 · 헤더와 연결 재사용

📨 HTTP/1.0 → 1.1 — 무엇이 추가됐나

출발점 코드의 요청 첫 줄을 다시 보죠. GET /hello HTTP/1.1, 그리고 Host:와 Connection: close 헤더가 따라붙었습니다. 그런데 방금 본 0.9엔 그런 게 하나도 없었어요. 버전 표기도, 헤더도, 상태코드도.

그 빈칸들이 바로 1.0과 1.1을 거치며 하나씩 채워진 것들입니다. 중요한 건, 본질(요청→응답)은 0.9 그대로 두고 실용성을 위한 살만 붙였다는 점이에요. 무엇이 왜 더해졌는지 순서대로 봅시다.

1.0이 더한 것 — 헤더와 상태줄

0.9를 실제로 써보면 금방 답답해집니다. 돌아온 응답이 HTML인지 그림인지 알 수가 없고(브라우저가 어떻게 그릴지 모름), 요청이 성공했는지 실패했는지도 알 길이 없어요(성공/실패를 알리는 코드가 없으니까). 그래서 1.0은 본문 앞에 메타데이터 줄들을 붙입니다. 이제 요청/응답이 이렇게 생겼어요:

GET /index.html HTTP/1.0          # 버전이 붙은 요청줄
User-Agent: Mozilla/5.0            # 헤더 등장!

HTTP/1.0 200 OK                    # 상태줄 — 코드(200)와 이유
Content-Type: text/html           # 본문이 뭔지
Content-Length: 137               # 본문이 몇 바이트인지 → 연결 안 닫아도 끝을 앎

<html>...</html>

✅ 무엇이 좋아졌나

상태코드(200/301/404/500)로 결과를 구분하고, Content-Type으로 이미지·JSON 등 무엇이든 보낼 수 있고, Content-Length로 "연결을 닫지 않고도" 응답의 끝을 알 수 있게 됐습니다.

1.1이 더한 것 — 핵심은 "연결 재사용"

1.0에도 여전히 큰 낭비가 하나 남아 있었습니다. 0.9처럼 요청 하나에 연결 하나를 쓰고 닫아버린 거예요. 이미지 10개짜리 페이지라면 ① 의 TCP 3-way handshake를 10번 새로 하는 셈이죠. 느릴 수밖에 없어요.

1.1의 가장 큰 기여가 바로 이 낭비를 없앤 연결 재사용(keep-alive)입니다. 그 외에도 실무에 꼭 필요한 것들이 함께 들어왔어요. 출발점 코드의 Host: 헤더도 여기서 등장합니다.

요청은 연달아 보냈는데, 응답은 반드시 보낸 순서대로 와야 합니다. 그래서 첫 응답이 느리면(큰 이미지·느린 쿼리) 뒤의 이미 준비된 응답들도 줄줄이 막혀요. 이 Head-of-Line 블로킹 때문에 브라우저들은 파이프라이닝을 사실상 껐고, 대신 연결을 6개쯤 동시에 여는 꼼수를 썼습니다. 이 한계를 정면으로 푼 게 바로 HTTP/2예요(다음 장).

✅ 체크포인트
HTTP/1.1에서 Host 헤더가 필수가 된 덕분에 가능해진 것은?
정답 A. 0.9/1.0 요청엔 "어느 도메인이냐"가 없어서, 한 IP는 한 사이트밖에 못 가리켰습니다. Host: www.example.com이 필수가 되면서 서버가 같은 IP·포트로 들어온 요청을 도메인별로 구분해 응답할 수 있게 됐어요 — 공유 호스팅·리버스 프락시(뒤의 장)의 토대입니다.
05 · 전송의 대전환

⚡ HTTP/2 · 3 — 완전히 달라진 전송

지난 장 끝에서 1.1의 막다른 골목을 봤죠. 파이프라이닝은 HOL 때문에 못 쓰고, 그래서 브라우저는 연결을 6개씩 여는 꼼수로 버텼습니다. "더 깔끔한 길은 없을까?" — 이 질문이 HTTP/2를 낳았어요.

1.1까지가 "주고받는 글자를 어떻게 다듬나"의 개선이었다면, 2부터는 전송하는 방식 자체가 바뀝니다. 한 연결을 다루는 법이 근본적으로 달라지는 거예요. (물론 본질, 요청→응답은 여전히 0.9 그대로입니다.)

HTTP/2 — 바이너리 프레임 + 멀티플렉싱

1.1의 문제를 한 줄로 줄이면 "한 연결로는 한 번에 하나씩"이었습니다. 그럼 한 연결에 여러 요청을 동시에 섞어 보내면 되잖아요? 말은 쉽지만, 텍스트를 그냥 섞어버리면 어디부터 어디까지가 누구 응답인지 알 수 없게 됩니다. 그래서 HTTP/2는 이걸 가능하게 하려고 세 가지를 도입했어요.

  • 바이너리 프레이밍 — 사람이 읽던 텍스트를 기계가 빠르게 파싱하는 바이너리 프레임(HEADERS·DATA)으로 쪼갭니다.
  • 멀티플렉싱 — 하나의 TCP 연결에 여러 요청을 스트림으로 동시에 흘립니다. 프레임을 번갈아(interleave) 실어, 1.1의 "한 번에 하나" 한계를 깹니다.
  • HPACK 헤더 압축 — 매 요청 반복되는 헤더(쿠키 등)를 인덱스 테이블로 줄여 오버헤드를 크게 낮춥니다.

✅ 결과

1.1에서 브라우저가 연결을 6개씩 열던 꼼수가 사라지고, 연결 하나로 수십 개 리소스를 동시에 받습니다. 서버 푸시도 도입됐지만 실효성이 낮아 지금은 대부분 폐기 추세예요.

직접 보기 ① — 요청이 프레임으로 쪼개져 섞여 간다

말로만 "멀티플렉싱"이라 하면 안 와닿죠. 3개의 요청(스트림 A·B·C)을 한 연결로 보냅니다. 모드를 바꿔 보세요 — 1.1은 메시지를 통째로 하나씩, HTTP/2는 각 메시지를 프레임(HEADERS·DATA)으로 쪼개 번갈아 실어 보냅니다.

그런데 한계가 남았다 — TCP 레벨 HOL

스트림은 논리적으로 독립이지만, 전부 같은 TCP 연결 위에 있습니다. TCP는 바이트를 순서대로만 올려주죠. 그래서 중간 패킷 하나가 유실되면, 그 뒤 모든 스트림의 프레임이 재전송될 때까지 기다려야 합니다. 1.1의 HOL을 앱 레벨에선 풀었지만, 전송(TCP) 레벨 HOL은 남은 거예요.

HTTP/3 — 아예 TCP를 버리다 (QUIC)

여기서 HTTP/3의 발상이 과감합니다. 문제의 뿌리가 "모든 스트림이 한 TCP 연결을 공유하고, TCP가 순서를 강제한다"는 데 있다면? 답은 단순해요. TCP를 안 쓰면 됩니다.

HTTP/3는 TCP 대신 QUIC(UDP 위에 새로 구현) 위에서 돕니다. QUIC은 스트림을 전송 계층에서 직접 다뤄, 한 스트림의 패킷 손실이 다른 스트림을 막지 않습니다. TLS 1.3을 내장해 연결 수립도 빠르고(0-RTT), 네트워크가 바뀌어도 연결이 유지돼요(연결 마이그레이션).

직접 보기 ② — 패킷 손실과 HOL (1.1 vs 2 vs 3)

이번엔 같은 3개 스트림(A·B·C)에 패킷 손실을 주입해, 버전별로 무슨 일이 벌어지는지 봅니다. 멀티플렉싱이 같은 2와 3이 손실 앞에서 왜 갈리는지가 핵심이에요.

✅ 체크포인트

정답 B. 헤더 압축(A)·멀티플렉싱(C)은 이미 HTTP/2가 했습니다. 하지만 2는 모든 스트림이 한 TCP 연결을 공유해, 중간 패킷이 유실되면 TCP의 순서 보장 때문에 모든 스트림이 함께 멈췄어요. QUIC은 전송 계층에서 스트림을 독립적으로 다뤄 이 전송 레벨 HOL을 없앴습니다.
06 · 신뢰의 채널

🔒 TLS / HTTPS — 신뢰는 어떻게 만들어지나

지금까지 우리 EchoServer가 주고받은 건 전부 평문이었습니다. 03장에서 telnet으로 손수 글자를 쳐 응답을 받을 수 있었던 것 기억하죠? 그 말은 곧, ① 의 라우터·프락시처럼 중간에 낀 누구나 그 글자를 그대로 엿보고 심지어 고칠 수 있다는 뜻이에요.

로그인 비밀번호가 그 평문에 섞여 흐른다고 생각하면 아찔하죠. HTTPS는 HTTP 밑에 TLS라는 보안 계층을 한 겹 깔아 이 문제를 막습니다. 그런데 "막는다"가 정확히 무엇을 막는 걸까요?

먼저, "보안"을 세 조각으로 쪼개기

"보안"이라고 뭉뚱그리면 안 됩니다. TLS는 사실 성격이 다른 세 가지를 동시에 보장해야 해요. 하나라도 빠지면 안전하지 않습니다.

  • 🔐 기밀성: 엿봐도 못 읽음 (암호화)
  • 🧬 무결성: 중간에 고치면 들킴 (MAC)
  • 🪪 인증: 접속한 상대가 진짜 그 도메인 (인증서)

💡 대칭키는 빠른데, 키를 어떻게 나눠 갖지?

대칭키(같은 열쇠로 잠그고 풂)는 빠르지만, 그 열쇠를 안전하게 전달하는 게 문제입니다. 도청당하는 채널로 열쇠를 보낼 순 없잖아요. 그래서 TLS는 비대칭키(공개키로 잠그면 개인키로만 풂)로 대칭키를 안전하게 합의한 뒤, 실제 데이터는 빠른 대칭키로 주고받습니다. 핸드셰이크가 하는 일이 바로 이거예요.

07 · 중간 머신의 정체

🔁 프락시 — 중간 머신은 서버이자 클라이언트다

출발점 코드에서 클라이언트는 서버에 곧장 connect했죠. 하지만 현실의 웹 요청은 그렇게 직통이 아닙니다. nginx, CDN, 로드밸런서 같은 중간 머신을 줄줄이 거쳐요. 다들 "요청을 전달한다"고 말하는데 — 정확히 어떻게 전달하는 걸까요?

많은 개발자가 바로 여기서 막힙니다. "프락시가 요청을 전달한다"는 알지만, 그게 한 연결을 그대로 흘려보내는 게 아니라는 것을 놓쳐요. 이 장에서 깰 한 문장을 미리 적어둘게요: 중간 머신은 한쪽엔 서버, 다른 쪽엔 클라이언트로, 별개의 두 연결을 중계한다.

핵심 오해부터 깨기

먼저 가장 흔한 그림과 실제 그림을 나란히 놓고 봅시다. 어디가 다른지가 이 장의 전부예요.

❌ 흔한 오해

"클라이언트 패킷이 프락시를 지나서 서버까지 쭉 간다" — 라우터(①)는 그렇지만 프락시는 아닙니다. 프락시는 클라이언트의 연결을 자기가 받아 끝내고(종료), 서버에는 자기가 새로 연결을 엽니다.

✅ 실제 — 연결이 둘, 소켓이 둘, 4-튜플이 둘

클라이언트는 프락시와만 대화합니다(연결 A). 프락시는 그걸 받아(accept → 서버 역할) 내용을 읽고, 오리진에 새 연결을 걸어(connect → 클라이언트 역할) 대신 요청합니다(연결 B). 클라이언트와 오리진은 직접 만난 적이 없습니다.

포워드 vs 리버스 — 누구를 가리나

➡️ 포워드 프락시 (클라 앞)

클라이언트를 가립니다. 사내망에서 외부로 나갈 때 거치는 게이트웨이·필터·캐시. 서버는 "프락시가 왔다"고 봐요. 클라 설정에 프락시를 지정.

⬅️ 리버스 프락시 (서버 앞)

서버를 가립니다. 외부 요청을 대신 받아 내부 서버로 넘김. nginx·LB·CDN·API 게이트웨이가 전부 이것. 클라는 진짜 서버를 모릅니다.

🪪 그런데 원래 클라이언트 IP는? — X-Forwarded-For

오리진 입장에선 연결 B의 출발지가 프락시 IP라, 진짜 클라이언트가 누군지 모릅니다. 그래서 리버스 프락시는 X-Forwarded-For: 203.0.113.9 같은 헤더로 원 IP를 알려줘요. (또 프락시가 TLS를 종료하면, 뒷단은 평문 HTTP로 받을 수 있습니다 — 06장과 연결.)

🔑 평생 가져갈 한 문장

라우터·프락시·LB·API GW·CDN — 이름이 달라도 전부 "한쪽엔 서버(accept), 다른 쪽엔 클라이언트(connect)"로 두 연결을 중계하는 같은 패턴입니다. 이걸 이해하면 다음 두 장(로드밸런싱·CDN)이 그냥 "리버스 프락시의 응용"으로 보일 거예요.

✅ 체크포인트
리버스 프락시 뒤의 앱 서버가 request.getRemoteAddr()로 접속 IP를 찍었더니 전부 프락시 IP로 나옵니다. 왜일까요?
정답 C. 클라이언트는 프락시와만 연결(A)을 맺고, 앱 서버는 프락시와 연결(B)을 맺습니다. 그래서 앱이 보는 TCP 출발지는 항상 프락시예요. 진짜 클라 IP는 프락시가 넣어준 X-Forwarded-For(또는 Forwarded) 헤더에서 읽어야 합니다 — "중간 머신은 별개의 두 연결을 중계한다"의 직접적인 결과입니다.
08 · 트래픽 분산

⚖️ 로드밸런싱 — 트래픽을 나누는 법

07장에서 프락시가 요청을 한 대의 오리진에 넘기는 걸 봤죠. 그런데 트래픽이 늘어 서버 한 대로 감당이 안 되면 어떻게 할까요? 당연히 서버를 여러 대로 늘립니다.

그러면 곧바로 새 문제가 생겨요. 들어온 요청을 그 여러 대 중 어디로 보낼지, 누가 어떤 기준으로 정하죠? 그리고 한 대가 죽으면 그건 또 어떻게 알아채고 빼죠? 이 일을 맡는 게 로드밸런서입니다. 그런데 정체를 알고 보면, 놀랍게도 07장 리버스 프락시의 특수형일 뿐이에요.

🔑 LB는 리버스 프락시다

LB도 클라 연결을 accept(서버 역할)하고 백엔드로 connect(클라 역할)합니다. 07장 그대로예요. 다른 점은 백엔드가 여럿이라, "이번엔 누구한테?"를 고르는 분산 알고리즘과 죽은 서버를 빼는 헬스체크가 붙는다는 것뿐입니다.

L4냐 L7이냐 — 어느 계층에서 나누나

🧭 잠깐 — L4·L7이 뭐였죠?

09 · 안 보내는 게 제일 빠르다

📦 캐싱 · CDN

드디어 마지막 장입니다. 지금까지 요청 하나가 서버에 닿는 길을 따라왔는데, 여기선 정반대를 봅니다 — 어떻게 하면 그 길을 덜 갈까.

생각해 보죠. 우리 EchoServer가 매 요청마다 DB까지 가서 똑같은 50KB 이미지를 만들어 준다면, 천 명이 같은 걸 요청할 때 동일한 일을 천 번 반복하는 셈이에요. 엄청난 낭비죠. 여기서 두 가지 깨달음이 나옵니다. 가장 빠른 요청은 아예 안 보내는 요청이고, 그게 안 되면 가장 가까운 곳에서 받는 요청이다. 이 두 문장이 캐싱과 CDN의 전부입니다.

캐시는 한 곳이 아니다 — 계층

요청은 아래 계단 중 가장 가까운(왼쪽) 캐시에서 멈출수록 빠르고 쌉니다. 멈추지 못하면 한 칸씩 오른쪽으로 갑니다.

💻 브라우저 캐시 → 🌍 CDN 엣지 → 🔁 리버스 프락시 캐시 → 🖥️ 앱(오리진) → 🗄️ DB

🌍 CDN이 가까운 이유 — Anycast

CDN은 전 세계에 엣지 서버를 두고, Anycast·GeoDNS(② 참조)로 사용자를 가장 가까운 엣지로 보냅니다. 서울 사용자는 서울 엣지에서 받으니, 미국 오리진까지 갈 필요가 없어요.

"안 보낸다"를 어떻게 구현하나 — max-age와 ETag

그런데 브라우저가 제멋대로 "안 보내고 캐시 쓰겠다"고 하면 위험하죠. 그새 서버 내용이 바뀌었을 수도 있으니까요. 그래서 주도권은 서버에 있습니다. 서버가 응답에 "이건 이렇게 캐시해도 돼"라는 규칙을 헤더로 붙여 보내요. 핵심은 두 개입니다.

  • Cache-Control: max-age=N — "N초 동안은 물어보지도 말고 캐시 걸 써". 이 동안은 네트워크 요청이 0건.
  • ETag — 리소스의 지문. 만료된 뒤엔 If-None-Match: <etag>로 "바뀌었어?"만 물어요. 그대로면 304 Not Modified(본문 없이!) 응답 → 큰 본문 재전송을 아낍니다.

🔑 가장 어려운 건 무효화 — cache invalidation

배포로 파일이 바뀌었는데 캐시가 옛 걸 주면 큰일이죠. 그래서 버전드 URL(app.a1b2.js)을 써서 바뀌면 URL 자체가 달라지게 하거나, CDN에 purge를 날립니다. 또 stale-while-revalidate로 "일단 옛 걸 즉시 주고 뒤에서 갱신"해 체감 속도를 높이기도 해요. "컴퓨터 과학의 두 어려운 문제 중 하나가 캐시 무효화"라는 농담이 괜히 있는 게 아닙니다.

📚 계층 모델과 "L4·L7"의 정체

본문(특히 로드밸런싱)에서 L4·L7이라는 말이 갑자기 나왔죠. 이건 네트워크를 계층(layer)으로 나눈 모델의 "몇 번째 층"을 가리키는 약칭입니다. 이 튜토리얼은 Tutorial ①의 TCP/IP 4계층을 기준으로 설명하니, 그걸 축으로 OSI 7계층과 나란히 정리합니다.

💡 한 줄 먼저 — L4와 L7만 기억하면 됨

L4 = 전송 계층 = TCP/UDP(포트·연결). L7 = 응용 계층 = HTTP 같은 앱 프로토콜. 그래서 "L4 로드밸런서"는 IP·포트만 보고 빠르게 넘기고(① 의 TCP 4-튜플 수준), "L7 로드밸런서"는 HTTP의 URL·헤더·쿠키까지 읽고 판단합니다. 나머지 층 번호는 몰라도 실무엔 거의 지장 없어요.

🔑 왜 본문은 TCP/IP 기준인가

OSI는 7칸으로 깔끔하지만, 실제 인터넷 구현(소켓·TCP·IP)은 TCP/IP 4계층에 더 정확히 들어맞습니다(세션·표현 계층은 현실에선 응용 계층이 흡수). 그래서 본문 설명은 TCP/IP 기준이고, "L4/L7"은 업계가 즐겨 쓰는 OSI 번호 약칭으로만 가져다 씁니다. 둘은 충돌이 아니라 같은 그림의 다른 눈금자예요.
